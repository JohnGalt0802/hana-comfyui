# 修复 issue #1 / #3 / #4（v0.16.0 ~ v0.16.2，2026-10-30）

> 三条都出自同一位报告者（Raizombie），四条 issue 全部带环境、复现步骤与根因定位。
> 本文记录改了什么、为什么这么改、验证到什么程度，以及 #2 为什么不需要改代码。

## #4 UI→API 转换整份拒绝动态输入节点（v0.16.0）

**现象**：含 `FlexibleOptionalInputType` 的社区节点（如 LoraManager 的 TriggerWord Toggle）连了线，转换阶段整份 throw，一条工作流都提交不上去。附带：`AUTOCOMPLETE_TEXT_LORAS` 这类自定义 widget 类型不在白名单，字段被静默跳过，后端报必填项缺失。

**根因**：`/object_info` 只上报 `required` 与 `optional` 两组可枚举字段，动态输入槽不在其中。`convertUiToApi` 收编连线时校验「槽名必须是声明输入」，于是把合法连线判成非法，攒进 problems 后整份拒绝。

**改法**（`app/lib/workflow-tools.mjs`）：

1. problems 拆成 errors 与 warnings。只有「槽不对应声明输入且能找到连线」降级为 warning 并按连线原样收编；无名槽、连线缺失、静音/旁路、子图、类型不在 object_info、R1 分歧仍归 errors。
2. named 分支由白名单改黑名单：只跳过已知 socket 类型，其余（含将来新出现的 widget 类型）默认当 widget。该分支按名取值且有 `hasOwnProperty` 守卫，放宽无错位风险。
3. 位置回退分支继续用白名单（`wvi` 位次对齐只认确知形态），追加 `AUTOCOMPLETE_TEXT_LORAS`。
4. 新增可选第三参 `{ strict = false, onWarning = null }`；`strict:true` 行为与旧版完全一致，留作排查档。

**验证**：`app/lib/workflow-tools.test.mjs` 19 条（必拒 6 类 + 必放行 2 类 + strict + options 容错 + origin 防线）。变异测试确认摘掉白名单新用例会红。真机验收用本机真实 `/object_info`（2535 节点类）与 rgthree `Power Lora Loader` 的动态槽复现：旧版拒绝、新版宽模式通过并正确收编 `lora_1: ["1",5]`、`strict:true` 仍拒绝。

**已知取舍**：`NON_WIDGET_INPUT_TYPES` 是常见 socket 类型的近似名单（实测 220 个输入类型只覆盖 20 个），漏项靠 `widgets_values_named` 本就没有该键兜底。降级分支不检查 origin 是否可发射（声明槽那条路径改前就有同样的洞）。

## #3 停止服务假成功（v0.16.1）

**现象**：点「停止服务」界面显示已停，ComfyUI 仍在跑。日志 `pids=[] stopped=[]`，接口返回成功。

**根因（两层）**：

1. 某类机器上 netstat 列出 8188 的 LISTENING 行但最后一列 PID 是 0；`Get-NetTCPConnection -State Listen` 返回空但查询成功。两路都是「成功、零个」，`bothOkEmpty` 短路成立，跳过命令行兜底。
2. 即使不短路，兜底里 `reconcileCmdlineCandidates(c.cands, b.pids, b.ok)` 的第三参传 `b.ok`，而 `b.ok=true` 且 `pids=[]` 会被当作可信监听集合，单候选被交集淘汰。**这意味着 2026-10-21 那次「失明判 ok:false」的修复，在 PowerShell 可用的机器上从未真正生效过。**

**改法**（`app/runtime/comfy-relay.mjs`）：

- `netstatListeningPids`：目标端口命中 LISTENING 行但 PID 不可见 → `ok:false, hidden:true` + 独立 reason（与「全局无 LISTENING 行」区分）
- `psListeningPids`：`HANA_PS_PID:0` → `ok:false, hidden:true`；`HANA_PS_EMPTY` 仍是「确无监听者」
- `bothOkEmpty` 增加 `!pidHidden` 前置条件
- 兜底第三参改为 `b.ok && b.pids.length > 0`
- 端口变化时归零 pidCache
- `diag` 透出 `hiddenRows`，诊断串渲染成 `netstat=1(隐1)`

**曾经走过弯路**：为防 CIM 全表枚举拖累状态面板，一度加了 60 秒节流。实测 `Get-CimInstance Win32_Process` 约 90~170ms（大头是启动 PowerShell 子进程），且这条路径只在双盲机器才走到，节流换来两个洞（返回值表达不了「未知」、5 秒缓存穿透）和三轮回炉，最终整层撤除。教训：性能优化先量再设计。

**验证**：真机 `pids: [36832]` 正常；异常形态靠 stub 注入矩阵（netstat 有/无/PID 不可见 × ps 有/空/失明，8 行）覆盖，其中「netstat PID=0 + ps 空 + 单候选」能正确采用 PID 而不再返回空。

## #1 预览帧到不了任务卡（v0.16.2，仅诊断）

**现象**：开启实时预览后卡片收不到采样帧。后端确认在发帧（报告者直连 /ws 收到 12 步 12 帧）。

**根因**：ComfyUI 的预览帧只发给发起该任务的 `client_id`。画布执行由前端直接 POST `/prompt`，中继不是发起者，结构上收不到。中继判不出归属就静默丢弃，日志无痕迹。

**改法**：只做可见性，不改链路。

- 无归属帧不再静默：`noteOrphanPreview` 记元信息（不存帧字节，无读出口），`warnOnce` 按原因分桶（`no-prompt-id` / `ambiguous-running`；`unknown-prompt-id` 为不可达的防御分支）
- `status` 的 `events.preview` 暴露 `received / attributed / attributedBySoleRunning / droppedNoOwner / oversizeDropped / emptyDropped / droppedByReason / lastReceivedAt / lastOrphan`，恒等式 `received === attributed + droppedNoOwner + oversizeDropped + emptyDropped` 成立
- `pickPreviewOwner` 判定逻辑一字未改

**不治本的理由**：帧只发给发起者，画布执行时人就在 ComfyUI 前端看着逐帧预览；真正需要卡片预览的 agent 后台提交已经有帧。改提交链路的收益不足以支撑风险。此为已知限制，不是未修完。

## 遗留

1. `pidCachePort` 归零写在 `force` 计算之后，靠「归零后 at=0 必然使缓存失效」凑对，结果正确但顺序脆弱。
2. 双盲机器上 `cmdlineComfyCandidates` 走 `spawnSync`，PowerShell 卡到 20 秒超时会阻塞中继事件循环（HEAD 既有）。
3. `Power Lora Loader` 这类节点在画布执行时若唯一 running 记录不匹配，帧会被兜底归属给错误任务，目前只计数（`attributedBySoleRunning`）不改判定。
