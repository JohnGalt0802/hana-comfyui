## 一、现象（用户报告）

在 `moss-image-SFT综合` 画布提交了几次生图，切到 `Qwen21 t2i 质量版 (00002)` 又提交了几次，
回来发现提交树「串台」：出现一个所有分组色条全亮的提交节点。

## 二、根因

提交链路的**抓图**与**取工作流身份**隔着一次 `await`：

```js
// installQueuePromptCapture（包装 api.queuePrompt）
let graph = app.graph.toJSON();               // ① 抓图（画布 A，同步）
const r = await orig.apply(this, callArgs);   // ② 原生提交，耗时数秒
...
void reportHistoryCommit({ graph, promptId, blocks, source });  // ③ 上报

// reportHistoryCommit
let workflow = currentWorkflowInfo().name;    // ④ 此刻才取工作流名（可能已是画布 B）
```

只要在 ① 与 ④ 之间切换了画布，就变成**图归 A、名字归 B** —— 快照被写进 B 的历史。
`identity` 里的 `workflowId` / `workflowPath` 同样是在 ④ 附近由 `withWorkflowId()` 现取，一起错。

## 三、实证

**证据 1：图与历史归属不符**

`c01b05e9`（moss-image-SFT综合）的索引里，`seq=359` 的快照是 42 个节点、类型全为
`TextEncodeQwenImage21 / BasicGuider / EasyCache` 等 Qwen 工作流特征，**没有任何 MOSS 节点**；
三秒后的 `seq=360` 又变回 17 节点的 MOSS 工作流（`MOSSImageHFLoader / MOSSCacheSelector` 等）。
该画布本体一直是 MOSS 工作流。

**证据 2：时间间隔符合「提交中切换」**

| 时间（北京） | 画布 | seq | 图 |
|---|---|---|---|
| 17:46:03 | SFT综合 | 357 / 358 | MOSS（merge） |
| 17:48:19 | SFT综合 | **359** | **Qwen 42 节点** |
| 17:48:22 | SFT综合 | 360 | MOSS 17 节点 |
| 17:52:18 | Qwen质量版00002 | 1183 | Qwen（parent=2） |

**证据 3：「所有色块都亮」不是串台标记**

提交节点上的色条是**分组框色条**（`.hnode-bar`）：一条对应一个画布分组框，本次提交的 delta
碰过该框则亮。`359` 亮 5 条、`360` 亮 6 条，因为它们是**整套工作流被替换**，delta 覆盖全部节点。
Qwen 画布正常提交只亮 1~2 条（如 1180 亮 2 条、1181/1182 各亮 1 条）。

## 四、修法（选 A）

**在抓图那一刻同步捕获工作流身份，随快照一起上报。**

1. 新增 `captureWorkflowIdentity()`：一次性取 `{name, id, path, temporary}`，中间无 `await`。
2. `withWorkflowId(payload, identity?)`：传了 identity 就用捕获值，否则维持原行为（现取）。
3. `reportHistoryCommit({..., identity})`：`workflow` 取 `identity.name || currentWorkflowInfo().name`；
   请求体用 `withWorkflowId(body, identity)`。
4. `installQueuePromptCapture`：抓图后立刻 `captureWorkflowIdentity()`；
   `source` 也一并快照（`historyCommitSource` 会被 agent 通道临时改成 `"agent"` 再还原，跨 await 会读错）。

**不选 B（图签名与 HEAD 快照差太远就拒绝）的理由**：用户经常在回跳后提交（真实的早期分叉），
签名差异大是合法场景；用签名距离做拒绝条件会误杀，且阈值无法自证。身份问题用身份解决，
不要用内容猜测代替。

## 五、数据清理（只清一条）

`96dd27ac`（Qwen质量版00002）`seq=1183` 的 `parent` 由 `2` 改为 `1182`。

- 该记录是在 HEAD 停在 seq 2 时提交的，图上表现为一条横跨 1181 条历史的长边；
- 泳道算法对比：修复前 9 条泳道 → 修复后 **8 条**（多出来的那条就是这条长边）；
- 备份：`D:\HanakoWorks\_temp\index-96dd27ac-before-parentfix.jsonl`；
- **delta 不重算**：它记录的是「当时相对 HEAD 的差异」（seq 2 的图 vs 提交时的图，只差 2 个 widget），
  属历史事实；若重算成相对 1182，会与当时画布的实际变化不符。

`c01b05e9` 里 `359/360` 两条错配记录：**不动**（用户决定），作为历史保留。
