## 〇、一句话结论

git 客户端的提交图（gitk / GitKraken / VS Code Git Graph）绘制的是 **DAG**；我们的提交图是 **严格树（每节点单 parent）+ 只分不合（无 merge）+ 时间戳自打（天然拓扑序）**。
直接套 git 的泳道算法会撞**三面墙**：

1. **泳道爆炸**：git 分支最终 merge 会让宽度收敛，我们的树**只分不合 → 泳道数单调增长**，永不回收；
2. **纵向高度**：泳道式把「提交数」搬到了 X 轴（解决了），但把「分支数」搬到了 Y 轴——分支一多，纵向又爆；
3. **「合并」语义不同**：我们的「合并」是「同一提交含多次运行（runs）」= **节点上叠次数**，不是 git 的「两条线汇成一条」。

## 一、关键前提：我们的是「树」，不是「DAG」`[源码]`

| 维度 | git（DAG） | 我们（树） |
|---|---|---|
| 父节点 | `parents[]` 多值（merge ≥2） | `parent: number \| null` **单值** |
| 合流 | 有 merge commit，分支汇回主干 | **无**——分支一旦分出，永不合并 |
| 排序依据 | committer date（**可能非拓扑序**，rebase/时钟问题） | 自打 `at`，且 `parent.seq < child.seq` **恒成立 → 按 seq 排即拓扑序** |
| 数据量级 | 万级提交、上百分支 | 工作流级别，十~百级提交、个位分支 |

> 依据：`app/lib/canvas-history.mjs` `buildIndexLine` → `parent: normParent(m.parent)`（单值）；`方案-画布提交历史-P5-数据模型.md` §2.1。
>
> **正面影响**：因为 `parent.seq < child.seq` 恒成立，**按 seq 升序排天然是拓扑序**，不需要 pvigier 那套 `temporal_topological_sort`（他必须处理「committer date 非拓扑序」的情况）。这是我们比 git 简单的地方。
>
> **负面影响**：没有合流 → 泳道宽度只增不减，这是 git 客户端**不存在**的问题。

## 二、成熟做法对照 `[外部]`

### 2.1 泳道分配与回收（最核心）

- **gitk / `git log --graph`**：单提交一行，列会在分支结束后**复用**。git 2.37+ 提供官方截断开关 `--graph-lane-limit=<n>`：「Lanes over the limit are replaced with a truncation mark `~`」——**官方承认泳道会爆炸，给出的答案是「超限截断」**。
  来源：<https://git-scm.com/docs/git-log>
- **pvigier「straight branches」算法**（gitamine 作者，硕士论文专章）：
  - 关键动作 `replace d by c in B`——**子节点继承父节点的列位**，这就是列复用；
  - 分支结束用 `B[d'.j] = nil` 释放该列，且**不移动其他列**（因此分支是「直」的）；
  - 父有多个子时：**一个继承父列、其余新开列**（选谁继承有讲究，默认选最左）；
  - 强调**输出必须确定性**：同一历史两次渲染结果必须一致，不依赖遍历顺序。
  来源：<https://pvigier.github.io/2019/05/06/commit-graph-drawing-algorithms.html>
- **GitKraken**：追求**完全笔直的分支**（每分支固定一列），可读性最高，是闭源的；SourceTree 半直（偶尔弯）。
  来源：同上（作者横向对比 Git Cola / Git Extensions / gitk / GitKraken / SmartGit / SourceTree）。
- **d3-dag / Sugiyama 分层布局**：适合「需要表达层级/依赖」的 DAG；对我们这种「一条主干 + 偶尔分叉」的树，**泳道式更简单也够用**，不需要上分层算法。
  来源：<https://github.com/erikbrinkman/d3-dag>、<https://en.wikipedia.org/wiki/Layered_graph_drawing>

### 2.2 性能优化（大历史）

pvigier 实测（react 仓库，10 万级提交）：**只渲染可见的节点+边** 比全量渲染快 **~180 倍**（106ms → 0.58ms）。
做法：节点按行高整数除法 O(1) 定位；边用「区间树」找与可视区相交的边。
来源：同 2.1

### 2.3 时间轴 vs 拓扑轴

pvigier 明确：**按 committer date 排序不保证拓扑序**（rebase / cherry-pick / 多机时钟不同步都会打破）。他发明 `temporal_topological_sort` 兼得两者。
**我们的情形天然免疫**——见 §一，不需要。

## 三、问题清单

### 🔴 P0 — 真缺陷（现有代码即错，或方案落地必错）

**Q1 · 线性历史退化成 N 行纵向长条** `[源码]`
- 现象：`historyTreeRenderTree` 按 **depth 分层**（`depthOf` / `rows: Map<depth, ent[]>` / `.htr-row` 一层一行）。
- 根因：线性提交链 `parent.depth + 1` 逐个递增 → **每次提交独占一行**。
- 影响：17 次提交 = 17 行（面板 `height:200px` 约装 7~8 行）；180 提交 = 180 行 = **十几屏滚动**。密度上去直接废掉。
- 性质：**布局模型问题**，非样式问题。

**Q2 · 泳道无回收 → 泳道数单调增长（我们的树特有）** `[推断，由§1+§2.1]`
- 我们的树**只分不合**（无 merge），分支到叶子后**没有「合流」把该列还回来**。
- 若照 pvigier 简化实现，每个新分叉新开一条泳道，且**已休眠的分支仍虚占列位**（其「最上端节点」还挂在 active 列表里，直到被 child 接手）。
- 影响：长期使用后泳道数 ≈ 历史分叉总数。20 条泳道 × 30px = 600px 高，**面板装不下**。
- 对照：git 靠 merge 收敛 + `--graph-lane-limit` 截断；**我们两者都没有**。

**Q3 · 「合并」语义 ≠ git merge，视觉会误导** `[源码]`
- 我们的合并 = 同 sig 的多次运行 → `mergeInto` 追加到 `runs[]`（「一提交多 runs」）。
- 数据模型里**没有多 parent、没有合流**。
- 影响：若图上画成 git 那样「两条线汇成一条」，用户会**误以为分支合流**。应表现为**节点上叠一个计数**（如「×3 runs」或色条加粗/加亮），而不是连线汇聚。

### 🟡 P1 — 设计缺陷（方向对，但会撞墙）

**Q4 · 泳道的纵向高度 vs 面板高度** `[推断]`
- 泳道式解决了「提交数」但对「分支数」不设防：分支多 → Y 轴爆。
- 需：泳道数上限 + 超出「折叠为休眠分支」或「懒展开（默认只显主干，分叉按需展开）」。

**Q5 · 横轴是「序」不是「时间比例」** `[源码]`
- 现横轴只标两端时间（`t0`/`t1`），中间按 seq 等距。
- 三次 1 分钟内提交 vs 三次跨三天提交，**视觉等宽**。
- 建议：保持等距（整齐、稳定、实现简单），但需 John 确认；hover 已能看具体时间。

**Q6 · 新增提交落在最右端 → 长历史要一直往右滚** `[推断]` ⚠️ 需拍板
- 「左旧右新」是时间轴惯例，但**新提交会跑到最右**。历史一长，打开弹层看到的是最旧的，要看最新的得滚到底。
- 备选：① 默认自动滚到最右（新提交可见）；② 反时间轴「右旧左新」（新提交常驻最左）；③ 保持现状 + 打开即滚右。
- **这条影响用户第一眼看到什么，必须定。**

**Q7 · 框视角过滤后拓扑断裂** `[源码]`
- 框视角按当前框过滤提交。若 `parent` 不在过滤集内，连线画到哪？「第几条提交」的关系会断。
- 现状：**宁多勿漏**（不过滤，只淡化 `data-legacy` / 不命中条）——已规避，但「真正想只看某框的提交线」这个诉求尚未满足。

**Q8 · 性能：DOM 数 = 提交数** `[推断]`
- 每节点 = 色条堆(1~N 根) + stem + 容器，180 提交 ≈ 700+ DOM，尚可；1800 就卡。
- 需：**横向虚拟化**（只渲染可视区节点+边），照 pvigier 的可见区算法。

**Q9 · 分支无名字/无归属标注** `[源码]`
- 「3 分支」但看不出是哪 3 条、从哪分出来的。
- 建议：分叉点标「从 #N 分出」，或给分支起 agent 可命名的短名（长线议题）。

**Q10 · 空存档（save 但画布无变化）** `[推断，需实测]`
- 若连续两次「存档」且 sig 相同，会不会产生两个 save 节点？
- 需确认合并判定对 `kind="save"` 的行为（`shouldMergeWithHead` 只看 sig，未区分 kind）。

**Q11 · 泳道分配必须确定性** `[外部 §2.1]`
- 同一历史两次渲染泳道必须一致，否则用户眼花。pvigier 专门强调。

### 🟢 P2 — 打磨 / 待拍板

**Q13 · 缩略图联动**：框里刻度有缩略图，树节点无。是否统一？
**Q14 · HEAD / 游离状态**：回跳后 HEAD 指向中间节点，图上需能看出「当前停在哪」。

## 四、对「泳道式」的落地建议（把 Q1~Q4 一次解掉）

### 4.1 泳道分配算法（树专用简化版）

```
active[L] = 该泳道当前「悬挂末端」的节点 seq（null = 空位可复用）
按 seq 升序（= 拓扑序）遍历提交 c：
  父 p = c.parent
  若 p 非空且 ∃L: active[L] == p：
      c.lane = L              // 子继承父列（回收：父占位交给子）
      若 p 有多个子 → 其余子随后会「找不到空位 → 新开」
  否则：
      c.lane = 第一个空位；无空位 → append 新泳道
  active[c.lane] = c
  // 释放：一个节点若已有 child 接手，其旧占位自然被覆盖；
  // 叶子节点保留占位，直到「休眠判定」把它折叠
```
- **确定性**：按 seq 升序、同分叉固定选「最左继承」，输出唯一。
- **回收**：pvigier 的 `B[j]=nil` 不移动其他列 → 分支保持笔直。

### 4.2 休眠分支折叠（解 Q2/Q4，我们必需）

```
若泳道 L 的悬挂末端 over 阈值（如：距最新提交 > 30 次 or > 7 天）无新 child：
  → 折叠为「休眠分支」标记（< 从 #N 分出 · 12 次提交 >）；泳道 L 释放复用
```
- 展开按钮可查看休眠分支全文。
- 这是**我们没有 merge 的补偿机制**，是解泳道爆炸的唯一正解（git 靠 merge，我们靠休眠折叠）。

### 4.3 纵向封顶

- 默认只显「主干 + 活跃分支」泳道；超过 `maxLanes`（如 5）→ 其余进「+N 休眠」。
- 高度自适应：`H = min(实际泳道数, maxLanes) × laneH`。

### 4.4 性能（将来）

- 横向虚拟化：只渲染可视 X 区间内的节点与边。
- 提交数 < 500 时不必做；> 500 再做。
