## Q2. `ctx.surfaces.open` 的适用范围

**结论**：`ctx.surfaces.open` **不是**「生产 App 把自家 card 推到宿主主界面」的通道；它是面向 **App-owned isolated instance（builder 环境）/ environment（带 appId）** 的 surface 视图开关。生产 App 在宿主主界面打开自家已声明卡，走的是另一条——UI 能力 `hana.cards.open`（受 `allowedSlots` 约束，见 Q4）。

证据（SDK 契约，`sdk/app-contract/surfaces.d.ts`）：

- `surfaces.d.ts:9` 顶层注释与句柄定义
  ```ts
  /** A view of one declared UI contribution in an App-owned isolated instance. */
  export type AppSurfaceSlot = "card" | "settings" | "function-panel" | "slot";
  interface AppSurfaceHandleBase { ... readonly slot: AppSurfaceSlot; ... }
  ```
- `surfaces.d.ts:38-47` 句柄联合体——强制二选一：`instanceId` **或** `environmentId`
  ```ts
  export type AppSurfaceHandle = AppSurfaceHandleBase & (
    { readonly instanceId: string; readonly environmentId?: never; }
  | { readonly environmentId: string; readonly instanceId?: never; }
  );
  ```
- `surfaces.d.ts:73-90` `open` 的两个重载签名
  ```ts
  open(input: (AppSurfaceOpenBase & { instanceId: string; environmentId?: never })
            | (AppSurfaceOpenBase & { environmentId: string; appId: string; instanceId?: never })
    ): Promise<AppSurfaceHandle>;
  ```
  其中 `AppSurfaceOpenBase`（`surfaces.d.ts:66-74`）含 `definitionId`（要打开的 surface 定义 id）、`slot?`、`parentSurfaceId?`、`detached?`，但**不接收生产 App 上下文里的 `pluginId`**（生产 App 上下文是 `ctx` 自带 `e.pluginId`）。

含义：传入 `instanceId` ⇒ 操作某个 App 自有隔离实例（builder/预览实例）；传入 `environmentId+appId` ⇒ 操作某环境。两者都不是「在生产 App 自身已挂载 UI surface 的前提下、把卡推到宿主 chalkboard 主界面」的语义。生产 App 主界面开卡靠 `hana.cards.open`（UI 能力，仅当其自身某 surface 已挂载且完成握手后可用，见 Q4）。

置信度：**代码推断**。

## Q3. 三种 iframe surface 的挂载机制 + 非用户交互挂载途径

**结论**：card / function-panel / settings 三种 surface 均由**用户入口**挂载（卡中心、设置页、活动卡的左侧功能面板/导航项）。存在两类「非用户点击」的开卡，但都依赖一个**前置已挂载 surface** 或 **工具返回**：(a) `hana.cards.open` 在已挂载且完成握手的 App surface 内被调用，可程序化打开同 App 另一张已声明卡；(b) 工具返回 `details.card` 时宿主自动在聊天流渲染卡。未发现「无需任何前置已挂载 surface、由 API/事件直接把生产 App 卡/功能面板挂载到主界面」的证据。

## Q4. 复核 `allowedSlots` 结论

**结论（确定）**：`hana.cards.open` 在渲染层注册时 `allowedSlots = ["card","function-panel","settings"]`（变量 `fs`，字符偏移 **10991**），handler 在 `_s()`（偏移 **13249**）返回 `{name: Qi.OPEN, allowedSlots: fs, ...}`，其中 `Qi.OPEN = "hana.cards.open"`（`_ui-protocol.d.ts:200`）。语义：`allowedSlots` 列出**调用方 UI surface 的 slot 类型**——只有处于 `card` / `function-panel` / `settings` 这三种「App 认证 iframe surface」内的代码才能调用该能力。App **原生窗**（`ctx.windows.create`）不在此 slot 集合内，因此不是「被拒绝」，而是该能力**根本不向原生窗暴露**（与「已完成事实」的 `APP_WINDOW_UI_OPERATION_UNAVAILABLE / This App window does not provide hana.cards.open` 一致）。

证据：

- `PlanModeButton-CxtrW7Pn.js` 字符偏移 **10991**（字面量定义）
  ```js
  const fs=["card","function-panel","settings"];
  ```
- 同文件偏移 **13249**（`_s()` handler 注册）
  ```js
  function _s(){return[{name:Qi.OPEN,allowedSlots:fs,requiresGrant:!1,validatePayload:hs,handle:ws}]}
  ```
  且 `Qi.OPEN` 对应 `"hana.cards.open"`（`_ui-protocol.d.ts:200`：`readonly OPEN: "hana.cards.open";`）。
- 同文件偏移 **12772**（`ws` handler 主体）——先经 `gs` 守卫（需 surface 已挂载且已完成可信握手），再在 `pluginCards` 中按 `pluginId===e.pluginId && id===cardId && channel==="app"` 查找声明卡：
  ```js
  function ws(e,t){
    gs(e);                       // 守卫：surface 必须 active + ready
    const {cardId:n,instanceKey:i}=t;
    ...
    const r=S.getState().pluginCards.find(o=>o.pluginId===e.pluginId&&o.id===n&&o.channel==="app");
    if(!r) throw new Oe("APP_CARD_UNAVAILABLE","This App does not currently declare the requested card.");
    return ds(e.pluginId,r,{...});
  }
  ```
- 能力网关 `Yc`（`PlanModeButton-CxtrW7Pn.js` 偏移 **68405**）对每条能力做 slot 校验：
  ```js
  function Yc({message:e,context:t,capabilities:n}){
    const i=n.find(o=>o.name===e.type);
    if(!i) return ...UNKNOWN_TYPE...;
    if(!i.allowedSlots.includes(t.slot)) return ...SLOT_DENIED...;  // "Plugin UI capability \"...\" is not allowed in ${t.slot} slots."
    if(i.requiresGrant && !t.grantedCapabilities.has(i.name)) return ...CAPABILITY_DENIED...;
    ...
  }
  ```
  ⇒ `hana.cards.open` 仅当 `t.slot ∈ {"card","function-panel","settings"}` 通过；原生窗不属于这三者之一 → `SLOT_DENIED`/能力缺失。
- 对比：宿主原生窗的 slot 标识不是上述三者。`AppSurfaceSlot`（`surfaces.d.ts:9`）与 `PluginUiSlot`（`_ui-protocol.d.ts:570`）把 `card|settings|function-panel|slot|input-panel` 列为 App 认证 surface 的 slot；原生窗（`ctx.windows.create` 的 `chrome:"native"` 窗口）是独立的 window-kind 载体，不持有这些 slot 之一，故 `hana.cards.open` 不对其暴露。

置信度：**实测（代码实锤）**。
