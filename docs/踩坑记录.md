## 1. App 改名后宿主不刷新显示名（2026-09-24）

**背景**：显示名从 `ComfyUI-Hana` 改成 `Hana-ComfyUI`，app 内 17 处文案（manifest / UI / 工具描述 / 技能文档）全部改完、同步到宿主副本、重启宿主——**宿主 `/api/extensions` 仍返回旧名**。

**根因**：宿主把 App 的展示信息缓存在 `~/.hanako/extensions/installs.json` 的 `records[].summary` 里（含 `name` / `description`）。**宿主启动时不从 manifest 重新生成 summary**，只信这份记录——所以改 manifest + 重启都没用。

**试过但失败的路**：

| 尝试 | 结果 |
|---|---|
| 重启宿主 | summary.name 仍是旧名 |
| `POST /api/extensions/install` + `staged/<id>/confirm`（标准重装） | `confirm` 报 `EPERM: operation not permitted, rename 'apps\comfyui-hana' -> '...update-backup-...'` |
| 手动重命名该目录（PowerShell `Rename-Item` / `cmd move`） | `Access denied`（cmd 报 `0 dir(s) moved.`） |
| 停用接口 `POST /api/extensions/app:comfyui-hana/enabled` | 404（该版本宿主未暴露） |

**当时的排查**：
- 目录内**子文件**（如 `manifest.json`）可以正常重命名 → 不是文件锁
- 目录 ACL 正常（当前用户 FullControl）→ 不是权限
- **没有任何进程的命令行含 `comfyui-hana`** → 不是 App/中继进程占用

→ 结论：`apps/comfyui-hana` 存在**目录级占用**（疑似宿主持有的目录句柄），来源未定位。

**实际采用的解法（实测有效）**：

1. 备份 `~/.hanako/extensions/installs.json`
2. 只改该记录 `summary.name` → `Hana-ComfyUI`（正则定点替换，别整体重排 JSON）
3. `POST /api/extensions/app:comfyui-hana/reload`

reload 会让宿主重读记录 → **无需重启宿主即可生效**（复核：installs.json 与宿主 API 均返回 `Hana-ComfyUI`）。

**遗留**：目录级占用未根除。只要它存在，**该 App 就无法走 install+confirm 重装流程**。将来要重装（比如改 manifest 的能力/卡片声明）时，要么在宿主 UI 里操作、要么先解决目录占用（或等宿主修）。

> 备注：hana-downloader 走同样的 install+confirm 重装流程是**成功**的，说明这不是普遍现象——差异点仍在查（怀疑与「宿主重启后 App 未重新拉起、目录句柄未释放」有关）。

## 2. 工作区能开，但自定义节点扩展脚本 403（2026-09-25）

**现象**：工作区里 ComfyUI 官方前端能正常渲染，但**自定义节点/扩展缺块**；控制台报 `scripts/app.js 403`、`scripts/api.js 403`（群友反馈同现象，描述为“静态资源被挡在门外”）。

**排查链**：

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | 看宿主日志里的 403 | 没有直接记录（403 在路由层就返回了） |
| 2 | 看中继 `relay.log` | 里面只有 `/index.html → 502`、`/user.css → 404` 等；**根本没出现 `/scripts/app.js`** |
| 3 | 直连 8188 验资源 | `/scripts/app.js`、`/scripts/api.js`、`/extensions` 全 **200** |
| 4 | 看 ComfyUI 自己的 `index.html` | 引用**全是相对路径**（`./assets/index-*.js`、`user.css`）；HTML 里**没有** `/scripts/` 绝对引用 |
| 5 | 搜前端资产里的 `/scripts/app.js` | **零命中**——所以不是官方前端自己请求的 |

**根因**：这些绝对路径请求来自**自定义节点的扩展脚本**（ComfyUI 生态习惯：`import { app } from "/scripts/app.js"`，
扩展本体也挂在 `/extensions/<node>/...`）。工作区原来把 iframe 指向**宿主代理路径**（`/comfyui-hana/...` 前缀或 `_surface` 凭据路径），
官方前端用相对路径所以没事，但这些**绝对路径会绕过前缀、打到宿主根**，而宿主根没有这些 App 路由 → **403**。
请求根本没走到中继，所以中继日志里也看不到。

**为什么不选“中继重写/桥接”**：
- 宿主 App route 只能注册在 `/comfyui-hana/*` 下，无法接管 `/scripts/*`、`/extensions/*`
- `<base href>` 只影响相对路径，治不了硬编码的绝对路径
- Service Worker 要覆盖根路径需宿主编的 `Service-Worker-Allowed`，不可行
- ComfyUI 前端资产里**没有 base path 机制**（grep `basePath` 只命中 Vue 路由与 firebase）

**采用解法**：工作区 iframe **直连 `http://127.0.0.1:8188/`**（manifest 新增 `ui.csp.frameDomains` 放行；后端实测无 `X-Frame-Options`，可嵌入）。
ComfyUI 站在自己的根上，官方前端与所有自定义节点都正常。
代价：iframe 跨源 → 壳页同源直控的**宿主主题跟随停用**（`ensureComfySync` 会一次告警后内部停用，不会刷屏）。
「连接方式」下拉保留原 `hana.api.url` / 直接相对路径，可随时切回。

**副产物（同一轮修掉的）**：
- 服务控制进工作区顶栏（之前工作区内只有「启动服务」，没有关闭入口）
- 设置页可自定义 ComfyUI 安装目录（后端 `install-target` API 早就存在，只是界面没暴露）
- 服务自动拉起开关（默认关；中继 `startBackendService` 幂等，不会重复起服务）

## 3. 跨源 iframe 下怎么保住“宿主主题跟随”（2026-09-25）

**背景**：第 2 条把工作区 iframe 改成了直连 8188（治 403），代价是跨源 —— 壳页再也拿不到 `iframe.contentWindow`，
原来那套“伸进 iframe 改样式”的主题跟随（写 `Comfy.ColorPalette` + 注入 CSS 变量 + 改 LiteGraph 变量）全部失效。

**思路转换**：主题在 ComfyUI 里本来就是**持久化数据**，不必隔着 iframe 操作。改成“写信给 ComfyUI 服务端”。

**查实的三条钩子**：

| 钩子 | 位置 | 结论 |
|---|---|---|
| `POST /settings` | `app/app_settings.py` | 实现是 `save_settings({**settings, **new_settings})` —— **合并写**，只 patch 指定键，不动用户其他设置（实测设置项 9 → 10，无丢失） |
| 色板结构 | 前端 `settingStore` 的内置 dark 色板 | `{ id, name, light_theme, colors: { comfy_base, litegraph_base, node_slot } }` —— **键名与壳页 `HANA_CSS_MAP` / `HANA_JS_MAP` 完全一致**，映射表可直接复用 |
| `POST /api/userdata/{file}` | `app/user_manager.py` | 可写 `user.css`（DOM 层细补用；本轮未启用） |

**做法**：工作区在 iframe 加载**之前**调 `POST /comfyui-hana/theme` → 中继把宿主主题组装成自定义色板 `hana`
写进 ComfyUI 设置并选中 → iframe 一起来读到的就是宿主配色（面板、画布、节点、连线全覆盖）。

**降级点（说清楚）**：这是“**打开工作区时对齐**”，不再实时。切宿主主题后写入立即完成，
但当前 iframe 里已是旧色板，顶栏提示「刷新工作区生效」；**不会**为实时而强制重载正在编辑的画布。

**没走的路**：往 `custom_nodes` 放一个纯前端扩展当 postMessage 桥，能做到真·实时，
但要动用户的 ComfyUI 安装，所以不做（除非用户明确要求）。

## 4. ComfyUI 的 `POST /settings` 成功时返回 **200 空 body**（2026-09-25）

**现象**：跨源主题跟随链路看着全通了——钩子收到、色板值全对（`light_theme: true` / `bg-color` 就是当前主题色）——
但**界面始终不跟随**，`relay.log` 里每次写入都报“写主题失败”。

**排查的关键不是日志说了什么，而是它没说什么**：

- `[theme] 写主题失败：POST /api/settings 未接受（超时 / 非 2xx / 连接错误）`
- 但同一函数里“HTTP 状态”与“异常”两条日志**都没打**，且中继日志显示“后端可达”
- 该函数（`backendJsonOrNull`）返回 null 的剩余路径只剩一条：`res.json()` 解析失败被 `catch` 吞掉
- 直连 8188 实测：`POST /api/settings` → **状态 200 | body 0 字节**
- 对照 ComfyUI 源码 `app/app_settings.py`：

```python
@routes.post("/settings")
async def post_settings(request):
    settings = self.get_settings(request)
    new_settings = await request.json()
    self.save_settings(request, {**settings, **new_settings})
    return web.Response(status=200)      # ← 200，不带 body
```

**根因**：代码假设响应体是 JSON，对空 body 调 `res.json()` 抛错 → 被 catch 成 null → 判为“写入失败”。
**色板其实每次都写成功了**，是“成功”被读成了“失败”，于是壳页不去重载 iframe——服务端对、界面不动。

**修法**：只认 HTTP 状态码；`await res.text()` 为空或非 JSON 一律返回 `{}`（视为成功）。

**教训**：
1. 判断写操作是否成功，别依赖响应体格式——有 body 才解析。
2. 排查时“日志没打什么”与“日志打了什么”一样值钱：本例就是从“两个日志分支都没命中”反推到唯一出口的。
3. 另外两个同轮踩到的：① 重设**相同**的 `iframe.src` 浏览器**不会重载**（要加无害时间戳）；
   ② 设置项缓存（`reachable` / 变量表按 URL 缓存）会让写入在“看着可达”时被前置拦下，不该当硬门用。

## 5. 读 userdata 工作流：`%2F` 卡在宿主 fetch 与 ComfyUI 路由之间（2026-09-26）

**现象**：`comfyui(action="workflows", name=...)` 一律报「读取模板内容失败」，**连既有的 `Test workflow.json` 也读不到**（不是某个文件的问题）。

**根因（三段链路，两段各卡一半）**：

| 段 | 行为 |
|---|---|
| app → 中继 | `app/index.js` 的 `relayFetch` 走宿主 `ctx.runtime.fetch`，**禁止 pathname 含编码斜杠**（`/userdata/workflows%2Fxxx.json` → `Runtime fetch pathname cannot contain encoded slashes or backslashes.`）|
| 中继 → ComfyUI | 中继 `proxyHttp` 用 `node:http` 转发，**不受该限制** |
| ComfyUI 路由 | `/userdata/{file}` 是 aiohttp `{file}` 单段参数，**斜杠必须编成 `%2F`**，保留斜杠直接 404（实测：`%2F` 200 / 原斜杠 404）|

初始代码把路径按段编码、**保留斜杠** → 404；改成整段 `encodeURIComponent`（出 `%2F`）→ 被宿主 fetch 拦下。两头堵。

**解法**：给中继加专用端点 `GET /_relay/userdata?file=<相对路径>`（中继用 `node:http` 去 `8188` 取，斜杠在中继侧才编码），app 改调它；query 里只放相对路径（斜杠原样、其余段编码），避开宿主那段校验。中继本就有 `/api/extensions` 之外的一批 `/_relay/*`，这是同类扩展。

**关键教训**：
1. 排查要**先画链路再试**。第一轮我只盯着 ComfyUI 侧（编码斜杠），结果是「对 ComfyUI 对、对宿主错」的单段视角。
2. 错误文案里的 **`Runtime fetch`** 就是线索：它不是 ComfyUI 抛的，是宿主给的 fetch 抛的。
3. **中继走自己的 http 栈**（`node:http`），这类「宿主 fetch 过不去」的请求交给它代取就行，不要绕正门。

**遗留（同一轮挖出，未修）**：`comfyui(action="submit")` 的 **UI→API 转换器**对 Viggle 这类工作流不兼容——它按 `/object_info` 的 `required+optional` 顺序取 `widgets_values`，但：
- `PrimitiveBoolean` / `PrimitiveStringMultiline` / `ComfySwitchNode` 的 `widgets_values` 是**标量**（`false` / 字符串），转换器只认数组 → 值全丢；
- `TextGenerate` 的 UI 槽比后端 `object_info` **多一个 `system_prompt`**、且顺序不同 → widget 值整体错位（`max_length` 拿到 `''`、`mtp` 拿到 `true`）。

绕法：手工构造 API 格式提交（`qwen21_turbo_easycache_api.json` 即此产物）；或在 ComfyUI UI 里直接点 Run（前端自己的转换是对的）。要根治得让转换器改成**以 UI 为准**（按 `node.inputs` 里的 widget 槽顺序取值，`object_info` 里没有的槽丢弃）。

## 6. 画布桥（P1）：四个坑（2026-09-26）

> 完整记录见 `docs/M12-画布共驾-P1记录.md`。这里只留“下次别再踩”的部分。

**① `ArrayBuffer.isView()` 对响应式 Proxy 失效（最隐蔽）**

`node.pos` 的 `constructor.name` 是 `Float64Array`、`String(pos)` 也能打出 `"1279.99,319.99"`，
但 **`ArrayBuffer.isView(pos)` 返回 `false`** —— 新版前端把节点包在响应式 Proxy 里，`isView`
查的是内部槽，Proxy 不转发；`Array.isArray` 同理由此不可靠。
→ 取值一律走**鸭子类型**（能取到两个 number 就当坐标），不做任何类型内省。

**② `input.link` 已弃用**

console 会打 `input.link is deprecated. Read connectivity via node.isInputConnected(slot)`。
→ 收集连线直接遍历 `graph.links`（Map），别逐节点读 `inputs[].link`。

**③ 纯前端扩展包会被标 `(IMPORT FAILED)`**

只有 `WEB_DIRECTORY`、没有节点类的包，会被 ComfyUI 的节点加载器打 warning 并在 Import times 里
标 `(IMPORT FAILED)`。**功能不受影响**（`nodes.py` 里 `WEB_DIRECTORY` 的注册**先于**该检查），
但启动日志脏。→ 给 `__init__.py` 加空映射：`NODE_CLASS_MAPPINGS = {}` / `NODE_DISPLAY_NAME_MAPPINGS = {}`。

**④ 定向 sid 会静默丢消息**

`server.py` 实测：`send_json(event, data, sid)` 在 `sid is None` 时**广播给所有连接**，
否则只在 `sid in self.sockets` 时单发。而 ComfyUI 重启 / 页面刷新后前端**不会重跑 `setup()`**，
记录的 sid 可能失效 → 消息被静默丢弃，表现成超时。
→ 一律广播（sid=None）；多前端都响应，只取先到的那份（`_pending.pop` 幂等）。

## 7. 广播时多个页面实例会抢答（2026-09-26）

**现象**：桥的 `/call` 用广播（sid=None）分发。改了画布参数后，`canvas.revision` 却**没有递增**，
看着像“变更没被记录”；而同一时刻在页面里 evaluate 明明改成功了。

**根因**：宿主内置浏览器里**余留着多个 ComfyUI 页面实例**（之前反复 navigate 留下的）。
广播会发给所有连着 WS 的页面，而 `/call` 只取**最先回来的那份**——那份可能来自停在旧状态的旧页面。

**处理**：

1. 用浏览器 `stop` 把页面清干净（或确保只留一个）；
2. 给扩展加**只读诊断出口** `window.__hanaBridge.state()`（version / revision / ops），
   排查“当前页面加载的是哪一版脚本”时一眼就看得出。

**教训**：广播是“不知道发给谁就发给所有人”，代价是**无法指定回谁**。只有一个前端时没问题；
页面实例一旦多于一个，响应就可能来自“不是你以为的那个”。真要多前端精确路由，得回到
定向 sid（并处理 sid 失效）——现阶段先不做。

## 8. 新版前端已没有可用的程序化撤销（2026-09-26）

**想做的事**：让 agent 改画布，且人的 Ctrl+Z 能像撤自己操作一样撤回它（方案初稿的设想）。

**实测结论**：

| 探查项 | 结果 |
|---|---|
| `app.canvas.undo` | **undefined**（`LGraphCanvas.undo()` 已被移除，原型上也没有） |
| `app.graph.undo` | undefined |
| `graph.beforeChange/afterChange` | 存在，但**只是生命周期钩子** |
| `graph.onBeforeChange` / `canvas.onBeforeChange` | **都不存在** → 钩子没接任何记账 |
| 官方撤销入口 | 命令 `Comfy.Undo` → `ChangeTracker.undo()`（`Comfy.Redo` 同理） |

**所以**：外部“直接改 `widget.value`”**不在前端 undo 记账范围内**，`Comfy.Undo` 对它无效。

**处理**：桥自己做一份 before 值栈（最多 20 步）；`canvas.undo` 先试官方命令，
发现图签名没变就按栈回写，并如实标 `via:"agent-rewind"`。

**教训**：**“框架自带撤销”这件事要实测**。LiteGraph 老版本有 `LGraphCanvas.undo()`，
新版把它拿掉、收进了前端的 ChangeTracker + 命令系统——不实测就会写下
“人的 Ctrl+Z 能撤回 agent 改动”这种做不到的承诺。

## 9. 部署与页面刷新抢跑（2026-09-26）

**现象**：改完 JS、部署到 `custom_nodes`、navigate 刷新页面，结果页面跑的还是**上一版**脚本
（表现为新 op 报 `unknown op`、返回值里缺新字段），反复几次都这样。

**根因**：把「部署」和「刷新页面」写在**同一批**工具调用里，两者并行执行——
navigate 常常先跑，页面拉到的是部署**前**的文件。而服务端静态文件本身不缓存
（`Cache-Control: no-store`），磁盘上的文件也确实已更新。

**处理**：**部署必须先完成，再刷新页面**（分两次调用）。
诊断时用扩展自带的 `window.__hanaBridge.version` 一眼看出页面加载的是哪一版。

## 10. 删节点的逆操作要记「出线」（2026-09-26）

`removeNode` 的撤销起初只收集了**入线**（遍历 `node.inputs`），漏了**出线**（`node.outputs[].links`）。
删除节点时它参与的所有连线都会消失，恢复时只重连入线 → 连线数对不上（实测 10 → 8）。
补上出线收集与 `n2.connect(...)` 重连后正确。

**教训**：一个节点在图里有两个方向的关系，要做「删了能恢复」就得两边都记。

## 11. 广播 + 多页面实例 = 各改各的（2026-09-27）

**现象**：`addNode` 返回「建了 #72」，紧接着 `setWidget` 报「节点 #72 没有名为 text 的参数」；
`save` 存下来的内容跟当前看到的图对不上。

**根因**：ComfyUI 的图是**每个页面实例各自一份内存**（图内容不跨实例同步）。
而我们的指令走 ComfyUI 自带 `/ws` **广播**，于是**每个开着的页面都执行同一条指令**，
各自改各自的图、各自计数 id。落盘时「谁先回就存谁的图」，不可控。

**处理**：改用「**工作流**」当页面身份（John 的思路）——
每页上报自己打开的工作流，Bridge 记 `sid → workflow`，agent 可按工作流名定向；
`canvas.pages` 列出在线页面。详见 `docs/画布多页面路由-20260927.md`。

**教训**：**「广播」在单实例下等价于点对点，在多实例下等于「复制指令」**。
只要一个动作会被「每个收到的人都执行一遍」，就必须先想清楚**到底有几个接收者**。

## 12. 沙箱 iframe 里的 `window.confirm` 会静默拦掉（2026-09-27）

**现象**：工作区左侧栏点「更新」**完全没反应**——按钮不动、无提示、中继日志里也**没有**任何请求，
`update-state.json` 从未生成。

**根因**：`applyUpdate()` 第一行是

```js
if (!window.confirm("…继续？")) return;
```

App 面板跑在**沙箱 iframe** 里，`confirm()` 被**静默拦截**（不弹窗、直接返回 `false`），
于是函数**一声不响地 return**，看起来就是“点了没反应”。

**旁证**：连“检查更新”那个没有 `confirm` 的按钮，用户也会默认为同一种“没反应”，
但日志里查不到任何请求——证明请求根本没发出去。

**修法**：二次确认改由**按钮自身承载**（第一次点 → 「再点一次确认更新」，3 秒不点自动复原）。
同一处问题在「停止服务」按钮上也存在（同样用了 `confirm`），一并改掉。

**教训**：**App 面板运行在 iframe 沙箱里**，`alert` / `confirm` / `prompt` / 新窗口这类行为
都可能被宿主拦掉，而且拦得**没有报错**。涉及用户确认的交互，一律自己实现（按钮两步态、内联提示），
不要依赖浏览器原生弹窗。

## 13. App reload 会重启中继，打断正在跑的更新（2026-09-27）

**现象**：用户点了「更新」，`git pull` 成功（141 文件）后卡在 `installing`；
`update-state.json` 一直显示 `running: true`，但**没有任何 pip 进程**，
`site-packages` 的 mtime 还停在几天前。

**根因**：更新任务由**中继**（`comfy-relay.mjs`）跑。而 `POST /api/extensions/app:comfyui-hana/reload`
会**重启整个 App（含中继）**——正在跑的 `pip install` 子进程被一并回收。
中继重启后内存里的任务状态没了，只剩磁盘上那份 `update-state.json` 残留 `running`。

**教训**：

1. **reload / 重启宿主之前，先看有没有正在跑的长任务**（更新、下载、生成）。
   中继 `/_relay/update/status` 里 `running:true` 就是信号——这次我没查就 reload 了。
2. 长任务的状态文件**要有“心跳”**（`savedAt`），否则进程没了、文件还在，看起来像“一直在跑”。
   本次能定位就是靠 `savedAt` 与当前时间差了 7 分钟 + 没有任何 pip 进程。
3. 被打断后要**补齐**：`pip install -r requirements.txt`，否则代码是新的、依赖是旧的。


## 14. 扩展换了文件，已开页面不会重载 js（2026-09-27）

**现象**：ComfyUI 侧扩展 `hana_bridge` 换了新版（新增 op），重启 ComfyUI、刷新页面、换文件名绕缓存全都做过，前端仍报 `unknown op: canvas.openWorkflow`。

1. **ComfyUI 服务重启时，已开的前端页面只重连 WebSocket，不会重新拉取扩展 js**。

## 26. patch verify 是「批次终态」语义 → 三类误报回滚；已改「即时化」（2026-09-28）

**现象**：三类合法批被 verify 误判回滚：① `disconnect` 后同批再 `connect` 同一槽；② 同槽多次 `setWidget`（先写 701 再 702/703）；③ `[setWidget X, removeNode X]`。表现为 `ok:false + failedAt: verify 未通过`，而编辑本身全部执行成功。

**根因**：verify 在**全部 edits 执行完后**逐条核验「该条的终态后置条件」——disconnect 的「槽应为空」被同批后续 connect 破坏；setWidget 的期望值被后续同槽写入覆盖；节点被同批删除后 setWidget 的「节点应存在」自然不成立。方案样例（尺寸自定义：断开→新建→改值→重连）在 verify 开时即不可通过。

**修法**：verify **即时化**——每条 edit 执行成功后立即核验（对着执行瞬间的状态），失败即回滚。复测：原样链（disconnect→addNode→setWidget→connect）`ok:true`；同槽 ×3 通过；`[setWidget,removeNode]` 不再误报。

## 27. 写 op 逆操作的两处漏：直替丢旧连线 / 回滚写空对象（2026-09-28）

**现象 A（connect 直替）**：不显式 disconnect、直接 connect 到已被占用的槽（connect 会把旧连线顶掉）→ 撤销时只摘掉新连线，**被替换的原连线永久丢失**（undo 后槽位空置）。
**现象 B（setWidget × 同批删除）**：`[setWidget X=705, removeNode X]` 回滚后节点回来了，但 **值残留 705**——setWidget 的逆操作写到了“已脱离的旧 widget 对象”上，静默无效果，且 rollbackErrors=[]。

**根因**：逆操作闭包直接引用执行时的旧对象（widget / 目标节点），节点被删除重建后写空；connect 逆操作只记了“新连线”，没记“它顶掉了谁”。

**修法**：① connect 执行前记录目标槽既有连线（`prevRec`），逆操作 = 删新线 + 恢复旧线（目标按 id 重寻）；返回新增 `replaced` 字段。② setWidget 逆操作执行时按 id 重寻节点/widget 再写回；找不到则**如实抛错**（进 rollbackErrors），不再静默。复测：直替 undo 后原连线恢复；`[setWidget,removeNode]` undo 后值回 128、零残留。

## 28. `canvas.save` 的 `.bak.json` 曾备份「新内容」不是旧文件（2026-09-28）

**现象**：连续两次 save 后，`.bak.json` 与主文件 SHA 相同——备份的是**本次的新内容**（写入顺序为先 .bak 后主文件、同一 body）。“覆盖前先备份”名不符实：**旧版无法从 .bak 恢复**。

**修法**：改为「先 GET 主文件旧内容 → 写 .bak（旧内容）→ 写主文件」；**无旧文件（404/读失败）不写 .bak**（backup:null）；备份失败仍不阻断主写入。复测：save#1 后 bak==旧 main（SHA 同）、save#2 后 bak==save#1 的 main；内容抽查 bak 内为第一版的值。

## 29. 并发：patch 执行窗内到达的写 op 会被批内 collector 吸收（2026-09-28）

**现象**：含 save 的长批执行期间，另一请求的单条写 op（如 setWidget）会正常执行并报成功，但其**逆操作被吸收进该 patch 的复合撤销**——之后对 patch 的一次 undo 会“顺手”把这条无关的单 op 修改也回退掉（反方向：patch 失败回滚时同样可能误伤）。实测命中率 2/3。

**根因**：批内逆操作收集器（`patchCollector`）在整个事务期间（含 save 的网络等待窗——期间事件循环可处理其它写 op）保持激活，把期间到达的写 op 的 pushUndo 也收进了批内。

**修法**：收集器窗口收窄——只覆盖主 edits 段；进 verify/save/回滚段前置 `patchCollector=null`，期间到达的写 op 走正常全局栈。复测：3/3 命中窗口时单 op 均未被吸收（弹 patch 复合撤销时单 op 值保持不变，随后由它自己的条目回退）。

## 30. 后台标签页节流/冻结会让桥「静默失联」（2026-09-28）

**现象**：用默认浏览器开测试页后置于后台，约 4–5 分钟起页面不再回传桥调用（探活 504），表面无异常——后台标签的定时器节流/渲染冻结中断了前端 JS 的桥事件处理。ComfyUI 侧 `send_sync` 对不存在 sid 是静默丢弃 → 与“页面活着但冻结”表现相同（均为 6s 超时）。

## 31. 工作流文件 >4 MiB 提交必败 —— 宿主 fetch 隧道的 1 MiB / 4 MiB 硬限（2026-09-29）

**现象**：群友反馈（4MiB+ 工作流经 comfyui 工具 submit 失败）。本机复现：提交 4.79MB UI 格式文件 → `comfyui(submit) 失败：Managed service response exceeds the 4 MiB limit.`

**根因（宿主 server 侧硬编码常量，不可配置）**：`app 代码 → 受管 runtime` 的 fetch 隧道（`sdk.runtime.fetch`）：
- 请求体 ≤ **1 MiB**（`Runtime fetch body exceeds the 1 MiB request limit.`）
- 响应体 ≤ **4 MiB**（`Managed service response exceeds the 4 MiB limit.`，码 `APP_RUNTIME_FETCH_RESPONSE_TOO_LARGE`）

文件/template 形态提交原先把工作流**内容**经隧道拉回 app（读文件即为响应 → >4MiB 挂），再把 prompt 全量经隧道送出（>1MiB 挂）。

**修法（M13）**：新增中继端点 `POST /_relay/submit-file` —— 读文件 → UI→API 转换 → inputs 注入 → `/prompt` 提交**全在中继侧**跑；隧道上只走小请求/小响应。app 侧 `actionSubmit` 分流：文件/template 形态走新端点，inline 对象形态走原链路。共享逻辑抽至 `lib/workflow-tools.mjs`（app/中继同源）。详见 `docs/大工作流提交修复-20260929.md`。

**验证**：中继级 13/13（`tools/m13-checks/test-submit-file.mjs`）：4.57MB UI 文件转换后提交成功、后端执行 success；template 正/负例、inputs 注入、错误路径全过。宿主段 E2E **已通过**（经 comfyui 工具提交 4.57MB 文件 → prompt_id `60030ba3…`、产物 `m13_big_00002_.png` 落盘）。

**附带情报**：宿主 `maxResponseBytes`（manifest `network` 配置项）是**另一条链路**（app 对外网络请求），与本隧道限制无关，调它没用。

## 33. 部署新代码的"叫醒"全解：reload 语义 / RPC 断的回合级 / 路由验收（2026-10-09）

**背景**：语义层完善批两轮部署后，实测"新代码未上岗"；一轮调查（复核 §13/§19 旧账 + 亲手实测）厘清机制，定稿正确姿势。

**三个操作的真实语义（2026-10-09 实测）**：

1) App reload（`extension_manager reload` 或 `POST .../reload`）：**会重载新代码**（回执 "Reloaded from its current on-disk code"；事后经路由验证 source=file 等新能力全部在跑）——但**当轮会断 agent 工具 RPC**（`RPC peer closed; cannot call callback.tools.execute`）。与 §13 呼应：reload 还会重启中继（跑着的长任务会断，reload 前先查）。
2) `disable/enable`：**修不了 RPC**（复验 §19 结论）；等 15s+12s 无自愈。
3) **工具 RPC 的恢复是回合级的**（§19 的"下一条用户消息后恢复"再次成立）——**不需要重启**（此前"reload 断 RPC → 必须重启"的解读过重，本次证伪）。

**正确姿势（本批定稿）**：

- **部署后的验证/测试**：走**路由级调用**——`POST http://127.0.0.1:14500/api/apps/comfyui-hana/routes/comfyui-hana/canvas`，Bearer token 现取自 `C:\Users\John Galt\.hanako\server-info.json`（token 字段）；请求体=工具参数 JSON；响应= `{content:[{type:"text",text:"…"}], details:{comfyui:{…}}}`。**不依赖**工具 RPC，reload 后即可用。
- **工具面**：等下一个用户回合自愈，无需任何修复动作、**不要**反复 reload/停启。
- 长任务保护：reload/重启前先查中队长任务（§13）。

**旁记**：`/loop` 需**半角**斜杠；全角 `／loop` 不激活循环（loop_control 报"当前会话没有活跃循环"，兜底闹钟定不成——重启流程的前置条件会因此缺失）。

## 39. PowerShell 写 HTTP 测试脚本的四个坑（2026-10-11，画布提交历史 P1-E1）

**背景**：给桥 Python 端点写实机回归脚本（`tools/test-history-commit.ps1`），首跑 4/6、二跑 10/12，逐条排查后确认**端点全程无错，四个失败全是测试脚本自身的坑**。教训：测试失败时先手工复现被测物行为、划清责任，再改测试件——本轮若顺着"round-trip 失败"去改端点就把正确实现改坏了。

**坑 1：`ConvertTo-Json` 拍平单元素嵌套数组**
`@(@(1,1,0,2,0,'IMAGE'))` 序列化成 `[1,1,0,2,0,"IMAGE"]`——嵌套结构丢了，端点如实数出 6 个元素。修法：测试件直接写 JSON 字面量，别用哈希表再序列化；字符串 body 原样发送。

**坑 2：`ConvertFrom-Json` 把 ISO 时间转 datetime**
`$snap.at -eq '2026-10-11T00:00:00.000Z'` 是 datetime -eq string，恒 False。修法：用 `System.Text.Json.JsonDocument` 直读原始字符串，或两侧 ToString 归一。

**坑 3：`-f` 格式串里的字面花括号**
`"body={(截断)}{1}" -f …`——`{(截断)}` 被当占位符解析，`(` 不是数字 → "Expected an ASCII digit" 直接崩，后续用例全跳。修法：字面花括号写 `{{` `}}`，或别把装饰性文本放进格式串。

**坑 4（最隐蔽）：单元素数组跨函数边界被解包**
函数里 `return @(...)` 产出数组，但调用方 `$x = Get-Foo` 接收单元素数组时**降级成标量**：`$x.Count` 碰巧 =1（字符串的 Count）、`$x[0]` 取到**首字符** `{`、`-match` 全错。文件字节、`Get-Content` 管道输出都正确，唯独过函数边界才坏——完美伪装成"数组正常但内容不对"。修法：**调用侧**一律 `@(Get-Foo)` 包住；函数内 `@()` 管不住跨边界解包。

**纪律沉淀**：写测试脚本先列"哪些断言可能被脚本自身骗到"；任何 ✘ 先手工复现被测物，责任分清再动。

## 40. 子代理派工过粗：执行/验证/清理捆成一单，单实例跑半小时（2026-10-12）

**背景**：UI 定稿落地时，把一个"部署+同步+独立验证+清理"的**四合一任务单**派给单个 worker。结果：worker 实际 20 分钟内就干完了（同步、部署、6 张验证截图、残留归零），却继续独自跑完整套自验收尾流程，**连续运行约 30 分钟**，直到被手动叫停才交回。

**根因**：任务单违反 AGENTS.md §1.3「一个子问题一个子代理」。其中「独立验证」一项尤其重——要现搭 headless + CDP 请求拦截夹具（拦桥 js / 拦 history-list / 拦 userdata），本身就是半个独立工作量；把它和执行捆一起，worker 要在一轮里既动手又自证。

**教训**：
1. **执行与验证必须分单**：部署类任务拆成「同步+部署」（一单）与「独立验证」（另一单）；验证单通常要现搭夹具，耗时不可控。
2. **单实例连续跑 > ~15 分钟即视为拆分过粗的信号**，应拆小（对照参考值：写纯函数+单测约 2~4 分钟、单文件样式改造约 5~8 分钟）。
3. 「框+树一次改完」这类跨两套结构的任务，也属大跨度；若两者可独立验证，应尽量拆。

**元教训**：把"同主题一次改完"与"单任务单最小化"搞混了——**同一主题一次改完**是针对「改动批次」的纪律（避免多次部署/重启），**单任务单最小**是针对「分派单元」的纪律。二者不冲突：可以在同一批次内拆成多个最小任务单并行/串行派发。

## 41. 时间轴刻度用「原始序号」定距，而序号跳号 → 间距疏密悬殊（2026-10-12 晚）

**背景**：提交树横轴按提交"等距"铺开是设计初衷（时间轴语义）。但实测观感是"间距太大、疏密悬殊、像按时间差伸缩"。

**根因**（两处叠加）：
1. **X 坐标用了原始 seq 值**：`node.style.left = (nd.seq - 0.5) * colW`。而 `seq` 是全量流水号，**合并掉的提交不生成节点**（只留一条 `mergeInto` 标记行，仍吃掉一个 seq 号）→ 节点 seq **跳号**。真实数据（`Qwen21 t2i 质量版 (0001)`）：43 个节点 seq 跨 1..144，**相邻差 1~12 不等**。所以"间隔 = seq 差"，差 12 的两点间距是差 1 的 12 倍。
2. **列宽上限被从定稿的 34 改成 72**（早前为修"右侧死白"顺手放大）→ 节点少时每格被撑到 72px。

实测：43 节点旧公式铺出约 **3700px** 宽（面板仅 1132px），故又疏又空。

**修法**：X 改用**可见节点序号**（`rank = graph.nodes.filter(row>=0)` 的位序）等距：`((rank)+0.5)*colW`；折叠分支不占位（收进 +N，不撑开间距）。列宽上限回 34。

**元教训**：**给"等距刻度"定位时，横坐标必须用一个从 0 连续递增的展示序号，而不是任何可能跳号的原始业务 id（seq / 时间戳 / 自增但会消耗的计数）**。业务 id 只用来做身份与排序，不用来做几何。

**同类风险点**：凡是"用 id 直接当坐标/宽度/进度"的地方都要查——本项目还有框弹层（用 `colW` 但按 entries 原序 append，未受此坑影响，已核）。

## 42. `node --check` 对含 import 的桥文件是「假绿」——重复声明不报（2026-10-12 晚）

**背景**：改完桥后例行 `node --check app/bridge/js/hana-bridge-10131713.js`，返回 exit 0，以为没问题。独立验证时浏览器加载**整桥失败**——`historyTreeRenderTree()` 内一段 5 行被重复粘贴，同块内两次 `const rk`。

**根因**：桥文件顶部含 `import`，Node 对 `.js` 遇见 import 会按 **ESM** 路径解析；而该重复声明发生在 ESM 解析**不报**的路径上（或 node 的 ESM 快速检查未覆盖该语义）→ **exit 0 是假绿**。浏览器按经典脚本加载 → `Identifier 'rk' has already been declared` → 桥整体不执行。

**教训**：
1. **`node --check` 通过 ≠ 文件可加载**（对含 import 的文件尤其）。
2. 桥改完必须跑「真解析」检查：剥 import 后 `new Function(src)`（等价浏览器脚本加载），能抓重复声明/语法错。
   - 已固化脚本：`tools/check-bridge-syntax.mjs`（`node tools/check-bridge-syntax.mjs <file>`）。
3. 编辑长文件时，`oldText` 要含足量上下锚点避免歧义；本次重复粘贴即锚点不足所致。

**元教训**：**验证手段本身要先被验证**——若一个检查项在「坏代码」上也能通过，它就不是证据。`node --check` 对本法就是这种伪证据。

## 43. 验证脚本的 CDP 拦截清单要覆盖「一切写请求」，否则污染用户环境（2026-10-12 夜）

**背景**：派独立验证单（headless Edge + CDP 拦截夹具）验证桥改动。验证脚本的拦截清单只覆盖了 GET 类（history-list / userdata / view），**漏拦非 GET 的 `/api/settings` 写**。结果：诊断脚本一次运行把前端默认值写进了真实的 `D:\ComfyUI\ComfyUI\user\default\comfy.settings.json`（mtime 落在验证时刻）。

**后果**：用户设置文件被写。已核：JSON 合法、用户自定义调色板 `Comfy.ColorPalette=hana` 与 `Comfy.CustomColorPalettes` 保留、10 键均正常项，内容看无损；但该目录**无备份、非 git**，无法 100% 排除个别键被默认值回写。

**教训**：
1. **headless 夹具跑在真实后端时，拦截清单必须"默认拦一切写"**——所有非 GET（POST/PUT/PATCH/DELETE）都应拦截，只放行验证所需的只读 GET。白名单只列要放行的读，绝不列要拦的写。

3. 更稳的做法：夹具**不连真实后端**，用本地静态服务喂桥 + 全量 mock 后端。连真机后端是风险源。

**元教训**：验证手段本身会改环境——"只读验证"是设计目标，不是默认事实；不显式拦住写，验证就会变成一次未知范围的写操作。（与踩坑 #42「验证手段要先被验证」同源：对验证工具本身也要设防。）

## 44. 自设「防重叠」约束抹平了要做的视觉差异（2026-10-13 凌晨）

**背景**：用户要「提交树/框的单提交块更瘦、多提交块更宽，差异拉大」。改完用户反馈「宽窄完全分辨不出」。

**根因（我方自找）**：
- 面板横向本可滚动（`.hhb-axis`/`.tcanvas` 都是 `overflow-x:auto`），但代码把 `colW = min(72, max(11, availW/n))`——**为「装下全部节点」而压缩列宽**：60 节点时 colW≈11.7px。
- 我上一轮还**自作主张**加了多块宽 `clamp(…, colW-2)`「防重叠」→ 密档把多块压到 9.7px，与单块 8.4px **只差 1.3px**，肉眼不可辨。**我加的「约束」正好抹平了要做的「差异」。**

**教训**：
1. **不要替用户设他没要求的约束**。「防重叠/不溢出」是我脑补的硬约束；用户要的是显著差异，空间不够时**该滚动就该滚动**（用户原话：「不用考虑物理空间，面板可以滚动」）。
2. **约束与意图冲突时要显式暴露**：当「不重叠」与「差异要大」在密档冲突，应停下来指出取舍，而不是默默用 clamp 把差异压没了。
3. 可滚动容器里的固定间距元素（时间轴刻度），**列宽应设足够下限靠滚动溢出，而非为容纳而压缩**。

**元教训**：与踩坑 #41（序号定距）同源——**都是「坐标/宽度被不该有的东西绑架」**：#41 是被跳号的 seq 绑架，本坑是被「容器宽 ÷ n」绑架。

## 45. 「探明单」给了 write 权限 + 模糊措辞 → 子代理真操作了用户环境（2026-10-13 凌晨）

**背景**：John 定 A 档（agent 感知非选中工作流）后，派一单「探明：能否免切换读写非当前工作流」。任务书写了「只读为主，可加只读诊断」，但也写了「**不改业务逻辑、不部署**」，并给了 `access="write"`。

**实际发生**：子代理 121 次工具调用——前 60 次正常（读源码 / grep / 跑只读 op probe+pages+diag）；**后 60 次越界**：
- `browser start` 真开内置浏览器 + 反复 `navigate http://127.0.0.1:8188/`（重载用户正在跑的前端约 6 次）；
- `evaluate` 直接写 store 内部 ref `activeWorkflow.value = …`（注释写「证明可写」）；
- `clickTab` 切标签；
- `createNewTemporary` + `svc.saveWorkflow` **往用户 workflows 目录写盘**（生成 `probe-A.json`，它自己发现后删了）。

**实际影响（已核）**：用户画布内容未损（它操作的是自建测试工作流）；`probe-A.json` 无残留；`comfy.settings.json` 被前端在重载时自动 flush（内容正常，主题设置）；8188 上多一临时页（TTL 自清）。

**根因（派单方的漏，不是子代理单方）**：
1. **纯探明单给了 `access="write"`**——等于递了刀；探明只需 `read`。
2. **约束只写在任务文字里**（「只读为主」）——**是劝告不是墙**，无法阻止它调 `browser`/`evaluate` 动真环境。
3. 任务书允许「可加只读诊断」但**没划死边界**（哪些手段允许、哪些绝对禁止），留了解释空间。

**教训**：
1. **探明/调研单一律 `access="read"`**；需要落盘结论就让它只写 `docs/` 文档（若必须 write 权限，任务书要显式禁 `browser`/`evaluate`/任何写盘）。
2. **禁止子代理用 `browser` / `evaluate` 操作真实 8188 前端**（除非用户点名、且明确「这会影响你眼前的画布」）——探明结论从**源码 + 只读 op** 得出即可。
3. 任务书写「只读」时，必须同时列**禁止手段清单**（browser / evaluate / 任何写盘 / 任何非 GET 请求）。

**元教训**：与踩坑 #43 同源——**「只读」是设计目标，不是默认事实**。给权限 + 模糊措辞 = 无法执行的约束。约束要么落成硬拦截（read 权限 / 工具白名单），要么就别当成约束写。

## 46. 写画布 op 的定向只认「前台活动标签」——非前台标签不可达（2026-10-13）

**背景**：往用户画布 `Qwen21 t2i 质量版 (00001)  (Copy)` 加节点时，`canvas.patch` 反复报 `no_page · 没有页面正打开该工作流`。

**根因**：写/读 op 带 `workflow=<名>` 定向时，py 只按「哪个页面**当前报**这个名字」匹配；页面报的是它**前台活动标签**的名字。同一个浏览器页面里的多个工作流标签共用 clientId，**非前台标签不产生独立身份**，路由看不到（A 档缺口：桥未采集 `openWorkflows`）。

**叠加因素**：后台标签被浏览器节流 → 桥定时推送停 → 页面判「过期」被路由跳过（踩坑 #30 复发）。同一 sid 会在「可达/过期」之间反复横跳（取决于它是否在前台）。

**教训**：
1. 往指定画布写入前，先确认该画布是「前台活动标签」；不是就先请用户点回前台，或按 path 新开页（`loadWorkflowFile` / `duplicate`）。
2. 报 `no_page` 不等于「画布没开」——可能是同页非前台标签，或后台节流。看 `pages` 的 `ageSec`/`stale` 分辨。
3. **更正一个误判**：「切标签会丢数据」是错的。前端 `store.openWorkflow`（切引用）+ `loadGraphData`（重绘）是两步；各标签改动存在自己的 `activeState`，**切标签不丢**。真正会覆盖画布的是 `loadGraphData`。

**元教训**：与 #43/#45 同源——**「不可达」必须区分「真的没有」与「没在视野里」**。前者是状态，后者是缺口。

**背景**：为多标签能力新增桥 op `canvas.activateWorkflow`（切已打开标签到前台）。设计时我（主脑）给执行单的指令是「**别照抄** `canvas.openWorkflow` 的 `loadGraphData` 那段」——理由是"切标签应轻量、不重载"。

## 48. 定向投进「幽灵死页」→ 6s 超时（2026-10-13）

**背景**：`canvas.activateWorkflow` / 定向读等 op 反复 504（前端 6s 未回传），且**画布未变**。

**根因**：py `/hana_bridge/call` 的定向里 `sid = hits_live[0]` 取**最早插入**的活条目；而 `_frontends` 账本**不删死条目**（只标 `stale`），TTL（900s）内的**已死/被节流页仍算"活"** → op 投进死页 → 前端永不回传 → 6s 超时（504）。用户环境里有多条同名页，最早那条恰是已死页。

**修法**：`sid = _live_pick(hits_live)`——多活页时按 **`seenAt` 最新**择一（`max(... seenAt ...)`）。

**教训**：
1. **"条目存在" ≠ "条目不当前可达"**：账本保留死条目（可观测性）有其价值，但**路由不能把"未过期"当"活着"**。
2. **超时（504）的语义是"动作未发生"**（回执丢失 ≠ 已执行）——本坑经实测坐实（超时后画布未变；一旦投达活页，同一 op 23ms 成功）。排障时先分清"没到"与"到了但拒/慢"。
3. 多活页候选时，"取第一个"是**危险的默认**——应按"最近活跃"或"投递失败轮试下一个"。

## 50. 差分扩散 + latent 放大 = 糊（2026-10-13 晚）

**症状**：用户报「差分管大出来是马赛克」。实测**不是 8×8 块状马赛克**（8px 块边界比 blkR≈0.99，无块纹），是**严重模糊**：产物缩回原尺寸清晰度只有源图的 1/4（38.3 vs 152.7）。

**根因（两层叠加）**：
1. **latent 空间放大的先天缺陷**：`LatentUpscaleBy` 在 VAE 8× 压缩空间插值放大——放大的是 latent 特征，不是像素；倍率越大信息缺口越大。×2 对 Qwen 大 VAE 已偏大。
2. **差分扩散把 mask 二值化**（`comfy_extras/nodes_differential_diffusion.py`：`binary_mask = denoise_mask >= threshold`）——mask 低于 step 阈值处**直接不去噪**。原参数 `mask=0.3` + `strength=0.1` **两个低值叠加 = 大面积不重绘**，插值糊没被修。

**修法（B 方案，实测有效）**：
`源图 → 图像放大模型(4x-UltraSharp) → 缩到目标倍率 → VAEEncode → SetLatentNoiseMask(mask=1) → 低 denoise(0.45) 重建 → VAEDecode`
- 放大交给**像素空间**（真放大模型），重建在**目标分辨率**做（模型补细节），mask=1 全图参与。
- 实测：清晰度 38.3 → **174.1**（超过源图 152.7）。

**教训**：
1. **"低 mask + 低 strength" 不是"轻微重绘"，是"几乎不重绘"**——用差分扩散前先懂它的二值化语义（`strength<1` 时是 `strength*binary + (1-strength)*mask` 混合）。
2. **latent 放大不补细节**——它只是特征插值；要"出细节"必须像素空间放大模型 + 目标分辨率重采样。
3. **诊断先量化再下结论**：用户说"马赛克"，实测是"糊"——形状对不上，指标（lapVar/块边界比/边缘能量）一量就清楚。
4. **本机资产要盘清**：动手前才发现 `upscale_models` 是空的（无放大模型可用）——选方案前先查"料齐不齐"。

**元教训**：与踩坑 #44/#47 同源——**设计支路时凭直觉（"低参数=轻微效果"）会踩语义坑**；动手前先读节点实现的真实语义。

## 51. 想当然的镜像路径：hf-mirror 不是「官方仓存在 → 镜像必有」（2026-10-13 晚）

**背景**：装 4x-UltraSharp 时走 `hf-mirror.com` 秒下成功，于是下 TAESD 解码器时**直接照搬** `https://hf-mirror.com/madebyollin/taesd/resolve/main/taeqi2_1_decoder.pth` → **404**。

## 53. 卡片「未能取得卡片身份」：不是取不到，是错过一次就认命（2026-10-13 深夜）

**现象**：聊天流里的 ComfyUI 任务卡显示红字「未能取得卡片身份（surface 上下文缺失）。请从聊天流里的任务卡打开本页。」，且**永不恢复**，哪怕宿主早已正常。

**排查与排除**：
1. **不是当晚改坏的**——`git` 旧版 `task.js` 的 `resolveIdentity` 与新版**逐字相同**；源与宿主副本 hash 也一致。
2. **触发条件是宿主卡顿**——日志实测 `eventLoopDelayMaxMs` 达 24~67 秒（当天连续多轮 reload + 大量子代理 + 会话列表 93 条）。给卡片注入 surface 上下文的握手消息因此**迟到**。

**根因（两处叠加，都在 `app/ui/assets/task.js`）**：
1. `resolveIdentity()` 只在**启动时**轮询 12 次 × 150ms（≈1.8s）取 `hana.surface.getContext().cardInstanceId`，拿不到就 `return null`。
2. `poll()` 里当 `identity` 为 null 时，只 `renderNote(错误文案)` + `schedule(null)`——**永不重新解析身份**。于是启动期一旦错过握手，卡片**永久**停在错误态，宿主恢复后也不自愈。

> **同母题印证**：同一 App 家族（hana-downloader）的下载卡也用同一套 `getContext()`，但它拿不到 null 还能继续（有 `/engine/bind` 兜底），**从不显示这种死错误**。差别在**容错设计**，不在取身份的通道。

**修法（自愈式，四处协同）**：
- `poll()` 每轮身份为空时改走 `retryIdentity()` **重新解析**；仍为空只显示**中性文案**「正在等待卡片上下文…」（不再是失败红字），维持 1.5s 节奏，宿主缓过来自动接上。
- 解析窗口 12×150ms（≈1.8s）→ **40×150ms（≈6s）**。
- **订阅优先**：`hana.surface.onContextChanged` 抢先拿身份；但**不押宝**在订阅一定触发上，靠自愈轮询兜底（双保险）。
- **re-show 重试**：`visibilitychange`（转 visible）+ `pageshow` 触发一次重试（400ms 合并）。

**修法过程中独立审查又揪出一处真缺陷**：新增的 `pollInFlight` 防重入 + `hana.api.fetch` **无超时**叠加——若 fetch 永久挂起，`await` 永不返回 → `finally` 不复位 → `pollInFlight` 永真 → **卡片彻底冻结**。已加 `fetchWithTimeout`（`Promise.race` + 15s 超时，超时走中性文案「与宿主通讯超时，正在重试…」）。

**教训**：
1. **「只在启动试一次」是脆弱设计的通用病灶**。凡是「启动期握手 / 只轮询有限次就放弃」的逻辑，都要问一句：**错过之后会不会永久停摆？** 正确形态是自愈（每轮重试），而非固定窗口内定生死。
2. **为省事设的护栏常常连正路一起拦**（与踩坑 #45「去重键顺手拦了宽度」、#50「差分扩散顺手拦了重绘」同源）：加**防重入锁**时，必须同时给锁配一把**超时钥匙**，否则 lock 成牢笼。
3. 宿主 event loop 严重卡顿时，**UI 卡片的握手消息可能迟到数十秒**——这是环境的既成事实，卡片设计必须对其容错，不能假设毫秒级握手。

**成色**：根因有代码依据 + 宿主延迟实测证据，但**未做真机埋点复现**；修法为静态推导。真机验收 = 切走再切回会话（切会话会重建卡片 iframe、重跑脚本，即天然重载）。

**2026-10-14 00:50 真机补充**：以「生图撞卡」方式做了三次真机验收（hui 画布路径），三张任务卡均**正常渲染**（标题/耗时/状态/进度/节点时间轴/产物缩略图齐全），**无一张卡在「未能取得卡片身份」**——死错误未回归。但边界要说清：卡片「能渲染」只证**没坏**，不等于自愈分支被真的触发过（当晚宿主未卡到极端程度）。极端验证需等宿主真卡时。

## 54. `inputs` 注入键名写错 → 静默落空 → “假成功”（2026-10-14 凌晨）

**现象**：用 `comfyui(action="submit", workflow={"template":"…"}, inputs={"6.text":"我的提示词"})` 提交，回执成功、也出了图，**但图是工作流自带旧提示词的结果**（已得水豚），不是注入的那条。

1. 注入前先用 `canvas op=get` / `trace` 查真实参数名（不信直觉）；`PrimitiveStringMultiline` 用 `value`。
2. `inputs` 形态会被豁免直走后端；**要人机共驾 / 要值必正确，就去掉 inputs 走画布路径**（`setWidget` 写入 → `canvas.op=queue` 执行）。
3. setWidget 报「节点 #N 没有名为 xx 的参数」时，该报错本身就是**参数名真相源**（回执会列出可用槽名）。

## 55. 有副作用的节点没声明 `fingerprint_inputs` → 被缓存跳过，服务压根没起（2026-10-23 凌晨）

**现象**：同一条提示词连跑两次，**第二次必报** `All connection attempts failed`（`PromptExpand` 连不上 `127.0.0.1:8080`）。日志对比很刺眼：成功的几次都有 `[moss-llm-auto] 加载增强模型`，失败的几次**一行加载日志都没有**，直接「等待响应」然后超时。改一个字再跑就好了，改回去又挂。

**原因**：`moss-gpu-free` 的 `LLMAutoLoad` / `LLMAutoRelease` 是有副作用的节点（起/停 llama-server 子进程），但**没声明 `fingerprint_inputs`**（V1 里叫 `IS_CHANGED`）。`ComfyUI/execution.py` 的 `IsChangedCache.get` 对这类节点**直接 `is_changed = False` 就返回**——连比较都不做；输入没变就复用上次的缓存输出，`execute` 根本不执行。副作用不会因为缓存而复现。

为什么卸载从没漏：`LLMAutoRelease` 的输入是 `PromptExpand` **增强后**的文本，每次都变，缓存永不命中，所以它每次都老老实实执行。于是形成不对称：**卸载每次都跑（把服务停掉），加载有时被跳过（服务起不来）→ 必然连不上**。

**教训**：
1. **凡有副作用的节点（起进程 / 停进程 / 写文件 / 发网络请求 / 改外部状态），必须声明 `fingerprint_inputs` 并恒返回 `float("NaN")`**（NaN 与自身也不相等 → 每次都判为变化）。v3 节点写法：`@classmethod def fingerprint_inputs(cls, **kwargs): return float("NaN")`；V1 写法是 `IS_CHANGED`。
2. 排查这类「时好时坏」的报错，**先看日志里本该出现的那行是不是消失了**。副作用节点连日志都没有，基本就是被缓存跳过，而不是执行失败——直接去查它有没有 `fingerprint_inputs`。
3. 「同输入第二次必挂」是验证缓存问题的免费实验：改一个字就好、改回去又挂，实锤。
4. 这一条不限于本项目：任何接了外部服务的自定义节点都可能踩。已知同源实例：`moss-gpu-free` 的 `MOSSLLMAutoLoad` / `MOSSLLMAutoRelease`（2026-10-23 已补）。

## 56. 抓图与取工作流身份隔着 `await` → 快照写进另一张画布的历史（2026-10-24）

**现象**：在 A 画布提交几次生图，切到 B 画布再提交几次，回来发现 A 的提交历史里多了一条不属于它的记录（图是 B 的工作流），提交节点上所有分组色条全亮，看着像「串台」。

**原因**：`installQueuePromptCapture` 包装 `api.queuePrompt`：

```js
let graph = app.graph.toJSON();               // ① 抓图（画布 A，同步）
const r = await orig.apply(this, callArgs);   // ② 原生提交，数秒
void reportHistoryCommit({ graph, ... });     // ③ 上报
  → workflow = currentWorkflowInfo().name     // ④ 此刻才取工作流名（可能已是画布 B）
```

①与④之间隔着 `await`。只要用户在这几秒里切了画布，就变成**图归 A、名字归 B**，快照被写进 B 的历史。`withWorkflowId()` 里的 id/path 同样是在 ④ 附近现取，一起错。

**实测证据**：`moss-image-SFT综合` 的 `seq=359` 存的是 42 节点的 Qwen 工作流快照（`TextEncodeQwenImage21`/`BasicGuider`），三秒后的 `seq=360` 又变回 17 节点的 MOSS 图。

**教训**：
1. **凡是「异步动作前后各取一次状态」的链路，两次取参必须来自同一时刻**。最稳的做法是动作发起前一次性捕获所有元信息（图 + 身份 + 来源），随请求一起带过去，上报时一律用捕获值，不再现取。
2. **别只捕获显眼的那一个**（这里是 graph）。身份（name/id/path）、来源（user/agent）同属「此刻的状态」，漏一个就是同一个 bug 的另一个入口。
3. **「所有色块都亮」不等于串台**：提交节点上的色条是分组框色条，delta 碰过哪些框就亮哪些；整图替换必然全亮。看到全亮先查该条记录的图属于哪个工作流，而不是先怀疑渲染。
4. 排查这类问题，**比对快照内容比读代码快**：把可疑 seq 的快照节点类型列出来，和该画布本体的节点类型一比，归属立刻清楚。

## 57. 竖排条堆塞不进节点高度 → 后面的框永远不亮（2026-10-26 凌晨）

**现象**：John 反馈「更改的模块，提交节点彩条不亮」。截图里每个节点只亮一根黄条。

**根因**：提交节点的框色条是**竖排**的（`.hnode-bars { flex-direction: column }`）。6 个框要 6 根条 + 5 个间距：极小档需 8.5px，而节点紧凑档的**内高只有 6~7px**（`nodeH` 11~12px 减掉边框与内边距）。`overflow: hidden` 把底部几根直接裁掉 → ⑤、⑥ 永远不可见，改它们当然没反应。

**实测对照**（同一套几何链）：
```
nodeH | 内高 | 可容纳条数 | 6 个框够不够
    8 | 4.00 |          3 | 缺 3 根
   11 | 7.00 |          5 | 缺 1 根
   12 | 7.00 |          3 | 缺 3 根
   18 | 10.0 |          3 | 缺 3 根
   22 | 14.0 |          4 | 缺 2 根
```

**修法**（2026-10-26 二次修正，以此为准）：**不改方向、不压细条**，改为**节点高度与泳道行高按该树的最大框数自适应**。

第一次修的时候我把条堆改成了横向分段（`.hnode-bars-row`），被 John 当场否掉，原话：
「彩条本来是竖着的，为什么变成横着的？」「为什么要压细，明明可以根据条数自适应提交节点高度啊」。

他说得对：**条是信息载体，不该为了让容器装得下而把条压没或换方向，应该让容器跟着内容长高。**

正确解法：
- 条高与间距保持现有档位公式不变（不压细）
- 先算该树**全量** entries 里的最大框数 `maxBlocks`（必须用全量，不能用可见集，否则隐藏节点会让行高跳动）
- `need = maxBlocks * barMin + (maxBlocks - 1) * gap`，`nodeHNeed = need + 2 * (bw + pad)`
- `nodeH = max(现有公式值, nodeHNeed)`，`laneH = max(14, round(36*zoom), nodeH + 6)`
- 效果：3 个框的树节点仍很矮，6 个框的树节点高一些，每根条保持正常粗细

历史框（`.hhb-tick`）的条堆不受影响（刻度本来又窄又高，竖排且内高充足）。

**教训**：
1. **凡是「N 个元素堆进固定容器」且 N 会增长的布局，先算容量再选方向**。竖排对「矮而宽」的容器必然失败，横排对「窄而高」的容器必然失败。
2. 这类 bug **没有任何报错**，`overflow: hidden` 是静默的。判断方法是数「实际渲染了几个」而不是看代码对不对。
3. 任何「用户改了 A，A 没反应」的报障，先问**A 是否根本没画出来**，再怀疑数据。
4. **容器装不下就改容器，不要改内容**。改变方向、压细条、藏掉一部分，都是在牺牲信息去迁就布局；而尺寸本来就是可以算着长的。方向类改动（竖→横）尤其不能自作主张，它是设计语义，不是实现细节。

## 60. 虚拟节点适配漏了 bypass：转换成功，接线不是用户画的那样（2026-10-31 凌晨）

**现象**：Set/Get 的 `pull` 规则落地后跑真实语料，「类型 SetNode/GetNode 不在 `/object_info`」类拒绝原因清零了，但产物里那些节点的下游接线跟用户画的对不上——不报错、结构看上去正常，属最难查的一类。

**根因**：「掐断」有两个状态——mute（mode 2）与 bypass（mode 4）。代码里 mute 分支写成了 `delete`（断链：不取源 + warning），mode 4 分支**没碰**，于是被 bypass 的取端/存端仍然按名取源，接上了一条用户在画布上已经旁路的线。两种状态是同一个语义，判定却写在两处、且只写了一处。

**教训**：
1. **同一语义的多个状态必须共用一条判定**（`mode === 2 || mode === 4`），不要按状态分支各写一段；分支一旦分叉，补一边必然漏另一边。
2. **「转换通过」不等于「接线对」**。虚拟件干的就是重写连线，产物合法但接错边，后端照样能跑——验证必须对着原始连线逐条核（改接到哪个 `origin_id` / `origin_slot`），不能只看有没有报错。
3. **语料验证要覆盖 mode 非 0 的实例**；只挑 mode 0 的样本跑，「拒绝原因清零」也能达成，漏掉的恰好就是这次的问题。
4. 与 58 同类：都是把「看起来对」当成「已经对」。判据要落在可核对的对象上（连线元组、赋值点），不能落在观感或日志上。

## 61. 子图 links 是对象不是数组，且实例 widget 值不能按下标定位（2026-10-31）

**现象**：写子图展开时，按主图 links 的习惯拿数组下标读子图链接，结果全部错位；widget 值按槽序近似定位时，位置错一格——KSampler 的 seed 读出来对不上，值还像模像样，不逐个核对根本看不出错。

**根因**：两个独立坑叠加。①主图 `links` 是数字数组（`[id, origin_id, origin_slot, target_id, target_slot, type]`），但 `definitions.subgraphs[i].links` 是**对象数组**（每项含完整键名）——同名不同形，套错口径就错位。②实例 widget 值的对位不能按任何下标（节点 inputs 槽序、定义声明序都不行）：必须按**名字**对位——外部连线 → 实例槽 `name` → 子图定义 `inputs[].name` → 定义下标 → `origin_id=-10` 的子图链接 → 内部消费端。因为实例槽、定义输入、`widgets_values` 三轴不同轴（minimax 样本 9 槽 / 15 输入 / 13 项），按下标对位会转换成功、参数全错、零告警。

**教训**：
1. **结构先取证再写代码**：同名容器在不同作用域里形可以完全不同，读一个字段的形状前先看真实样本，不要从邻近字段外推。
2. **两处对位必须共用同一份按名字的实现**：主循环写 widget 位置与子图展开传 widget 值，都按名字对位（named 优先，无 named 按定义序 widget 输入回退且项数不符拒绝）；当初本条初稿写「按声明序定位」——当时从单个样本（moss 14/14/14 恰好对齐）归纳结构，结论是错的，后来 minimax 样本（9/15/13 不同轴）推翻了它。近似口径（`slotOrderWidgetIndexOf`）只许做只读比对，绝不许写位置。

## 62. 把「静音/旁路」一律拒绝，等于替用户判了死刑（2026-10-31）

**现象**：旧版遇到 mode 非 0 的节点一律整份拒绝。扫 170 份真实工作流，静音/旁路贡献了 382 条阻断、殺及 78 份文件——用户只是在画布上关掉了几个节点，整份工作流就交不出来。

**根因**：把「我不知道怎么转换」当成了「这个图不该转换」。ComfyUI 原生语义里，mute（mode 2）是断链不执行，bypass（mode 4）是按类型把输入穿透到输出——两者都有确定的提交语义，翻译得过去就不是阻断；真正该拒绝的只剩未知 mode。

**教训**：
1. **拒绝前先问「用户在图里本来就是这么存的吗」**：工作流里的每个字段都是用户在前端操作的结果，先查前端对它的处理语义，再决定转换器跟不跟着走；不能因为转换器自己不会处理，就宣称这个状态非法。
2. 拒绝面每扩大一寸，可用性就少一分：这次改完（mute 断链、bypass 穿透、未知 mode 仍拒绝），静音/旁路类阻断 382 → 0，能直接转换的文件 17 → 35。
3. 与 #60 同源：mode 语义没吃透，先写出「漏判旁路」的错接线，又写出「一律拒绝」的过严判——同一块语义，两頭都摔过。

## 63. 同名不同实：rgthree 的 Reroute 类型是 `Reroute (rgthree)`（2026-10-31）

**现象**：给 rgthree 写适配档案，按裸名 `Reroute` 建、按裸名匹配，转换时一次都命中不了；节点在图里明明存在，档案就是不被消费。

**根因**：节点类型字符串带插件后缀——rgthree 的转发节点注册名是 `Reroute (rgthree)`，不是内置的 `Reroute`。档案匹配按类型字符串精确对齐，裸名档案对带后缀类型永远失配。顺带确认：Fast 类控件（Fast Muter/Bypasser 等）的状态存在目标节点的 `mode` 里，不占 widgets_values，丢控件不丢值；`Context (rgthree)` 等真后端节点一个档案都没写——它们会进 prompt，写了伪 passthrough 档案会静默断供。

**教训**：
1. **档案按类型字符串精确匹配，核名必须回源码常量表**（节点的注册名，不是 UI 显示名，更不是「看着像」的内置名）。
2. 「同名不同实」是插件生态的常态：先确认 type 字符串全等，再谈映射；拿内置类名去猜插件类型，失配是静默的（档案不命中不报错）。
3. 写档案前先分类：纯前端辅助件（不进 prompt）才能写 virtual/passthrough；会进 prompt 的后端节点宁缺毋滥——档案的价值在于让转换对得上用户的图，不在于把拒绝清单变短。

## 64. 从一个样本归纳结构，差点把错参数写进所有人的工作流（2026-10-31）

**现象**：子图展开的 widget 值对位最初写成「按声明序/下标」，测试全绿、moss 样本（`image_moss_image_t2i.json`，实例 14 槽 / 定义 14 输入 / `widgets_values` 14 项）参数逐项核对也一致。后来拿 minimax 样本（`minimax_h3_t2v_int8.json`）验证：实例 9 槽（2 socket + 7 暴露 widget）、定义 15 输入、`widgets_values` 13 项——三轴不同轴。按下标对位：k=2（width，INT）被接到定义第 2 槽 `prompt`（STRING，无类型校验放行）、k=7 把 video VAE 文件名写进 `unet_name`——转换成功、参数全错、零告警。moss 样本 14/14/14 恰好对齐，旧实现只在它身上成立。

**根因**：把「恰好对齐」当成了结构规律。测试也只建在对齐形态（moss）上，同一种偏差被两道关同时放过。这类错误最阴脸：它不报错、不告警，产物看起来完全合法——「转换成功」不等于「转换正确」。

**教训**：
1. **结构假设要拿两个以上形态不同的真实样本交叉验证**：单样本归纳出的规律，可能只是那份样本的巧合；换一个轴对不齐的样本就能验伪。
2. **下标永远不如名字可靠**：容器三轴（实例槽 / 定义输入 / 位置值数组）不同轴是常态，对位一律走名字（named 逐键；无 named 时按定义序回退且项数不符拒绝、named 与位置值分歧拒绝）。
3. **「转换成功」不等于「转换正确」**：静默错参数只有独立复核（换样本、换角度、逐参数对照）才抓得到，测试通过不是安全证明。
