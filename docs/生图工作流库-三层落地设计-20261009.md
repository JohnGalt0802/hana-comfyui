# 生图工作流库 · 三层结构落地方案（讨论稿）

日期：2026-10-09（深夜讨论定稿方向；本文为固化稿）

相关：hui 人机共驾（画布可见可调）、踩坑记录、资产地图

---

## 0. 总览

```
意图 ──▶ [skill：选 / 填 / 验 / 录] ──▶ [库：工件 + 状态机] ──▶ 真实生成（人机共驾）
                    ▲                                              │
                    └────── [成长循环：轻记录 → 定期提炼] ◀──────────┘
```

三层分工（一句话）：
- **库**管"结构"（图怎么搭、依赖什么），工件化、可执行、可打开；
- **skill** 管"判断"（选哪个、怎么填、怎么验、怎么维护）；
- **循环**管"成长"（什么被接受、什么被淘汰，回流前两层）。

核心原则：**来源不分贵贱，状态管命运**。实战收入的流与 agent 自建的流走同一条流水线，自建流从 candidate 起步。

## 1. 第一层：工作流库（工件层）

### 1.1 目录结构

```
<库根>/
├── index.json              # 自动生成（机读）
├── index.md                # 自动生成（人读）
├── runs.jsonl              # 轻记录（见 §3）
└── <slug>/                 # 每个流一个自包含目录
    ├── workflow.json       # 画布格式（人可开可调）；提交时导出 API 格式
    ├── meta.json           # 元数据卡（接口）
    └── sample.png          # 代表作（连同当时的参数快照）
```

### 1.2 元数据卡 schema（meta.json）

```json
{
  "id": "t2i-photo-basic",
  "name": "文生图 · 写实基础",
  "purpose": "从零生成写实照片风格图像；支持画幅与比例切换",
  "intent_keywords": ["文生图", "写实", "照片", "text2image"],
  "status": "verified",
  "source": "handoff | agent-built",
  "created": "2026-10-10",
  "verified": { "at": "2026-10-10", "level": "L3", "by": "user" },
  "variables": [
    { "node": "6", "field": "text", "label": "正向提示词", "hint": "主体+环境+光线+质感，按语义块组织" },
    { "node": "7", "field": "text", "label": "负向提示词", "hint": "默认沿用", "default": "..." },
    { "node": "5", "field": "width", "label": "宽", "range": "512-1536" },
    { "node": "3", "field": "seed", "label": "种子", "hint": "探风格用随机；复现固定回传" }
  ],
  "dependencies": { "models": ["..."], "loras": [], "custom_nodes": ["..."] },
  "sample": { "file": "sample.png", "note": "参数见同目录 sample.params.json" },
  "known_issues": [],
  "notes": ""
}
```

要点：卡片是唯一接口，上层只读卡；变量之外的一切字段冻结。

### 1.3 验证状态机

```
draft ──▶ candidate ──▶ verified ──▶ retired
  (我建/设计阶段)  (待实战验证)     (默认操作可用)    (退役，保留说明)
```

晋级 / 降级条件：
- draft → candidate：具备完整卡（用途、变量、依赖齐全）+ 一次技术性跑通（L1）；
- candidate → verified：至少一次真实任务中胜出（用户接受，L3），中途失败进 known_issues；
- verified 降级：连败两次或依赖失位（模型/LoRA/节点缺失）→ 回 candidate 或标警；
- 任意 status → retired：长期零引用、或质量漂移无法修复；**不删文件，留退役说明**。

### 1.4 「先定卡、后造物」（agent 自建流规范）

我新建工作流时，必须先写卡：用途一句话、变量清单、依赖清单——说不清的，就是还没想清，不搭图。产出即 candidate 态入库，等实战晋级。**未经实战的流永不出现在"默认操作"位，只能作为建议。**

### 1.5 索引自动生成

索引（index.json / index.md）由脚本扫描各 meta.json 生成，杜绝手工失同步。索引含：slug、名称、用途、状态、依赖要点、变量数、代表作缩略引用。

## 2. 第二层：skill（判断层）——四节骨架

skill 名暂定：`comfyui-workflow-library`（与 hui 的 comfyui-hana 技能并列，加载时读取库索引与约定）。

- **选（路由）**：任务类型分桶（文生图 / 图生图 / 编辑 / 放大）→ 题材与资产匹配。默认操作只指向 verified；意图模糊给 2-3 候选让用户点选；全新意图走"新建流"通道（先定卡后造物）。
- **填（旋钮）**：只动 variables 列出的字段，其余冻结；默认值策略（种子、负词、尺寸族）。
- **验（验收协议三级）**：
  - L1 跑通：无报错、出图、尺寸正确（机器可判）；
  - L2 稳定：同参重跑不崩、耗时可预期（机器可判）；
  - L3 效果好：对照代表作 + 用户接受（**判定权在用户**，agent 不得自判）。
- **录（维护规程）**：入库流程（卡先于图）、标坑规范、退役流程、提炼节拍（见 §3.2）。

## 3. 第三层：成长循环（记录层）

### 3.1 轻记录（runs.jsonl，一行一条）

```json
{"t":"2026-10-10T01:23:45","intent":"给客厅出一张暖光写实","flow":"t2i-photo-basic","params":{"seed":12345,"width":1024},"result":"ok|fail","user":"accepted|rejected|silent","note":"用户手动把强度 0.8 改到 0.6"}
```

规则：**agent 记，用户零操作**。只记"能改变未来行为"的字段，宁缺毋滥。

### 3.2 提炼节拍

触发：会话收工前 / 满一批未提炼记录。动作（agent 执行、关键变更给用户过目）：
- 被接受的参数 → 固化为流默认或新增变体；
- 被反复打回 → 记录原因，必要时降级；
- 反复出现的"用户手改项"→ 收编为默认。

### 3.3 用户修正回流（最高价值数据）

定期比照"我生成的版本"与"用户在画布上调整后的版本"，把差异归纳为：参数修正 / 结构修正 / 提示词修正。参数级修正直接回流；结构级修正走"先定卡后造物"建变体。**用户改了什么，比生成了什么更值钱。**

## 4. 配套：资产地图与依赖体检

- 资产地图：从 ComfyUI 拉取本机模型 / LoRA / 节点清单（自动），标注"验证过的搭配"；
- 依赖体检：逐流对账 dependencies vs 资产地图，缺件标红；体检结果进索引（每个流显示"可跑 / 缺件"）。

---

## 5. 防翻车护栏（六条）

1. 未验证不进默认位（candidate 只能被"建议"，不能自动选）；
2. 记录零操作（要用户填表的记录系统活不过一周）；
3. 卡与流同目录、同更新（防漂移）；
4. 不删只退役（保留说明给后来者）；
5. 代表作 + 参数快照随卡片（L3 验收的对照物）；
6. 状态硬条件（晋级/降级不由感觉决定，见 §1.3）。

## 6. 第一步（薄启动）与待拍板

待拍板：

首批动作清单：
1. 建库骨架与索引脚本；
2. 收编最近真实跑顺的一条流作为样例（走完整卡）；
3. 写 skill 第一版（选填验录四节，先薄）；
4. 用 2-3 个真实任务走全链（选→填→验→录），观察卡点；
5. 一轮提炼后修订本文档。

原则：**先薄后厚，用到哪、验证到哪、录到哪。**
