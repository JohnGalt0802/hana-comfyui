# 大工作流提交修复（M13）—— 绕开宿主 runtime.fetch 的 1 MiB / 4 MiB 限制

> 2026-09-29 · 状态：方案定稿，实施中
> 动因：群友反馈 —— 提交 4MiB+ 工作流文件时被拒（"Hana 的 ComfyUI 中继服务有 4MiB 限制"）。

## 一、问题与复现（实测）

群友场景：Qwen-Image 系工作流文件 >4MiB，经 comfyui 工具 submit 失败。

**本机复现（已实测）**：
- 造 4.79MB UI 格式 JSON（`_temp/big-read-test.json`）→ `comfyui(action="submit", workflow="<文件路径>")`
- 结果：`comfyui(submit) 失败：Managed service response exceeds the 4 MiB limit.`

## 二、根因（代码级定位，实测）

链路：app(index.js) → `sdk.runtime.fetch`（宿主隧道）→ 中继(comfy-relay.mjs) → 8188

宿主 server（0.1050.9）对「app → 受管 runtime」fetch 隧道有**硬编码**限制（`bundle/index.js` 常量区）：
- 请求体 ≤ **1 MiB**：`sBr = 1024 * 1024` → "Runtime fetch body exceeds the 1 MiB request limit."
- 响应体 ≤ **4 MiB**：`iBr = 4 * 1024 * 1024` → "Managed service response exceeds the 4 MiB limit."（错误码 `APP_RUNTIME_FETCH_RESPONSE_TOO_LARGE`）
- 均**不可由 app 配置放宽**（与 manifest 的 `network.maxResponseBytes` 是另一条链路，无关）。

comfyui-hana 提交链路的两个撞墙点（当前实现）：
1. **读文件**：文件 / template 形态把工作流内容经隧道拉回 app（`/_relay/fs/read`、`/_relay/userdata`）→ 内容 >4MiB 即响应超限 ✗（群友遇到的）
2. **提交**：`POST /prompt` 经隧道发出，请求体 = prompt 全量 → >1MiB 即请求超限 ✗（大 API 文件的次生风险；UI 转 API 后一般较小）

## 三、方案：中继侧直读直提（M13）

**原则**：大数据留在中继侧处理，只让「描述」与「结果」过隧道（两者均为小 payload）。
（同思路先例：`/_relay/upload`、`/_relay/fs/read` 本就是「中继本地读」模式。）

新增中继端点 `POST /_relay/submit-file`（controlKey 保护）：
- 入参：`{ path | template, inputs?, front? }`
- 中继侧完成：读文件（本机 fs 直读，不过隧道）→ 解析 → UI→API 转换（object_info 直取 8188）→ inputs 注入 → `POST 8188 /prompt`（client_id 与 /ws 订阅一致）→ 返回 `{ ok, prompt_id, source, nodeCount, applied }`（小响应）

**app 侧**：`actionSubmit` 分流 —— 文件 / template 形态走新端点；inline 对象形态保持原链路（对象已在内存，罕见大体积，一期不动）。
**代码组织**：`convertUiToApi` / `applyInputs` / `summarizeWorkflow` / 相关常量抽到 `lib/workflow-tools.mjs`（app 与中继同源 import，杜绝两份漂移）。

## 四、边界与风险

- 不改宿主；不碰 ComfyUI 本体；对象形态链路零改动（回退面小）。
- 读入上限设 64 MiB（本机内存保护）。
- 隧道 timeoutMs 上限 30s：中继内部各步超时收敛（object_info 12s / prompt 15s），保证 <30s 必回。
- **遗留（二期候选）**：
  - `workflows` 动作"读取结构摘要"读大文件（同"读取"限制）
  - 画布 `loadWorkflowFile` 读大文件（同）
  - inline 对象形态 >1MiB（可经"写临时文件 → submit-file"通道解决）
  - `/_relay/bridge` 大画布 JSON 响应 >4MiB（评估）
  - **向宿主方反馈建议**：评估放宽该隧道限制（如 32M/64M）或提供流式通道。

## 五、测试计划

1. **中继级单测**（standalone，`tools/m13-checks/test-submit-file.mjs`）：大文件（4.6MB，含巨型 Note，转换后被跳过）→ 提交成功；小文件 API 直提；template 正/负例；错误路径（不存在 / 非 JSON）。
2. **宿主段 E2E**：comfyui 工具提交 4.6MB 文件 → 成功返回 prompt_id（对照：修复前已复现失败）。
3. **回归**：inline 对象形态、常规小文件提交不回退。
4. **纪律**：测试一律极小纯 CPU 工作流；测试前确认队列为空。
