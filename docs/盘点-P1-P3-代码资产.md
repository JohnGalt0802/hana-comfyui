### 1.2 序列化/反序列化、剥 base64、graphSignature / fnv1a 在不在本文件？

- **序列化 / 反序列化**：
  - `buildSnapshot`(`:110`) 仅**构造**内存快照对象（graph 原样挂上），**不做 JSON 序列化**。
  - `parseIndex`(`:197`) 是索引 JSONL 的**反序列化**入口。
  - **快照 JSON 的 `JSON.stringify` 不在此模块**——由调用方完成：`app/runtime/history-commit.mjs`（用 `JSON.stringify(snapshot)`）与 `app/bridge/history_store.py`（用 `json.dumps(snapshot, ...)`）。本模块只产出可序列化对象。
- **剥 base64**：✅ 在 `stripHeavyFields`(`:159`) + `walkStrip`（内部）。正则 `BASE64_IMAGE_RE = /^data:image\/[a-z0-9.+-]*;base64,/i`（`:30`），命中替换为 `STRIPPED_IMAGE_PLACEHOLDER`。
- **`graphSignature`**：❌ **不在本文件**（在桥 js `:634`，见 §2）。
- **`fnv1a`**：❌ **不在本文件**（在桥 js `:625`；另有 `fnv1aU32` `:216`）。
- **`blocks` / 块归属**：❌ **不在本文件**。块计算在桥 js 的 `graphBlocks`(`:2258`)，且为 `canvas-outline.mjs` 的**复制**（CSP 下桥不能 import ESM）。`canvas-history.mjs` 只透传 blocks 字段（在 `buildIndexLine` / `parseIndex` 里当普通对象读），不计算。

## 3. 索引格式 `index.jsonl`

真实样本：`D:\ComfyUI\ComfyUI\user\default\workflows\.history\Qwen21 t2i 质量版 (00012)\index.jsonl`（17 行，seq 1–17）。

每行一条 JSON 对象（由 `build_index_line` / `buildIndexLine` 产出，**不含 graph**）：

| 字段 | 类型 | 含义 | 取值/示例 |
|---|---|---|---|
| `seq` | number | 提交序号（自增） | `1`…`17` |
| `file` | string | 对应快照文件名 | `"0001-bc1547d2.json"` |
| `promptId` | string\|null | 本次运行 prompt_id（UUID） | `"bc1547d2-9370-434f-99ae-37e8b9ea4413"` |
| `at` | string\|null | 提交时间 ISO8601 UTC | `"2026-10-11T12:10:43.041Z"` |

| `nodeCount` | number | 画布节点数（落盘时） | `25` |
| `linkCount` | number | 画布连线数（落盘时） | `32` |

### 4.1 顶层键

|---|---|---|
| `schemaVersion` | number | = 1（`SCHEMA_VERSION`） |
| `seq` | number | 提交序号 |

### 4.2 `graph` 是 UI 格式还是 API 格式？含哪些顶层键？

- **UI 格式**（`graph.toJSON()` 输出，即 LiteGraph UI 序列化），**非 API/Prompt 格式**。
- 证据：含 `widgets_values`、`groups`、`version`、`extra`、`revision`、`last_node_id`、`last_link_id`、`id`、节点带 `pos/size/flags/title/widgets_values_named` 等——这些都是前端 UI 形态，API 格式只有 `nodes[]{class_type,inputs}` + `links`，无上述键。
- 样本 `graph` 顶层键：`id`、`revision`、`last_node_id`、`last_link_id`、`nodes`、`links`、`groups`、`config`、`extra`、`version`。
  - `nodes[]`：每个节点含 `id,type,pos,size,flags,order,mode,inputs,outputs,title,properties,widgets_values,widgets_values_named`。
  - `links[]`：每条 `[linkId, fromNode, fromSlot, toNode, toSlot, type]`。
  - `groups[]`：每个 group 含 `id,title,bounding[x,y,w,h],color,flags`（与 `historyGroupRect` 读取的序列化字段对应）。
  - `blocks[]`（快照级）：`[{name, source:"group", nodeIds:[2,4,5]}, …]`——`source` 取 `"group"` 或 `"role"`，`nodeIds` 升序。

## 5. 块识别算法：`canvas-outline.mjs` 归组函数 vs 桥 `historyGroupRect`

### 5.1 `app/lib/canvas-outline.mjs` 的归组相关函数

| 函数/常量 | 行号 | 口径 |
|---|---|---|
| `ROLE_RULES`（常量） | `:37` | 角色兜底表：`/Loader\|LoadImage/→加载`、`/TextEncode\|TextGenerate\|StringFormat/→文本`、`/Sampler\|Scheduler\|Guider\|Noise/→采样`、`/^(Save\|Preview)/→输出` |
| `ROLE_FALLBACK = "其他"` | `:42` | 兜底角色 |
| `parseId(v)` | `:45`（内部） | 数值容错解析 |
| `cmpIds(a,b)` | `:50`（内部） | id 比较（数值优先，否则字符串序） |
| `keyOf(v)` | `:57`（内部） | 归一化 id 键（`8` 与 `"8"` 同键） |
| `minIdOf(ids)` | `:62`（内部） | 取块内最小 id |
| `outlineGraph(graph, {detail,select})` | `:71` | **主归组函数**：① `graph.groups` 非空时节点 pos 落在 bounding 内→归组（落多组取第一个，组名=title，空→`组{i}`）；② 未归组→角色兜底（first-match）。块名重名去重 `#k`；块按块内最小 id 升序；输出含 `blocks/blockEdges/issues/summary` |

归组口径（两级）：**group 优先（框内）+ 角色兜底**。空 group 不成块；与桥 `graphBlocks` 口径一致。

### 5.2 桥 `historyGroupRect` 是双处维护吗？

- **不是同一算法双处维护**。`historyGroupRect`(桥 `:2471`) 只解决「**运行时 group 实例的矩形怎么读**」（字段名在运行时是 `_bounding`/读不到 `bounding`，序列化才是 `bounding`），是读出框范围，不是归组。
- 真正的「块识别 / 归组」算法有两处：
  1. `canvas-outline.mjs` 的 `outlineGraph`（规范的纯模块，有单测 `canvas-outline.test.mjs`）。
  2. 桥 `graphBlocks`(`:2258`)——**复制** `canvas-outline.mjs` 的归组逻辑（注释明示「CSP 下桥不能 import ESM，只能复制而非引用；改动需同步两侧」）。
- 因此：**归组算法是双处维护**（outline 源 + 桥 graphBlocks 复制），`historyGroupRect` 是单处（仅桥内，服务于点击命中取框范围）。⚠️ 见 §7 问题。

## 6. 端点：`GET/POST /hana_bridge/history-*`

对照两端：桥 js（`HISTORY_*_PATH` 常量 + `postJson`/`fetchApi`）与 `app/bridge/__init__.py`（`_ROUTES` 注册 + `history_store.py` 落地）。三端点均**不校验 token**（P1-D1：8188 同源、本机-only 信任模型）。

### 6.1 `POST /hana_bridge/history-commit`

- **桥侧**：`reportHistoryCommit`(`:2239`) → `postJson(HISTORY_COMMIT_PATH, body)`。
  - 请求体：`{workflow, promptId, graph, at, source:"user"}`，可选 `blocks`（array，来自 `graphBlocks`）。
- **Python 侧**：`_hana_history_commit`(`__init__.py:612`) → `_history_commit(body, user_dir)` = `history_store.commit`(`history_store.py:commit`)。
  - 入参 body：`{workflow(必), promptId?, graph(必,dict), at?, source?, blocks?}`；`user_dir` 由 `_history_user_dir()` 解析（`<user_dir>/workflows/.history/<净化名>`）。
  - 出参：`{ok:true, status:200, seq, file, dir}` 或 `{ok:false, status, error}`；400=缺 workflow/graph，413=超 14MiB，500=IO/目录失败。
  - 落地：写 `NNNN-*.json`（含 graph + blocks 全量）+ 追加 `index.jsonl`（blocks 仅摘要 `{name,nodeCount}`）。

### 6.2 `GET /hana_bridge/history-list`

- **桥侧**：`historyBarLoad`(`:2514`) → `api.fetchApi(HISTORY_LIST_PATH + "?workflow=" + encodeURIComponent(wfName))`；期望 `{ok:true, entries:[…]}`。
- **Python 侧**：`_hana_history_list`(`__init__.py:624`) → `_history_list_commits(workflow, user_dir)` = `history_store.list_commits`。
  - 入参 query：`?workflow=<名>`（缺→400 `missing_workflow`）。
  - 出参：`{ok:true, status:200, entries:[索引行对象…], badLines:N}`；目录不存在→空 entries（ok=true）；`entries` 每项含 `seq/file/promptId/at/source/nodeCount/linkCount/blocks摘要`，**不含 graph**（回跳需再调 snapshot 端点）。

### 6.3 `GET /hana_bridge/history-snapshot`

- **桥侧**：`historyFetchSnapshot`/`historyFetchSnapshotQs`(`:2980`/`:2987`) → `api.fetchApi(HISTORY_SNAPSHOT_PATH + "?workflow=…&file=…|&seq=…")`；校验 `{ok:true, snapshot.graph}`。
- **Python 侧**：`_hana_history_snapshot`(`__init__.py:639`) → `_history_read_snapshot(...)` = `history_store.read_snapshot`。
  - 入参 query：`?workflow=<名>` 必填；`&seq=<n>` 或 `&file=<文件名>`（`file` 优先；`file` 只接受纯文件名，含路径分隔→400）。
  - 出参：`{ok:true, status:200, file, seq, snapshot:{完整快照含 graph}}`；400=缺参/非法，404=无该历史的/索引缺 file，500=读/解析失败。
  - 定位：回跳拿完整快照的入口；`seq` 路径会从索引解析出 `file` 再读。

> 关联但**非桥端点**的同源实现：`app/runtime/history-commit.mjs` 的 `handleHistoryCommit`（路由 `POST /_relay/history/commit`）镜像同一逻辑（同样依赖 `canvas-history.mjs`），是较早的 relay 通道；当前活动桥走的是 `app/bridge/history_store.py`。两者口径应一致，属潜在双实现（见 §7）。

## 7. 发现的问题（双处维护 / 命名不一致 / 隐患）

1. **归组算法双处维护（高）**：`canvas-outline.mjs` 的 `outlineGraph` 与桥 `graphBlocks`(`:2258`) 是同源复制，注释写明「改动需同步两侧」。桥复制体**无专属单测**（仅 `canvas-outline.test.mjs` 覆盖源侧）。任一侧改了归组规则（如 P5 数据模型换代）都需手改两处，易漂移。
2. **落盘实现双处（中）**：桥活动路径 `app/bridge/history_store.py`（端点 `/hana_bridge/history-commit`）与 `app/runtime/history-commit.mjs`（`/_relay/history/commit`）镜像同一套 `canvas-history.mjs` 逻辑。P5 若改索引/快照结构，两处都要改；`history-commit.mjs` 当前是否被接线需确认（活动桥只用 history_store.py）。
3. **签名口径两版不一致（中）**：`graphSignature()`(`:634`) 逐节点串接含 `mode` 与 widget **name**（`type:mode:title:widgets`）；回跳用的 `historySnapshotGraphSig`(`:2948`) 串接为 `type:0:title:widgets_values`（无 mode、无 name）。两者同族、同 `fnv1a`，但**跨形态哈希不可比**。注释已说明「只用于当前画布 vs 最近提交同口径对齐」——但若 P5 把快照改 API 格式或加 mode，比对口径需重写。
4. **`graph` 字段名互斥陷阱（低，已处理）**：运行时 group 实例字段是 `_bounding`/`_pos`/`_size`，序列化 JSON 才叫 `bounding`（`historyGroupRect` 已按命中链处理）。P5 若新增「读画布框」场景，勿直接读 `group.bounding`（运行时会是 `undefined`）。
5. **`blocks` 在索引与快照里结构不同（低，设计如此但易踩）**：索引 `blocks[]` 是 `{name,nodeCount}` 摘要，快照 `blocks[]` 是 `{name,source,nodeIds}` 完整。回跳/UI 若想直接用索引里的块，注意缺 `nodeIds`。
6. **`source` 恒为 `"user"`（设计约束，P6 注意）**：`reportHistoryCommit` 写死 `source:"user"`（注释：agent 若经此通道也先记 user，后续批次再细分）。P6 若要做来源筛选 UI，当前数据里 source 全部是 user，暂无区分度。
7. **`renderPop` 不存在（命名澄清）**：任务清单提到的 `renderPop` 在代码里无对应函数——弹层 DOM 由 `historyBarOpen`(`:2591`)+`historyBarLoad`(`:2514`) 内联构建；P6 改造框 UI 时勿找错函数。
8. **活动桥是单文件、双载红线（架构约束）**：所有 history UI/逻辑都在 `hana-bridge-1011095446.js` 单文件里，不新建 js（见 `docs/调研-画布提交历史-P2落点.md` 结论）。P5/P6 改动应继续落在该文件，避免引入新桥文件触发双载。
