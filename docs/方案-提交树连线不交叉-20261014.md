# 方案 · 提交树连线不交叉（泳道就近排列，2026-10-14）

> **用户反馈**：新分支的连线出现交叉（跨越旧泳道）；要么新泳道放上面，要么旧泳道往下移。

---

## 1. 现状根因（实测）

泳道算法（`commitGraphLanes`）**只增不回收**：新分支一律 `lane = active.length`（排到最下方）。于是新分支从**上方的父**连下来时，必须穿过中间的泳道 → 连线交叉。

**实测样本**（用户截图那棵，id `3f10d6d5…`，13 主行）：
```
seq=1..10  lane=0   （主链）
seq=11-15  lane=1   （从 seq=8 分出，到 15 走到头）
seq=16,17  lane=0   （回主链，从 seq=10 续）
seq=18     lane=2   （又从 seq=10 分出）← 被甩到最底，跨 2 道 → 交叉
```
`18(lane2) ← 10(lane0) Δ=2` 即那条交叉线。lane1（11-15）此时已空闲，本可复用。

---

## 2. 算法选型（多方案实测对比）

用**几何交叉检测器**（按 x=拓扑序/时序、y=泳道，逐边拆段判相交）评测：

| 方案 | 说明 | 用户样本 | 测试2/3/4 泳道数 | 结论 |
|---|---|---|---|---|
| **A（现状）** | 新分支 append 末尾 | 1 交叉 | 2/5/6 | 有交叉 |
| D/F（回收复用） | 空闲泳道复用 + 就近 | **0 交叉** | **2/2 破坏契约** ❌ | 改泳道数，不可取 |
| 纯行序重排（②） | 只换行号不改身份 | 1 交叉 | 不变 | 不解决 |
| **G（经典 git 排法）** | 新分支插到父泳道**正下方** | **0 交叉** | **2/5/6 不变** ✅ | **选它** |

**G 算法**（推荐）：
```
每条泳道 = 一个持久对象，物理顺序 = 数组顺序。
· 延续：找 head === parent 的泳道 → 用它的位置。
· 新分支（无 head===parent 的泳道）：
    · 父泳道存在 → 插到父泳道对象的**正下方**（数组 insert(index+1)）；
    · 父泳道不存在（根 / 孤儿）→ append 末尾。
· 泳道不回收（保持「每条活跃分支一条泳道」语义）。
```
本质：**新泳道挤在父泳道下方，旧泳道顺延下移**（= 用户原话的两条路合一）。**不改泳道数、不改每泳道成员**。

**实测收益**：
- 真实 6 棵树：`3f10d6d5` 交叉 1→0；其余全 0 交叉、泳道数不变。
- 测试 2/3/4 断言的泳道数（2/5/6）**完全不变** → 既有契约零破坏。
- 合成 200 节点 ×10：交叉 401→100、176→67、38→9（大幅降；剩余为复杂拓扑固有）。

## 5. 验收

1. 用户样本树（`00002` 等有分叉的）：连线**无跨道交叉**（几何交叉检测器 = 0）。
2. 分叉处新分支紧贴父泳道下方。
3. 测试 `commit-graph-lanes.test.mjs` 全绿（原 7 例 + 新增 2）。
4. 提交树既有功能（热区点击、预览、回跳、视角切换）不回归。

**⚠️ 口径更正（实现时发现）**：初稿写的验收断言「`|lane − lane(parent)| ≤ 1`」**与 G 算法不相容**——新泳道插到父下方会让**后续泳道索引整体下移**，故 Δ 可 >1（如用户样本 `seq=11 parent=8`：lane 2 vs 0，Δ=2），但几何交叉数 = 0。即 **Δ≤1 是错的口径，真实验收口径是「几何交叉数 = 0」**。已按后者实现与断言。（测试 3 的 lane `headSeq` 期望随索引平移而变，属算法变更的合理结果；泳道数 5、sleeping 恒 false、row=lane 等核心契约不变。）
