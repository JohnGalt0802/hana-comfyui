# 排查：hui 保活「有时很久不死、有时切回就死」定案（2026-11-01）

**性质**：只读排查（探针数据 + 进程账本 + 代码检索）。未改代码。
**成色分级**：`[实测]` 数据/命令输出 · `[代码]` 源码检索 · `[推断]` 未见直接证据

---

## 0. 一句话结论

**死掉的从来不是 ComfyUI，也不是中继，而是「承载界面的那张页面」被整体销毁。** 服务、中继、App 进程三条都已排除。

**页面是被容器销毁带走的，不是被节流冻住的**：98%（395/402）的重建，前后 5 分钟内没有任何 `hidden` 切换记录。真实的后台节流会先出现 `hidden` 段落并继续心跳（实测有 `hidden` 下 60 秒一拍、`n` 持续递增的段落），而死亡现场没有这个先兆。

**载体的分辨在本轮数据里做不到，此前的一版草稿（2026-11-01 早）曾断言「窗口态稳、卡页态死」，该结论作废**：踹探针只在 App 主动开窗的路径上启动（`index.js:5605-5609`），用户日常的独立窗口由宿主按 manifest `detached` 配置创建，不经过该路径，因而没有被探针覆盖；生命周期日志里的 `href` 也只有 `/ui/_surface/<token>/workspace.html`，不带载体信息。John 已确认他一直在独立窗口里使用，且切走即挂 —— 所以「窗口页也照样被杀」是事实，不是例外。

**当前能落地的结论只剩一条**：容器销毁这件事，App 侧拦不住（宿主契约无续租口子），只能选载体、减损、或绕开。

## 2. 决定性证据：页面是被销毁，不是被节流

### 2.1 「节流致死」已被数据否掉

`keepalive-probe-trace/poke-1793252780322.jsonl`（App 开的窗口，探针覆盖到的少数时段）：

- 8367 拍，跨度 **23.3 小时**（10-29 13:46 → 10-30 13:01），无断档。
- `pageVisibility` **100% 是 hidden**，即窗口全程不可见。
- 应答往返 `deltaMs` 中位 **2 ms**，8357/8367 为 `ok`，10 次超时。

→ 隐藏本身不会杀死页面，也不会让它失去响应。这一段只能证明「隐藏不致命」，**不能**用来证明「窗口态更稳」。

### 2.2 死亡的样子

- 21 天 **402 次**页面重建（410 次 boot，仅 1 个实例存活至今）。
- **98%（395/402）** 的重建前后 5 分钟内没有任何 `hidden` 记录 → 页面在仍显示状态时被整体拿走。
- 重建后存活（415 个已结束实例）：`<1min` 21.2% · `1-5min` 27.5% · `5-30min` 26.3% · `30min-2h` 15.4% · `>2h` 9.6%，中位 **350 秒**。
- **36%** 的断档 ≤30 秒 → 链式重载：刚拉起又被拿走。
- 近 7 天略好：`<5min` 由 48.7% 降到 27%。

### 2.3 载体分辨：本轮数据做不到 (2026-11-01 更正)

| 做法 | 结果 |
|---|---|
| 用踹探针时段判定「是否窗口页」 | 不可靠：探针只覆盖 App 主动开窗（`openWorkspaceWindow`），宿主 `detached` 窗口不经过该路径 |
| 用 `shell-lifecycle.jsonl` 的 `href` 判定 | 不可行：统一是 `/ui/_surface/<token>/workspace.html`，不含载体字段 |
| 用宿主日志对齐 | 不可行：主机日志不记录 App 窗口的创建/销毁（`detached` / window closed 均 0 命中） |

要分辨，必须在壳页里补一条「我是不是独立窗口」的自报字段，再复现一次。

## 3. 「清单」是什么，以及它为什么救不了 hui（2026-11-01 实测）

这里推翻了一份来自宿主 1.1.24 的旧解释（「不在清单里就被 `pruneSurfacesNotInPages` 剪掉」）。当前宿主版本下不成立。

### 3.1 清单在哪、长什么样

宿主本地存档：`~\.hanako\chalkboard\client-layout-profiles.json`（约 30 KB）。整份文件只有 **1 个 profile**：

- 键：`clp:user_<uid>:server-node~…:desktop:layout~:main`
- `scope = { key: "layout:main", kind: "layout" }`，**没有会话级档案**（旧版本的分会话 scope 在当前版本不存在）
- 结构：`profile.pages`（页面清单）+ `layoutDocument.surfaces`（界面结构快照）+ `frame`（面板宽度等）

### 3.2 hui 已经在清单里，而且 role 是 persistent

```
profile.pages["plugin-page:comfyui-hana:workspace"] = { id, order: 3, title: "ComfyUI 工作区", shape: "circle" }
layoutDocument.surfaces["surface:page:plugin-page:comfyui-hana:workspace"] = { kind: "page", role: "persistent" }
```

→ **「让它进清单就能保活」这条路不通：它本来就在清单里。**

### 3.3 那为什么还是会死

档案描述的是**界面结构**，不是内容的生命周期。切会话时宿主按档案重建结构，页面对象保留、清单条目保留，但承载 iframe 的组件被重新挂载，ComfyUI 前端随之重建——与页面是否在清单里无关。

`role: "persistent"` 管的是它在站点导航里的存活语义，不是「内容不被重挂」。

## 4. 为什么 App 侧治不了 `[代码]`

宿主契约（`APPS.md`）确认：

- 宿主负责装载并在「停止、失败或卸载」时回收注册，没有任何 App 可调用的续租/常驻接口。
- 自定义页面只保留最近 4 个，「被淘汰、删除或切换工作区时仍会卸载，不能把这项保留策略当作持久化保证」。
- surface session 是装载时铸造的短期票据，runtime 代理 URL「含短期受限凭证，不可持久化」。
- 进程级 `idleTimeoutMs=0` 默认不回收 App 进程（与第 1 节的进程账本一致）。

另有一条既有结论仍然成立：切会话触发 layout scope restore，重建时用 `pruneSurfacesNotInPages` 把不在 pages 清单里的 surface 整页删除（见 `排查-宿主1.1.24-大页保活机制-20261018.md` §6）。这条能解释「链式重载」：重建后若该页仍未进 profile 清单，下一轮 restore 再剪一次。

## 6. 处方

### 4.1 使用侧

- 独立窗口也挡不住销毁，别指望「换个载体就稳」——这一条是把先前草稿的错误结论改回来：**载体差异尚未证实**，不要据此做决策。
- 真要连续作业不受宿主影响，把 ComfyUI 官方前端直接在浏览器里开到 `http://127.0.0.1:8188`。它不经过宿主，宿主怎么回收都碰不到它；代价是无法使用 Hana 侧的能力（桥、副驾驶、验收回执）。
- 会话黑板里的卡页同样随用随开，别挂长任务。

### 4.2 App 侧可做的两件减害（不动宿主）

1. **缩短重建后的真空窗**：`SHELL_ALIVE_MS=5000` 内画布 op 全走扩展腿，`runtimeId` 变化又触发整页 `location.reload()`，叠加起来让重建后头十几秒体验像死。
2. **重建后自动恢复现场**：重建即回到上次的活动画布/tab，避免「活过来了但一片空」。

## 7. 下一步：补一条「载体自报」再复现一次

现在缺的只有一个字段：**这一刻的壳页是独立窗口还是页内卡**。补法很小：`pagehide` / `beforeunload` 与心跳记录里带上 `window.hanaAppWindow` 是否存在、窗口内外尺寸，以及 App 侧 `windows.onEvent('closed')` 的到达时刻。

复现一次「切到别处 → 切回」，就能三分定性：

1. App 收到 `closed` + 页面 `pagehide` 同时刻 → **窗口被宿主关掉**。
2. 没收到 `closed`、但页面 `pagehide` 后又 boot → **窗口还在，内容被重新装载**。
3. 两者都没有 → 页面没死，问题在连接/渲染（另查）。

## 8. 数据缺口（不掩盖）

- 宿主日志对 `ui-sessions` / `plugin-surface` / `workspace` **零命中**，402 次重建无法逐个对齐到宿主的具体动作，只能按载体相关性归因。要定到「哪一行代码触发卸载」，需要在宿主侧加日志，不是 App 能做的。
- 探针行里没有实例 ID / pid，实例切分靠 `n` 序列推断，多实例交错段可能有 ±个位数误差（已用多计数器算法降低）。
- 近 7 天 `<5min` 比例从 48.7% 降到 27%，与插件版本变化同期，无法完全排除版本因素。
