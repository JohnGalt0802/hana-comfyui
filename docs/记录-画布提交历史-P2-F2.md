## 二、边界处理说明（验收问项）

**① 空 groups 画布**：`blocks` 为**空角色兜底**——所有节点走角色分类，产出如 `[{name:"加载",source:"role",nodeIds:[…]},…]`；只有「groups 为空 **且** 节点也为空」时才是 `[]`。不是 null（null 保留给「graph 非对象 / 计算失败」的降级态，两种情况语义不同：`[]`=算过了、没有组块；null=没算成/没得算）。
**② 空节点图（nodes 为空）**：`graphBlocks` 返回 `[]`（合法零块）。但注意：提交通道上有 `hasGraph` 拦截（P1-C2 口径），空节点图**根本不会上报**，所以实战中 `[]` 只会出现在直连 Python 端点的请求里；落盘后快照 `blocks:[]`、索引行 `blocks:[]`（空摘要列表）。
**③ 旧快照兼容**：落盘/索引层面「无字段」即 JSON 的 null 语义；`list_commits` 原样返回旧条目（不缺字段的行不补 `blocks:null` 键），消费方 `.get("blocks")` 得 null，不报错（有专门用例覆盖）。

**blocks 大小**：每块一个 `{name, source, nodeIds}`，nodeIds 是纯数字数组。实测（本机 node 跑出来的数）：

| 规模 | blocks 体积 |
|---|---|
| 50 节点 / 4 组（id 2~3 位数） | **约 230–280 字节**（JSON 序列化后） |
| 对照：同规模 graph 本体（50 节点含 pos/type/widgets） | 约 5 KB |

即 **blocks 使快照膨胀约 5%（+~250B / ~5KB）**；50 节点工作流完整快照本就在几十 KB 量级，距离 14 MiB 上限有 3 个数量级余量。索引行摘要侧更小：每块仅 `{"name":"…","nodeCount":12}`，4 块约 80–120 字节。节点数上千、块数上百的极端图，blocks 也就 2–3 KB（id 数字变长 + 块名），不构成体积风险。
