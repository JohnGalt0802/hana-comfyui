# 调研：画布提交历史 — 捕获点

> 范围：仅调研取证，未改任何代码、未碰运行态。结论区分「代码确证」与「推断」，无法确证处标注待验证。

## 结论先行（建议的捕获路径）

**主捕获：在前端常驻包装 `api.queuePrompt`（挂在 `hana_bridge` 扩展里，load 时安装一次，替代现在的「每调用临时猴补」）。**
理由：
- 它正好位于「真实提交发生的那一刻」，能同时拿到 `prompt_id`（POST `/prompt` 的返回）和被提交的序列化 prompt（`output`/`workflow`），与画布状态天然配对（见证据四）。
- 现有桥已是这个入口（`hana-bridge` 第 1546–1562 行），只是临时替换+还原；改成常驻只把生命周期从「每次调用」改为「扩展加载一次」，逻辑不变。
- 它比包装 `app.queuePrompt` 更贴近「实际提交」：前者在队列真正落库时才被调用，避免 `processingQueue` 早期返回那次抓不到 id 的坑。

**辅捕获：保留中继 `/queue` 差集兜底**（已在桥第 244 行实现），专门覆盖「队列在跑、点击被并入内存队列、本次 `api.queuePrompt` 未即时产生新 id」的场景。
**丰富层：中继 `/ws` 的 `execution_start`/`execution_success` 作状态与时间轴**（它广播所有来源，但事件里没有画布图，只作节点状态/计时，不作快照来源）。

## 四条证据

### 1. 前端「运行」按钮的实际入口（代码确证）
调用链（全部在压缩 bundle 中实锤）：
- 按钮 `onClick` → 本地 `async queuePrompt(t)` → `await te.execute('Comfy.QueuePrompt'|'Comfy.QueuePromptFront', {metadata:{subscribe_to_run:!1,...}})`（`shiftKey` 走 Front）。
  文件：`ComfyQueueButton-CMg2PbJt.js`（`queuePrompt=async t=>{... await te.execute(n,...)}`；模板 `onClick:queuePrompt`）。
- 命令注册：`{id:'Comfy.QueuePrompt', function:async e=>{... await Q.queuePrompt(0, t, {intent:e})}}`（`Q`=app 实例）。
  文件：`GraphView-CDjciZjE.js` @629362。
- 真正的 `app.queuePrompt`：`async queuePrompt(e,t=1,n={}){...}`。键盘 `Ctrl+Enter`/`Ctrl+Shift+Enter` 也经 `keybindingService-B17SjPBL.js` 映射到同一命令 `Comfy.QueuePrompt`。
  文件：`settingStore-X9ZV_dAu.js` @1872831。
- 末端 `api.queuePrompt(e,t,n)`：组装 `{client_id, prompt, extra_pnginfo:{workflow}}` 并 `POST /prompt`，返回 `{prompt_id, number, node_errors}`。
  文件：`api-ftklx9tM.js` @76864。

**链路**：按钮点击 → 命令 `Comfy.QueuePrompt` → `app.queuePrompt` → 序列化 `rootGraph` → `api.queuePrompt` → `POST /prompt` → 返回 `prompt_id`。
**要点**：按钮不直接调 `api.queuePrompt`；所有前端来源（按钮/Ctrl+Enter/app 模式）都经 `app.queuePrompt`。键盘映射同命令（确证）。

### 2. 中继 /ws 事件字段（代码确证）
来源：`comfy-relay.mjs` `handleBackendEvent`（第 1809–1910 行）。已处理事件类型及所带字段（`msg.data` 解包为 `d`）：
- `execution_start`：`d.prompt_id`（string）→ 落 `state=running`、`startedAt=Date.now()`。
- `execution_cached`：`d.prompt_id`、`d.nodes`（数组）→ `cached=nodes.length`。
- `executing`：`d.prompt_id`、`d.node`（null=主体结束）。
- `progress`：`d.prompt_id`、`d.value`、`d.max`、`d.node`。
- `executed`：`d.prompt_id`、`d.output`（`{filename,subfolder,type}`）。
- `execution_error`：`d.prompt_id`、`d.node_id`、`d.exception_type`、`d.exception_message`。
- `execution_interrupted`/`execution_success`：`d.prompt_id`。
- `status`：`d.status.exec_info.queue_remaining`。

**关键事实**：
- `prompt_id` 在所有执行类事件中都存在（确证）。
- **没有 timestamp 字段**：`startedAt` 是中继进程收到事件时 `Date.now()` 自己盖的，不是后端原发时间。
- **没有 client_id / 来源标识**：事件 `data` 里不含来源；中继订阅用的是 `config.clientId`（`comfyui-relay`，第 1926 行），但事件体本身不回带。
- **没有 `prompt_update` 事件类型**（grep 全文件无此 case）。
- 事件里**不含画布图/序列化 prompt**，只有 prompt_id + 进度/输出元信息。

### 3. 能否常驻捕获「任何来源提交」（推断 + 代码依据）
- **可行性（高）**：`app.queuePrompt`/`api.queuePrompt` 是稳定公开方法；在扩展 `load` 时一次性包装是 ComfyUI 标准扩展模式。
- **不被前端重覆盖（代码确证）**：对全部前端 bundle 搜 `\.queuePrompt\s*=` 重赋值，结果**无匹配**——前端不会在运行时重写这两个方法，常驻包装不会被冲掉。
- **是否干扰原生流程**：只读包装（记录后 `return await orig(...)`）非侵入；正常返回 `prompt_id`，原生行为不变。
- **唯一漏抓**：`app.queuePrompt` 在 `processingQueue===true` 时**早期返回 `false`、不调 `api.queuePrompt`**（代码确证 settingStore @1872900 附近 `if(this.processingQueue)return!1`）。此情形需 `/queue` 差集兜底（桥已有）。
- **来源边界（推断）**：前端包装只覆盖「经 `app.queuePrompt` 的前端提交」；中继自身以 `config.clientId` 直连 `POST /prompt`（comfy-relay.mjs 第 2527 行）**不经过前端 `app.queuePrompt`**，故前端包装抓不到中继源。要覆盖「含中继/API 的任意来源」，需在中继层用 `/ws`+`/queue`（后端 `execution_start` 对所有 `/ws` 客户端广播，属 **推断**，取决于 ComfyUI 后端广播行为，本批文件未含后端代码）。

### 4. 提交与画布状态的配对（代码确证 + 待验证）
- `app.queuePrompt` 内 `x = await this.graphToPrompt(this.rootGraph)`（确证 settingStore @1872900 后）在**提交时刻**对当前 `rootGraph` 序列化，随后 `api.queuePrompt(e, x, ...)` POST 出去。`x` 是那一刻新产出的对象，之后用户再编辑不会反向改写它 → **单次提交的 prompt 固定为点击时画布状态**（确证）。
- **「队列在跑、这次点击被并入内存队列」的例外（待验证/有条件）**：`graphToPrompt` 实际执行发生在 `for(;this.queueItems.length;)` 出队循环里；若前一次还在跑、本次点击只 `push` 队列项并 `return false`，则序列化延到上次结束、本次出队时才跑。若用户在此间隙改了画布，**实际提交的序列化 = 出队时状态，而非点击时状态**。
  - 含义：对「队列在跑」场景，「执行开始抓快照」/「`api.queuePrompt` 被调用时抓」反而比「点击瞬间抓」更贴近后端真正运行的图；「点击瞬间抓」抓到的是用户意图，可能已过期。
  - 故**首选在 `api.queuePrompt` 包装内抓**：此时已拿到真实 `prompt_id` 与真实序列化 prompt，配对最准；并发改图场景下它就是后端实际运行态。
- `execution_start` 的 `startedAt` 是中继收到事件的时间，晚于提交，且其事件不带图，**不宜作为快照来源**。

## 未决项
- 中继 `/ws` 是否确能收到「前端提交」的 `execution_start`（取决于 ComfyUI 后端是否向所有 `/ws` 客户端广播执行事件）——**本批文件未含后端 `PromptServer` 代码，标记为推断，待查后端源码确认**。
- 「队列在跑 + 点击期间改图」场景下，提交 prompt 与点击时刻的偏离幅度，需实跑一次（连续两次点运行、中间改一个参数）验证，标记为**待验证**。
- 后端是否提供按 `prompt_id` 取回已提交 prompt 的 GET 接口（用于中继侧补图）——`/history` 只回输出，未见 GET `/prompt/<id>`，**待查后端**。
- 常驻包装 `app.queuePrompt` 与「其他扩展也可能包装同方法」的顺序/叠加影响——未做多扩展共存实测，标记**待验证**。
