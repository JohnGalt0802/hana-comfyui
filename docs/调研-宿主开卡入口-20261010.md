## 2. deliver_cards 与 show_card 的完整 schema：能否承载一张 App 卡（plugin-webview / plugin-surface binding，带 pluginId+cardId+channel）？

**结论：都不能。** 两者只能承载「模板卡 / interactive-artifact / chalkboard 上的展示卡」，schema 里没有 pluginId / cardId / channel / binding 之类的字段，`fO()`（卡片内容 schema）也不含插件卡绑定；承载 App（整页）卡不是这两者的设计意图。

### show_card（server bundle）
```
offset 7534089  name:"show_card", label:"Interactive Card",
  parameters: Sr({
    title, code, template, file:{type,fileId|path}, state, assets
  })
```
- 描述（7534150 区域）：`exactly one source: code, installed template, file/directory package`——即「HTML/SVG/交互式页面」或「已校验的 reference 模板（recipe-name/assets/<file>.card.html）」。这是模板卡/交互卡，不是 App 声明卡。
- 没有 pluginId / cardId / channel / binding 任何字段。

### deliver_cards（server bundle）
```
offset 7569440  uTn({...}) => name:"deliver_cards", label:"Deliver Cards",
  parameters: Sr({
    action,                       // 'new_page' | 'append'
    target:{ clientKind, deviceId },   // 必填，标识落到哪个客户端/设备
    title, cards, card, layoutPreset
  })
  description:"Put cards on a chalkboard: new_page (1-6) or append (one, right only)..."
```
- `execute`（`offset 7569900` 区域）只分发两种动作：
  - `action:"append"` → `TPt(a,{target,card})` 把一张卡追加到已存在 chalkboard 页；
  - `action:"new_page"` → `kPt(a,{target,title,cards,layoutPreset})` 新建一页（1–6 张卡）。
- `cards/card` 内容由 `fO()` 决定：全文件 grep `function fO`/`const fO` 无独立定义命中，但其被 `update_card_data`（offset 7553434）与 `deliver_cards` 复用，语义是「展示卡数据对象（plain object）」，不含插件绑定。
- **无 pluginId / cardId / channel / binding 字段** => 无法承载 App 卡。

### update_card_data（server bundle，旁证）
```
offset 7553434  Wkn({...}) => name:"update_card_data",
  parameters: Sr({ cardEntityId, data, key, value })
```
- 仅按 `cardEntityId` 写 host-data；「卡可还不存在」（描述原文），与 App 卡打开无关。

置信度：代码推断（高）——基于显式 parameter 结构与 execute 分支；实测事实（show_card 只能产模板卡、deliver_cards 只产 chalkboard 展示卡）为已知背景，不重验。

## 4. POST /api/apps/:id/ui-actions/invoke 的真实语义

**结论：它只是「调用 App（v2 plugin）的一个工具」；不打开任何 surface / 卡。** body 校验要求 `{ toolName, args?, context:{sessionPath,messageId?}, inputStatusId?, sessionId?, selectionText? }`，流程为：解析 pluginId → 校验 plugin 状态为 `loaded` → 校验 `r.toolBelongsToPlugin(u, h)` → 取 `n.get(h)`（工具注册）→ `T = _.execute; T(C)` 执行该 tool。全程没有出现「open surface / reveal card / create card」逻辑。

证据（server bundle）：
```
offset 5640674  e.post("/apps/:pluginId/ui-actions/invoke", async (l)=>{
  ... body 必须为 { toolName:string, args?:object, context:{sessionPath,messageId:string|null} }
  const v = r.list().find(U=>U.id===u);           // 找 v2 plugin
  if (v.state !== "loaded") → 409 PLUGIN_V2_NOT_LOADED
  if (!r.toolBelongsToPlugin(u,h)) → 404 PLUGIN_V2_TOOL_NOT_OWNED
  const _ = n.get(h); if(!_) → 404 PLUGIN_V2_TOOL_NOT_REGISTERED
  const T = _.execute; ... await T(C)             // 仅执行 tool
})
```
- 另有宿主侧封装 `offset 9366514`：`request('/api/apps/${appId}/ui-actions/invoke', {toolName, args, context})`，并先校验 `l.tools.some(d=>d.name===o.toolName)`，否则抛 `APP_ENVIRONMENT_UI_ACTION_DISABLED`——再次印证「这是触发一个 toolName，而非开卡」。
- `contributes.ui` 的解析（`offset 5275083` 的 `TZr`/`Den`/`VD` 等）只负责**校验贡献条目字段**，不在此端点触发任何 surface 打开。

置信度：代码推断（高）。

## 5. contributes.ui（homeActions 等，条目含 id/title/icon/surface/toolName/args）的宿主语义

**结论（局部，需存疑）：在本机提供的三份代码面（server bundle、renderer 分包、app.asar）里，未能定位到 `homeActions` 字段级解析器与 `surface` 字段去向的代码。** 现有可验证证据只覆盖「surface 是一组 iframe 槽位集合」这一层，来自于 renderer 的能力注册表 `allowedSlots`，而非「homeActions.surface 打开一个 surface」。因此本问不做"已证实"断言，仅汇报能找到的与不能找到的。

### 能找到的（renderer 分包 `PlanModeButton-CxtrW7Pn.js`）
能力注册表里每个 UI 能力声明自己的 `allowedSlots`，取值为一组 iframe 槽位：
```
{name:EXTERNAL_OPEN, allowedSlots:["page","widget","settings","function-panel"], requiresGrant:true, ...}
{name:RESOURCE_OPEN, allowedSlots:["page","widget","card","settings","function-panel"], ...}
{name:RESOURCE_SAVE_FILE, allowedSlots:["card","preview"], ...}
{name:RESOURCE_PICK, allowedSlots:["page","widget","card","settings","function-panel"], ...}
```
- 即宿主公认的 surface 槽位集合为：`page | widget | card | settings | function-panel | preview`。
- 这条与已采信事实一致：渲染层对 `hana.cards.open` 能力的 `allowedSlots = ["card","function-panel","settings"]`——即「该能力只对 App 的 card / function-panel / settings iframe surface 授权」，而不是「调用它就去打开一个 surface」。

### 找不到的（诚实汇报）
- 全文件 grep 下列关键词，在 server bundle / app.asar / 全部 renderer assets 中**均 0 命中**：
  `homeActions`、`home-action`、`contributes.ui`（作为字符串）、`openSurface`、`openPage`、`open_page`、`surface:`、`"surface"`、`appHomeActions`、`HomeAction`、`plugin-webview`、`plugin-surface`。
- 这意味着：要么 `homeActions` 的字段解析在另一份未被纳入本次检索的代码面（例如不同构建/未解包的 asar 内嵌 chunk、或版本漂移），要么本版本术语不同。依据"找不到不编"原则，不臆造其行为。

### 可由已知事实反推（不重验，标注为推断）
- 已采信事实：App 原生窗口（`ctx.windows.create`）调用 `hana.cards.open` 被拒（`APP_WINDOW_UI_OPERATION_UNAVAILABLE`）；该能力只对「card/function-panel/settings」surface 授权；M0 记录「已安装 app 的卡片不能由 Agent 程序化打开」。
- 由此可推断：`hana.cards.open` 的语义是「open/reveal **App 自己声明**的卡」，且只能在 App 页面内的合法 surface 上由卡内页面自身调用——它没有暴露成可跨 surface 程序化触发的宿主入口。这与本问 `surface` 字段作为「槽位授权集合」的解读互相印证。

置信度：代码推断（中/局部）+ 已知事实采信；`homeActions` 字段解析器未定位，置信度「未找到（代码）」。
