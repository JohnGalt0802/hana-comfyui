# hui 宿主需求清单 — issue 草案（2026-10-10）

> **状态：草案，未发布。** 本文只汇总「卡在宿主侧、本 App 无法自解」的需求，供整理成 issue 递交；发不发、何时发、发到哪个渠道由用户决定。
> **范围**：四条（App 窗防节流 / 整页卡程序化打开 / 子代理会话投递 / 探活唤醒哨兵）。第四条低优先，可并入第一条。
> **成色口径**：每条证据标注「实测」或「代码推断」；不提升成色。文末列「已试路径清单」，**已证伪的路径标注为「已试·证伪」，不写作「未试」**。
> **宿主版本基线**：1.0.11-beta。

## 需求一 · App 窗口创建无防节流参数

### 现象
App 通过 `ctx.windows.create()` 自开的原生窗口，**没有任何保活 / 防节流选项可传**。该窗口一旦被切走、最小化或被遮挡，页面进入 hidden 态；约 5 分钟后触发 Chromium 88+ intensive throttling（定时器降为约 1 次/分钟），桥的活性判据随之失真 —— 页面还在、偶尔上报，但桥调用（现抓 / 写 op）全部超时，呈「半死」态。人切回即复活（节流解除）。

### 对 agent 的影响
agent 拿不到可用的画布 op：`comfyui` 工具的写 / 读现抓全线超时，只能开窗拉活或停手；用户切走工作区去干别的事时，agent 对 hui 的连续操作会静默中断，且**无任何提示**（见需求四）。

### 期望宿主提供什么
`ctx.windows.create()` 增加等效 `backgroundThrottling: false` 的参数（或提供「后台保活 / 亮出来」原语），使 App 窗在最小化 / 遮挡 / 隐藏下也保持 visible 语义、不进入节流。

### 最小复现
1. 由 App 调 `ctx.windows.create()` 开一个工作区窗口，确认桥双绿；
2. 将该窗口切走 / 最小化；
3. 约 5 分钟后探活 / 现抓 / 写 op —— 全部超时（桥「半死」）；
4. 切回窗口，数十秒内桥复活。

### 证据出处
- **代码推断（asar 实现层实读）**：App 窗创建块的 `webPreferences` **无 `backgroundThrottling`**（默认节流）；对照 —— **主窗口**与 **browser-viewer** 两处已有 `backgroundThrottling:!1`（不节流），**App 窗不在其列**。（`docs/hui存活态-机理与方案-20261009.md` §6 结论一）
- **代码推断（契约面）**：`app/sdk/app-contract/windows.d.ts` 的 `create()` 参数仅为 `entry / title / bounds / parentWindowId / chrome / data`（另含 `callToken`），**无任何防节流 / 保活字段**；1.0.11-beta 更新中该文件**逐字未变**。（同 §6 结论一、本文档读取 `windows.d.ts` 核对）
- **实测（真机时间线）**：2026-10-09 22:41 起失联（切走后约 5 分钟），探针双败、现抓全超时；22:49 用户回到页面，22:50 探测复活（rev=7）。（同 §1「死法 2」）
- **实测（后台标签页）**：默认浏览器标签置于后台，约 4–5 分钟起不再回传桥调用（探活 504）；换专用实例 + 抗节流 flags 后全程稳定。（`docs/踩坑记录.md` §30）

### 备注（现状与边界，勿省略）
- **页面内心跳已为「工作区页」形态提供自足兜底**：10 秒心跳（timer + 极小 POST）实测在页面隐藏 9m35s、主窗最小化 2m+ 下均「零断、vis 恒 visible」（`hui存活态-机理与方案-20261009.md` §8.2）。故本条对**工作区卡页**的紧迫度下降。
- 但**原生窗口形态**的保活不在该心跳覆盖内（心跳落在 App 工作区页 `app/ui/workspace.js`；页面若被卸载则心跳随之消失，属另一死法）。因此**宿主侧不节流参数仍是独立窗 / 其它形态的正解**，本条继续成立。
- 生效路径优先级：**窗口保活（本条）优先，卡挂载保活其次**；两者都不行才落「数据不死 + 唤醒」兜底（§3-A/§3-B）。

## 需求二 · 整页卡程序化打开无入口

### 现象
宿主不提供任何 **agent 可调**的「打开本 App 声明的整页卡」入口。agent 无法把宿主主界面里的「ComfyUI 工作区」整页卡（App 声明的 card）程序化拉起来。**三条路径全部试过、全部证伪**（详见文末「已试路径清单」）。

### 对 agent 的影响
若用户未手动开着工作区卡，agent 就没有「让宿主页出现」的手段 —— 需要前端画布执行 / 人机共驾时，只能退化为拉独立原生窗，或要求用户手动开卡。**agent 无法独立完成「把工作区卡摆到用户面前」这一步**。

### 期望宿主提供什么
给 App 后端 / agent 一个**正规**的「打开本 App 声明卡」入口。二选一即可：
- 一条 agent / App 后端可调的「开本 App 声明卡」RPC 或端点；
- 或允许 App 工具回执携带**可直接挂载的受信 card surface**（使其不经 `hana.cards.open` 的 surface 守卫也能被宿主挂载）。

### 最小复现
任取下列三条路径之一，按「已试路径清单」操作，观察报错码（`APP_WINDOW_UI_OPERATION_UNAVAILABLE` / `APP_CARD_SURFACE_NOT_READY`）或「端点不存在」。

### 证据出处
- **实测**：三条路径全证伪 —— ① 原生窗调 `hana.cards.open` → `APP_WINDOW_UI_OPERATION_UNAVAILABLE`；② `details.card` 流内卡不走可信握手 → `APP_CARD_SURFACE_NOT_READY`（重试约 10s 仍不过）；③ agent 可调的开卡 RPC / 端点不存在。（`docs/踩坑记录.md` §38；`docs/复盘-agent操作hui-卡点-20261010.md` F2/K37）
- **代码推断（高）**：内置工具花名册（`Dlt` 数组）为显式枚举 + 强制分类校验，除已列出者外无任何「卡 / 打开页 / 工作台」相关工具；`show_card` / `deliver_cards` 的 schema 无 `pluginId` / `cardId` / `channel` / `binding` 字段，无法承载 App 卡；`/api/apps*` 全部写入类端点（`ui-actions/invoke` 只调 tool、`cards/events/emit` 只向**已存在**卡发事件）均**不开卡**。（`docs/调研-宿主开卡入口-20261010.md` Q1–Q4）
- **实测（代码实锤）**：`hana.cards.open` 注册时 `allowedSlots = ["card","function-panel","settings"]`，handler 先经 `gs` 守卫（要求 surface 已挂载 + 已完成可信握手）；原生窗不属这三个 slot 之一 → 能力根本不向其暴露。（`docs/调研-App开卡能力-20261010.md` Q4）
- **旁证（宿主产品定位）**：官方能力词说明「允许此 App 创建和控制**自己拥有的**独立窗口」——App 窗 = App 自建窗；「拆窗」是黑板卡体系语言，与 App 整页卡无涉。（`hui存活态-机理与方案-20261009.md` §7）

## 需求三 · 子代理会话的宿主任务回执（next-step）永不送达

### 现象
宿主 next-step 的**可靠投递只写桌面会话**。由**子代理会话**发起的宿主任务，被 `_assertActiveDesktopSessionPath` 静默拒绝；系统每 30s 重试，但**永不送达**。返回值会标注该情况，需 agent 主动 `query` / `result` 取回执。

### 对 agent 的影响
从子代理会话提交宿主任务后**没有自动回执**，agent 易把「无回执」误判为失败 / 卡住；须改为轮询式主动取，链路可预期性下降。

### 期望宿主提供什么
二选一：
- 子代理会话（或**显式声明的投递目标**）也能收到 next-step 回执；
- 或提供**明确的「不可投递」错误码**（而非静默拒绝 + 无限重试），使 agent 可据此决定改走主动查询。

### 最小复现
1. 在**子代理会话**内发起一个宿主任务（如 `submit`）；
2. 观察 next-step 投递：返回被静默拒绝、每 30s 重试、桌面会话侧始终收不到该回执。

### 证据出处
- **实测（一线观测）**：子代理会话发起的 submit 宿主任务 `_assertActiveDesktopSessionPath` 静默拒绝、每 30s 重试但永不送达；返回值会标注，需 `query` / `result` 主动取。（`docs/复盘-操作链路摩擦点-20261010.md` F6-1，严重度**高**）
- **代码推断**：投递谓词层面 `_assertActiveDesktopSessionPath` 即「可靠投递只认桌面会话路径」的判据。（同 F6-1 证据栏；`docs/复盘-agent操作hui-卡点-20261010.md` D1）
- **关联**：无 `callToken` 的调用同样降级为仅内存跟踪、不投递，需主动 query（F6-2，严重度中）。

## 需求四 · 探活 + 唤醒哨兵未落地（低优先，可并入需求一）

### 现象
桥失联时无自动告知、无自动拉活。用户与 agent 对「画布桥：真死 / 节流中半死 / 在线」无可见状态，也拿不到「最后活跃时间」。

### 对 agent 的影响
失联是「静默」的：agent 只能在操作超时后才发现，且无法区分「真死」与「慢档（节流中）」，处置口径也不一致（一律报错）。

### 期望宿主提供什么
- 失联**自动告知**（含最后活跃时间）；
- 授权下**自动拉活**（拉窗 / 重载），遵循「先说再动」；
- 桥态**可见**（在线 / 节流中 / 失联）与**分级**（真死 vs 慢档给不同处置）。

### 最小复现
制造失联（切走 / 最小化约 5 分钟）后，观察是否出现任何告知或自动拉活 —— 现状：无。

### 证据出处
- **方案稿**：唤醒与告知列为运维层兜底（`hui存活态-机理与方案-20261009.md` §3-C、§7 待办 B「兜底探活+唤醒未排，等用户点单」）。
- **复盘**：F4「探活+唤醒哨兵未落地」（`复盘-agent操作hui-卡点-20261010.md` F4/K38）。
- **注**：本条的「失联自动告知/拉活」为**宿主侧 / 运维层**需求；页面自足心跳（§8）只保活、不负责告知与拉活，二者不互相替代。

## 已试路径清单

> 原则：已试且证伪的路径，**标注为「已试·证伪」**，不写作「未试」。

### 需求二（整页卡程序化打开）—— 三条路径（全部已试·全部证伪）

| # | 路径 | 做法 | 结果 |
|---|---|---|---|
| 1 | App 原生窗内调 `hana.cards.open` | 在 `ctx.windows.create` 开的原生窗里调用该能力 | **已试·证伪** —— `APP_WINDOW_UI_OPERATION_UNAVAILABLE`（原生窗不暴露该能力） |
| 2 | App 工具回执带 `details.card`（流内卡） | 工具返回 `details.card`（`pluginId`+`cardId`+`route`…）由宿主在聊天流渲染，卡内调 `hana.cards.open` | **已试·证伪** —— 卡能渲染并执行脚本，但 `hana.cards.open` 报 `APP_CARD_SURFACE_NOT_READY`（「available after this App surface has completed its trusted handshake」，重试约 10s 仍不过）——流内卡不走可信握手 |
| 3 | 直接找 agent 可调的开卡 RPC / 端点 | 在宿主内置工具面与 `/api/apps*` 写入类端点中找开卡入口 | **已试·证伪** —— 不存在：内置工具花名册无开卡工具；`show_card`/`deliver_cards` 不承载 App 卡；全部 `/api/apps*` 写入类端点均不开卡 |

边界：`hana.cards.open` 仅授权 **card / function-panel / settings iframe surface**（须已完成可信握手），agent 工具面与原生窗均不在其列。

### 需求一（App 窗防节流）—— 已核路径
- 契约面核查 `app/sdk/app-contract/windows.d.ts`（1.0.11-beta）的 `create()` 参数面：**无任何防节流 / 保活字段**——已试·证伪（宿主未开放）。
- 实现层核查 asar：App 窗 `webPreferences` 无 `backgroundThrottling`（默认节流），主窗 / browser-viewer 有 —— 已试·证伪（App 窗不在其列）。
- 自足兜底：页面 10s 心跳（timer + 极小 POST）——**已试·有效**（工作区页形态保活成立，见需求一备注）。
