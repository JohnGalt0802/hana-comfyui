## 〇、一句话结论

**探针没坏，此刻还在跑。** 不保活的真因是**形态**：探针分两条命——

| | 页内心跳（自救） | 踹探针（外援） |
|---|---|---|
| 机制 | 页面自己 `setInterval` 每 10s 打点 | 主进程每 10s `windows.request()` 踹，页面同步应答 |
| 实现 | `app/ui/workspace.js` `setupThrottleProbe` | `app/index.js` `pokeOnce` + `workspace.js` `setupKeepalivePokeListener` |
| 生效条件 | 页面**活着**才能跑 | **仅原生窗口态**（需 `window.hanaAppWindow`） |
| 抗冻结 | ❌ 页面被冻结/卸载 → timer 停 → 断 | ✅ 主进程不受页面节流，可穿透 |

**现在工作区是卡态，没有"外援"通道，只剩页内心跳自救** → 页面一旦被宿主冻结/卸载就断。

`sdk/app-contract/windows.d.ts`（1.0.16-beta，宿主内置）：

```ts
export interface AppWindows {
    /** Sends an opaque JSON request to this window's UI and waits for its opaque JSON response. */

- `request` / `handleMessages` / `onEvent` 均挂在 **AppWindows** 域下 → **只有 App 原生窗口**才有这条通道

- 无 `backgroundThrottling` 类保活参数（与 10-09 调研一致，宿主仍未开放）

  ...
```
→ **卡态下 `window.hanaAppWindow` 不存在，踹探针监听器根本不注册**。外援不存在。

## 三、推断与待验证 `[推断]`

**T1. 卡态 = 无外援，只剩自救。** 工作区嵌在宿主主界面的卡态时，页面被冻结/卸载无人踹醒 → 页内心跳跟着停 → 断档。这解释了当前"不保活"。
- 验证方法：开一个**原生窗口态**工作区，观察 poke 文件是否恢复、切走后是否仍 1~2ms 应答。

**T2. 宿主更新（10-11 08:59 升至 1.0.16-beta）可能加剧了冻结。** 时间强关联：心跳 08:59 前满速，**08:59 起断 566 分钟**。
- 但 10-10 也已有断档 → 宿主更新**不是唯一**原因，可能只是加深了（iframe 生命周期/节流策略变化）。
- 验证方法：对比更新前后同一操作（切走 10 分钟）的 `vis` 表现。

**T3. 页内心跳的定位偏差。** 文档《hui存活态-机理与方案》§8 曾结论"探针即保活器"——该结论建立在 10-10 当天单点观察上；落盘数据显示它**只能证明"页面活着时的节流程度"，无法阻止冻结**。探针是**测量器**，不是**保活器**（能保活的只有外援）。
