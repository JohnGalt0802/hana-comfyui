# hui 存活态 · 机理与方案（2026-10-09 深夜立题）

> 立题：用户点题——「如何维持 hui 的存活态？开 hui 就是要干活，必须维持画布一直存活。这是非常非常核心的问题！」
> 性质：机理分析 + 解法分层 + 宿主需求增补 + 验证计划；本文为立题稿，待验证与拍板。
> 证据来源：2026-10-09 22:42-22:50 真机实录（sess_0mv12qm1m 复制演示会话）、2026-09-27 持久态实录、Chrome 88+ Intensive Throttling 官方文档、Electron BrowserWindow 文档、`app/sdk/app-contract/windows.d.ts`。

## 0. 一句话

「画布开着」≠「桥在线」——承载画布的容器一旦被系统/浏览器判定为「不活跃」，桥（依赖前端定时器与回帖）随即失联；必须从**容器层保活**入手，辅以**数据不死**与**唤醒告知**，才能让「画布一直被 agent 用到」成为稳定事实。

## 1. 三种「死法」（机理钉死）

| # | 死法 | 触发 | 后果 | 现有证据 |
|---|---|---|---|---|
| 1 | **卡被卸载** | 用户切回 Hana 主页 / 切走工作区卡 → 卡片 `not_mounted`、iframe 销毁 | 页面没了，桥两腿全断；要重新挂载才能复活 | 9-27 实录：「你切回主页后它就休眠了」；「壳页死了 + 扩展死了」 |
| 2 | **页面被节流（半死）** | 页面/窗口 hidden（切走、最小化、被遮挡）→ **5 分钟后** Chrome 88+ intensive throttling：定时器降至 **1 次/分钟** | 页面还在、偶尔上报，但壳页 800ms 轮询与扩展腿 6s 回帖全部赶不上 → 「回帖超时 = 失联」；**人回来即复活（节流解除）** | 10-09 实录：22:41 起失联（切走后约 5 分钟），探针双败、现抓全超时；22:49 用户回到页面，22:50 探测复活（rev=7） |
| 3 | **进程/窗口关闭** | 用户手动关闭、宿主重启 | 归零（已知、可接受；按需重新拉起） | 《宿主侧需求》§二「用户手动关闭/重启归零**已知、可接受**」 |

关键机理链（死法 2 的完整闭环）：
```
用户切走 → 页面 hidden →（约 5 分钟内）timer 仍近全速
→ 5 分钟后 intensive：timer ≤1 次/分钟
→ 桥的活性判据失真：shellAlive（5s 内上报）不成立；6s 回帖超时
→ 「桥不可达」→ 写/现抓全不可用 → agent 只能开窗拉活或停手
→ 用户回来 → 页面 visible → 节流解除 → 桥复活
```
（Chrome 政策官方口径：hidden >5 分钟、静默 ≥30s、无 WebRTC、timer 链 ≥5 → 强化节流至每分钟最多 1 次；企业策略 `IntensiveWakeUpThrottlingEnabled` 可调但不可指望用户环境。）

## 2. 为什么一直被漏掉（诚实复盘）

- 它**不在 hui 的代码里**——在**宿主容器策略**里（卡挂载生命周期、窗口节流参数）。hui 自己的视角看到的是"桥不可达"，看不到"容器睡着了"。
- 两次冒头都没有升格：9-27「持久态」话头被当作当日 bug 顺手处理；10-08《宿主侧需求》里"保活"只列为"可选/待确认"。
- 直到 10-09 晚「复制演示」案（桥两腿双败 + 开窗拉活 + 用户质问"为什么新开窗"）——它才以系统性问题的面目完整暴露。

## 3. 解法（三层，从治本到兜底）

### A. 容器保活（治本，两笔宿主需求）

1. **窗口保活参数**：允许创建 `backgroundThrottling: false` 的工作区窗口。
   - Electron 官方语义：**"If backgroundThrottling is disabled, the visibility state will remain visible even if the window is minimized, occluded, or hidden."** ——最小化/遮挡/隐藏都不进入 hidden 态 → 从根上不触发节流。
   - 现状缺口：`app/sdk/app-contract/windows.d.ts` 的 `create()` 参数仅 `entry / title / bounds / parentWindowId / chrome / data`——**无任何保活参数**（宿主 owns window lifecycle）→ 需要宿主侧增补。
2. **卡挂载保活**：《宿主侧需求》§五已有条目（"主工作区卡隐藏挂载 / 预挂载（或等效的'后台保活 + 亮出来'原语）"）——**从"可选"升格为核心**：卡形态要做到"切走不卸载"或"隐藏挂载"，等效于窗口保活。

> 备注：窗口形态与卡形态应至少有一条"保活路"（推荐窗口保活优先，卡保活随后）。若两者都不行，则落入 B/C 层的"不死+唤醒"兜底。

### B. 数据不死（保险，不依赖前端活着）

- **状态真相下沉**：画布状态自动落盘 / 提交快照（包 C #24-26 范围）——前端睡死或重启后，一切可从档案恢复。
- **写路径多轨**：agent 的写操作尽量具备"文件层"通道（`source=file` / fs 路由已有）——前端不在线也能推进"非共驾"的活；用户回来刷新即见。
- 定位：**不替代保活**（共驾价值在"活着"），但保证"死了也不怕、不丢、可续"。

### C. 唤醒与告知（运维层）

- **探活哨兵**：app/中继侧定期 probe；判定"失联（含节流半死态）"→ ①告知用户（含最后活跃时间）；②授权下自动拉活（拉窗/重载），并遵"先说再动"纪律。
- **"开窗"升格**：从"权宜之计"升格为"保活/唤醒的正式形态"之一（与保活窗口合并考虑）。
- **桥态可见**：用户能直接看到「画布桥：在线 / 节流中 / 失联（最后活跃 X 分钟前）」——"肉眼开着≠在线"这件事必须可见。
- **桥态分级**：区分"真死"与"慢档"（节流中），对慢档给更宽容忍或触发唤醒，而非一律报错。

## 4. 验证计划（先出数据，再写需求）

**切走实验**（建议 30-40 分钟，一次做完）：
1. 开着 hui（记录形态：卡 / 窗口 / 浏览器），确认桥双绿；
2. 依次制造：①切到 Hana 主页 ②切到其他 app（窗口失焦）③最小化窗口 ④被全遮挡；
3. 每档记录：1 / 5 / 10 分钟后的探活结果（probe、现抓、回帖延迟）；
4. 复位（切回）后记录复活时间；
5. 产出：失联拐点（是否 5 分钟）、各形态差异、复活曲线、跨源 iframe 是否有更严待遇。
→ 结论直接决定：宿主需求怎么写（窗口参数 / 卡保活）、哨兵阈值怎么定。

## 6. 宿主 1.0.11-beta 能力核查（2026-10-10 凌晨补录）

背景：宿主要求核查「保活/形态相关能力」在 1.0.11-beta 更新中的变化。核查途径：安装壳 asar（实现层）+ `artifacts/server/1.0.11-beta.../skills2set/hana-app-creator/assets/sdk`（契约层，与本地技能包逐字节一致 F4F307CD769E3C6E）。

### 结论一（无变化）
- `app-contract/windows.d.ts` **逐字未变**：create 参数仍为 entry/title/bounds/parent/chrome/data，**无任何防节流/保活字段**。
- 实现层（asar）：App 窗创建块 `webPreferences` **无 `backgroundThrottling`**（默认节流）；对照：**主窗口**与 **browser-viewer** 两处已有 `backgroundThrottling:!1`（不节流）——**App 窗不在其列**。
- 即：**「App 窗防节流」在 1.0.11 没有开放**；既有慢档实测结论不变。

### 结论二（新增一大波「形态化」能力——方向变了，更值得跟）
1. **官方 detach/dock（分离/停靠）**：
   - manifest 卡贡献新增 `detached?: { route }` + `detachedDefaultSize`（App 可声明「分离形态」的入口与默认尺寸）；
   - `workspace` 命令新增 `card.detach` / `card.attach`（限 App-owned workspace）；
   - `chrome` 保留动作 `close/detach/dock/pin`（宿主拥有）；
   - surfaces/instances 侧均有 `detached` 标记字段。
2. **视图状态双态 + 恢复**：`APP_VIEW_STATE_KINDS: ['compact','detached']`（两个独立视图位各有 revision/state，界面位置可跨形态保持）；`_ui-app-view-recovery`（跨文档恢复控制器，防旧文档迟到写入）；`_ui-app-current-view`（视图归属握手）。
3. **受控 chrome（新契约 app-contract/chrome）**：App 可提交「标题/tabs/actions」纯数据描述，宿主管渲染、保留系统动作（close/detach/dock/pin）。
4. 其他：`contract-versions`（PRELOAD=1 / PROTOCOL=1 / DATA_EPOCH=2）；`workspace.d.ts` 仅 +1 行（card.open 增 `instanceKey`）。

### 意义与验证点
- **「保活」课题可能改道**：从「防节流保窗不死」转向「官方分离/停靠 + 状态恢复」（死了原地复活、形态自由）。分离窗为宿主自有形态，其生命周期/节流待遇待实测。
- **关键可行性问号**：hui 的「ComfyUI 工作区」整页卡（主工作区体系）**能否走官方 detach**——需进一步核实（契约层面 detach 当前落在 App-owned workspace 与卡 chrome 体系）。
- **对我们的已有交付**：自绘三键（2026-10-10 凌晨交付）为「能跑版」；未来可升级为声明式受控 chrome（宿主渲染 close/detach/dock/pin）。

## 8. 定稿：心跳保活（2026-10-10 凌晨·用户拍板）

**一句话**：宿主 hui 页的存活靠的不是宿主恩赐，而是**页面自己的心跳**——每 10 秒一次的定时器 + 一次极小 POST，主动打破 Chromium 的「静默」判定，深度节流永远不会落下。**探针即保活器。**

### 8.1 发现过程（诚实记录）
- 今夜之前：多次会话反复碰壁——「宿主 hui 掉线」；两次查验（宿主更新前后）均得出「独立大卡不带保活（宿主未开放此机制）」。
- 昨夜至今：为「测量是否被节流」加装了 5 秒心跳探针（timer + fetch 落盘）。
- **用户观察**：「自从加了探针，它就没再掉过。」
- 由此反转：**变量唯一——探针本身**。

### 8.2 实测数据（2026-10-10 02:11-02:25）
| 场景 | 时长 | 结果 |
|---|---|---|
| 页面在前台 | ~1 分钟 | n=1..12，5s/拍 |
| 切到聊天页（页面隐藏） | 9 分 35 秒 | 116 拍，零断，vis 恒 visible |
| 主窗最小化 | 2+ 分钟 | 累计 168 拍，零断，vis 仍 visible |

- 全部间隔 5000ms ±10ms；落盘文件 `~\.hanako\app-data\comfyui-hana\keepalive-probe\hui-page-pulse.jsonl`。
- 结论：**心跳让页面在所有「被藏起来」的场景下都保持满速运行**。

### 8.3 机制原理
- Chromium 88+ intensive throttling 前提：页面 hidden **且「静默」（≥30s 无活动、无 timer 链、无音视频/WebRTC）**；
- **每 10 秒的 timer + fetch** → 静默窗口永远 <30s → 节流条件永不满足 → 满速；
- 定稿参数：**10 秒**（用户拍板；≈360 次/小时，一次 timer + 一个极小 POST，开销可忽略）。

### 8.4 旧结论修正
- 「独立大卡不带保活（宿主没给）」——**宿主确实没给**（App 窗 `backgroundThrottling` 未开放，issue 仍成立、仍值得递）；
- 但**保活不必等宿主**：页面自我活动已是**自足的保活器**（零宿主改动、全自足）；
- 两条路并存：**心跳保活（已有）＝常态兜底；宿主窗口保活（issue）＝独立窗/其它形态的正解**。

### 8.5 产物清单
- 探针/心跳：`app/ui/workspace.js`（sendPing，间隔 10s）+ `app/index.js`（KEEPALIVE_PROBE 块 + `keepalive-probe-ping` 路由）；
- 数据落盘：`~\.hanako\app-data\comfyui-hana\keepalive-probe\`；
- 活口：本次为「页面内心跳」；若页面真的被卸载（not_mounted），心跳随之消失——该场景归 §1 死法 1（卡卸载），另按挂载保活/重挂方案处理。

## 8.6 校正（2026-10-12 晚，用户追问触发）

**用户问**：「之前的探针维持 hui 持久态现在不管用了吗？」

**校正定论**：不是「失效」，是**职责口径被 §8 写宽了**。准确说法：

- 页内心跳探针是 **「防节流」保活器**（打破 Chromium 静默判定，防 §1 死法 2「页面还在、被降频」）；
- 它 **不防「卸载」**（§1 死法 1，页面被宿主销毁）——这一点 §8.5「活口」当时已写明，但 §8.1/§8.4 那句「探针即保活器」表述过强，易误读为「能保一切」。

**2026-10-12 实测**：当日断档**全是归零型**（断档后 `n` 从 1 重来 = JS 上下文重建 = 页面被卸载），全部落在探针**设计上就不覆盖**的「死法 1」格。另：10-10 加探针当天 02:11 上线、02:47 即出现首次归零断档（n 429→1）——即卸载型它一直防不住。

**根因**：宿主对「看不见的卡」的策略是 unload + 按 saved state 重建（宿主契约 `card-guide/guide.md:180` 原文佐证），App 侧拦不住。详见 `排查-宿主大卡保活-根因定向-20261012.md`。

**表述修正（仅此一条为准）**：探针 = 「**防节流**保活器」；「维持持久态」需叠加「**防卸载**」（宿主挂载保活需求，或改窗口态）。§8.1/§8.4 中「探针即保活器」请按本条读。
