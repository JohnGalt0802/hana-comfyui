# 调研：画布提交历史 — 落盘通道

## 结论（推荐方案）
- **首选（零改动、可立即落地）**：快照以「点前缀扁平文件」直接落盘到工作流目录内，不建子目录——
  `user/default/workflows/.hist_<工作流名>_<rev>_<promptId前8>.json`，元数据（rev/promptId/时间/工作流名）直接编进文件名；
  可选每工作流一个 `.hist_<工作流名>_index.json` 记轻量索引（规避共享 index 的并发写冲突）。
- **更优（需中继极小改动）**：`user/default/workflows/.history/<工作流名>/<rev>-<promptId前8>.json` + `.history/index.json`，
  前提是中继 `writeFileAtomic` 增加「自动 mkdir 父目录」（见证据 2）。
- **点前缀（`.` 开头）关键**：实测目录下已存在 `.index.json`（未被 ComfyUI 当作工作流列出），说明点前缀文件不会被工作流列表污染；子目录 `.history/` 同理（ComfyUI 一般只列顶层 `.json`）。

## 证据 1 · 中继 fs 能力清单（代码确证）
来源：`runtime/comfy-relay.mjs` + 头注释（L15-17）、分发 L2950/L2959、处理函数 L2334/2357/2381/2389。
- `POST /_relay/fs/read` — L2334。入参 `{path, encoding?}`（encoding=`base64` 或默认 utf8，`maxBytes` 仅注释提及未强制）；返回 `{ok,size,encoding,text|base64}`。上限 `FS_READ_MAX_BYTES=8 MiB`（L77）。
- `POST /_relay/fs/write` — L2357。入参 `{path, text}`；返回 `{ok,path,size}`。上限 `FS_WRITE_MAX_BYTES=16 MiB`（L78）。内部调 `writeFileAtomic`（L2372，从 workflow-file.mjs 导入）。
- `POST /_relay/fs/stat` — L2381。入参 `{path}`；返回 `{ok,path,stat:{exists,isFile,isDirectory,size,mtimeMs}}`。
- `POST /_relay/upload` — L2389。把本机图片 POST 到 ComfyUI `/upload/image`，非通用 fs 操作。
- **无** `list/readdir`、`delete/rm`、`mkdir` 端点（分发处仅上述四者）。
- **路径限制**：中继层对 `path` 无白名单/沙箱——`handleFs*` 直接 `readFileSync/writeFileSync/safeStat`（任意绝对路径，仅受 `controlKey` 鉴权）。工作流目录边界由 **app 层** `resolveWorkflowPath`（`workflow-file.mjs` L48）强制，不在中继。

## 证据 2 · 能否建目录（关键项）
- **现有通道不能创建 `.history/` 子目录（代码确证）**：`writeFileAtomic`（`workflow-file.mjs` L369-387）= `writeFileSync(tmp)` → `renameSync(tmp,abs)`，**无 `mkdirSync(dirname)`**。写入不存在的父目录会抛 ENOENT，被 handler 转 500。
- 中继 `comfy-relay.mjs` 内虽有 `mkdirSync`（L121/727/849/1413），但均用于自身日志/状态目录，**未暴露为 `/_relay/fs/*` 端点**。
- app 进程受宿主 `--permission` 沙箱限制，fs 白名单不含 ComfyUI 目录，**不能自己 mkdir**（`index.js` L4958 的 mkdir 仅作用于 `app-data`，非 workflows）。
- **替代方案**：① 扁平点前缀文件名，无需建目录（零改动）；② 给中继 `writeFileAtomic` 加一行 `mkdirSync(dirname(p),{recursive:true})`（极小改动，约 1 行），即可用子目录结构。

## 证据 3 · 快照体积与 base64（实测 + 代码确证）
- **实测 46 份真实工作流**（已复制到 `D:\HanakoWorks\_temp\` 操作，未碰源目录）：min 156 B、median **67 815 B（≈66 KB）**、max 98 142 B、总 2.22 MB。
- **base64 实测：0 份含内嵌 base64**（`data:image/` 或 `;base64,` 全不匹配；长 base64 token >300 字符数 = 0）。
- 含 `PreviewImage` 节点的有 3 份，但该节点只存输入 `link`（如 `"link":923`），**不内嵌图像数据**（已读 `共编存档…json` 验证）。
- **结论（实测）**：UI 格式 JSON 本机工作流几乎不含 base64；「剥掉 base64 后」体积≈原体积（无料可剥）。字段路径若日后出现，通常在 `nodes[].widgets_values` 内嵌缩略图或 `PreviewImage` 的 image 槽——但当前语料无此情况。快照单份 ≈ 66–98 KB，远低于 16 MiB 写上限。

## 证据 4 · 原子性与并发（代码确证 + 推断）
- `writeFileAtomic` 用 `writeFileSync`（**同步阻塞**）写 `.tmp` 再 `renameSync`：Node 单线程下两个并发写同一路径不会半写交错，末尾写者胜、无损坏（**代码确证**；rename 在同盘上为原子替换）。
- **每份提交是独立唯一文件名**（rev+promptId8），互不冲突；快照一次写后只读不覆盖 → 并发提交**不会损坏快照**（代码确证/推断）。
- **唯一共享可变文件是 `index.json`**：两次快速提交会「读—改—写」同一 index，最后写者胜 → **可能丢一条记录**（read-modify-write 竞态，推断）。缓解：① 用追加式 JSONL（`_index.jsonl`，每行一条，免读改写）；② 每工作流一个 index 文件，缩小冲突面；③ 把元数据编入文件名/快照内，index 仅作可选缓存。

## 未决项

2. index 写入采用 JSONL 追加还是每工作流单文件——建议 JSONL 或每流单文件规避竞态。
3. 历史清理/上限：中继无 `delete` 端点，删除旧快照暂无通道（需新增或借 `fs/write` 空内容覆盖，不推荐）。
4. ComfyUI 是否扫描 workflows 子目录为工作流——建议实测 `.history/` 是否被列出（点前缀已可规避顶层污染）。
