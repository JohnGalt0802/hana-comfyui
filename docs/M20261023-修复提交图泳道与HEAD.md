## 一、根因回顾

提交上报时 `parent` 被强制取「索引末条主行」（2026-10-22 为修预览图绑错而加的补丁），
回跳时写入的 HEAD 在读取时被绕过。结果每次提交都接在最后创建的节点上，图退化为单链，泳道永远一条。

而该键在 Hana 宿主上从未可靠落盘。

## 三、独立复核结论（laoge，不同实例，未参与实现）

**通过**（均为复核者自己重跑实测，非采信执行者自报）：

1. parent 语义链：设 head 后提交，parent 指向 head；索引末条更靠后时仍取 head。
2. 脏 parent 校验：指向不存在 / 指向 merge 行 → 退回 head。
3. merge 与 head：merge 分支不触达写 head 代码，merge 前后 `.head.json` 逐字相同。
4. `list_commits` 的 head 三情形（无目录 / 坏 JSON / 指向已删）+ merge 行，均返回 null。
5. 前端 localStorage HEAD 引用清零，`historyPageKey` 未被误删。

## 五、遗留与已知边界

- **历史无法回填**：已产生的线性 parent 是既成事实（如 `moss-image-SFT综合` 的 15 个节点），
  改完只对后续提交生效。要修历史需单独设计索引重写，风险另评。
- **迁移触发面**：`migrate_history` 只在工作流改名且目标已有历史目录时走到合并分支；触发面窄，但一旦触发就是图错，故按真 bug 修。
- **跨标签页**：后端 HEAD 是 per-workflow 单值，两个标签页同时编辑同一工作流会互相拉扯 HEAD。这属于正确语义（HEAD 只有一个），不额外处理。
- **`.head.json` 写入失败**：best-effort，不阻断已成功的提交；读侧有「退回末条」兜底。
