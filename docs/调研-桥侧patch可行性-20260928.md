### 1.2 op 注册与执行链

- **注册**：单个对象字面量 `const OPS = {...}`（js L258–L792），键=op 名，值=handler 闭包；无独立注册器。JS 侧 21 个：

  另有 2 个**不走前端**、由 Python 直答：`canvas.state`、`canvas.pages`（`__init__.py` L205–L213）。
- **执行**：`api.addEventListener("hana_bridge.call", ...)`（js L817–830）：

```js
const fn = OPS[msg.op];
if (!fn) throw new Error("unknown op: " + msg.op);
payload = { ok: true, data: await fn(msg.args || {}) };
// catch → payload = { ok: false, error: String((err && err.message) || err) }

```

- **全链路**：`agent → app actionCanvas →（壳页腿 | 中继 /_relay/bridge）→ 8188 /api/hana_bridge/call（校验 x-hana-token）→ PromptServer.send_sync 经 /ws → 扩展 OPS → /hana_bridge/result → Future 回填 → 原路返回`（`画布共驾方案-20260926.md` §2.2；`__init__.py` L196–L276）。

- **超时预算**：前端等待默认 **6s**（`__init__.py` L61–63，环境变量 `HANA_BRIDGE_TIMEOUT` 可覆盖）；中继→桥 fetch 20s（relay L2137）；app→中继 30s（`index.js` L1716）。

### 1.4 undo 逆操作栈

- **存什么**：`[{label, undo: 闭包, at}]`，**最多 20 条**（超了 `shift()` 掉最旧），内存态、每页面一份、刷新即失：

```js
function pushUndo(label, undo) {
  writeStack.push({ label, undo, at: new Date().toISOString() });
  if (writeStack.length > 20) writeStack.shift();   // L143-147
}
```

- **谁消费**：仅 `canvas.undo`（L769–791）。流程：先试官方命令 `Comfy.Undo`（与人的 Ctrl+Z 同一条路，但实测对"外部直接改图"无效）→ `pop` agent 栈 → `await last.undo()`；失败**放回栈**并抛错；成功回 `via:"agent-rewind"` + `stackLeft`。
- **怎么回滚一步**：逆操作闭包各自带 `withChange` + `pollGraph`，只回退 agent 自己那一步（不做整图快照——不碰人在此期间的改动，见 `画布结构写入-20260926.md` §2）。
- **压栈时机**：效果**先执行、成功后**才压栈（效果抛错则不入栈，语义上"没发生"）。

## 2. 组合与事务可行性

### 2.1 现有 handler 可组合性（改动量评估）

现状每个 handler = 验证 + 执行 + 记账 + 返回四合一；**效果与逆操作是配对的**——这是可组合的基础。缺的是独立"预检"入口（dryRun 需要）。两条路：

**路径 A · 薄编排器（推荐 v0）**：patch 执行器按序调 `OPS["canvas.xxx"](args)`。对象字面量自引用在**调用期**解析（arrow 函数体执行时 `OPS` 已初始化），技术上没有任何障碍。执行器自己负责：edits→op 映射、`$` 解引用、失败聚合、逆序回滚、dryRun/verify。
- 改动量估值：桥 js **+150～250 行**（含预检/后置检查轻量实现）；`app/index.js` **+40～80 行**（op 表、参数白名单、回执格式化、工具 enum/描述）；`__init__.py` **0 改动**（op 透传本就通用）；`workspace.js` **0 改动**。
- 现有 8 个 handler 一行不用重写；最多给 `pushUndo` 加一个可选的"收集到批次局部列表"参数。

**路径 B · 纯函数化单元（可选后做）**：拆 `validate(args)→norm` + `apply(norm)→{payload, undo}`。dryRun/verify 覆盖度、错误粒度更好，但重写 ≈250–350 行且要防行为回归。**非 P4 前置**。
建议：v0 走 A；是否值得 B 留给 dryRun 的真实使用反馈。

### 2.2 同批内 `$` 引用（引用新建节点）的时机

**可行，且无竞态**：
- `canvas.addNode` 链路：`LG.createNode(type)` → `withChange(() => { ...; app.graph.add(node); })` → `return { nodeId: node.id, ... }`（L587–612）。`graph.add` **同步**分配 id——handler 返回时 id 已是真实值。
- patch 维护符号表 `symbols[as] = payload.nodeId`；后续 edits 的节点引用字段（`nodeId` / `fromNode` / `toNode`）按 `$name` 解析。同一 /call 内顺序同步执行，不存在"等 id"问题。
- 边界约定（v0）：`as` 重名 → 拒绝；未定义 `$name` → 报错触发回滚；`$` 只在节点引用字段解析；`as` 仅同批有效。
- 注意：失败回滚**不复原 id 计数器**（LiteGraph 的 last id 不倒退）。重试同一 patch，新节点 id 会更大——语义无碍，但验收断言别拿 id 做全等。

### 2.3 失败回滚（逆序执行现有逆操作栈）可行性 + 坑

机制上完全可行：写 handler 已把"怎么撤回去"备好；**逆序执行**即 LIFO 天然正确（先撤后发生的关系：先删链接、再删节点；先撤新连、再恢复旧断线）。要封的坑：

1. **writeStack 20 条上限**：批量 >20 条时 `shift()` 挤掉最旧条目（先是批前旧步骤，继而波及本批最早几条）；"记栈深→pop 回栈深"的方案在触发驱逐时不可靠（回滚集合不齐/不干净）。→ **批内把逆操作收集到局部数组**；成功后（a）逐条压栈或（b）压 1 条复合逆操作；回滚直接用局部数组，不碰全栈。
2. **逆操作闭包内部吞错**：`removeNode` 恢复连线、`disconnect` 恢复重连都是 `try/catch 忽略`（L648–661、L702–710）。批量回滚必须**逐条记录失败**并如实返回 `rollbackErrors[]`，不得报"原子成功"。
3. **save 不可逆**：图能回滚、文件不能。→ `save` 只允许作**最后一条** edit；前序全成功 + verify 通过后才执行；文件侧兜底＝它自带的 `.bak.json`。
4. **"假成功"污染事务**：`canvas.connect` 对 `linkId=null` 不抛错（L676–685），§23③ 的"首连静默失败"会以"成功 edit"进账。→ patch 的 connect 单元以"`graph.links` 里出现目标槽连线"为唯一成功判据，失败重试 1 次、再不行才 fail。
5. **回滚别走 `canvas.undo` op**：它会先执行官方 `Comfy.Undo`（可能撤到人的操作）再 pop。patch 回滚应直接执行局部闭包。
6. **回滚期间的噪音**：逆操作闭包自带 `withChange`+`pollGraph`，revision 会跳几次、state 快照会推几次——可接受（本来就是真实变化）；verify 终态对账要等全部回滚完成后做。

### 2.4 dryRun 可借的现成能力

| 能力 | 现状（行号） | 用途 |
|---|---|---|
| 槽存在性解析 `slotIndex` | L149–157（名字优先、纯数字回退索引、-1=不存在） | connect/disconnect 槽预检 |
| 节点存在性 `findNode` | L62–66（getNodeById + 名单兜底） | 所有 nodeId 引用预检 |

2. **改 `__init__.py`（Python 路由/账本）**：**必须重启 ComfyUI**（路由启动时注册）。重启后已开页面只重连 ws、js 不重载——若同时改了 js，还需第 1 步。
3. **一键**：`bridge-reload.ps1`（注意：默认会重启服务 + 开浏览器 + 冒烟）。
- 版本诊断：页面里 `window.__hanaBridge.version`（js L796–806）或 `api.probe.bridgeBuild`（L330）。

## 4. 结构化返回的组装点

- **桥**：只产 JSON payload（handler 返回对象；错误为 `error` 字符串）。**不产人话文本**。
- **app**：`actionCanvas` 的 if/else 链（`index.js` L1746–1845）逐 op 拼人话给 agent——如 `已连线 #27[0] → #8[0]（linkId=38）`（L1823）、`已落盘：workflows/…（27 节点），备份 …`（L1827）、`已撤销「…」（剩余可撤销 N 步）`（L1831）。`details.comfyui` 只带零星结构化字段。**§23④"返回是人话文本"的出处即此**。
- **P4 应动 app 层**：
  - 桥侧：新增 `canvas.patch`，payload 结构化（`{results[], verify, rollback?, rev, warnings[]}`）；
  - app 侧：`CANVAS_OPS` 加 `patch`（write:true）→ 白名单加 `edits/verify/dryRun` → 工具 enum/描述补充（L2002–2020、L2054）→ 文本分支：成功给"人话摘要 + 结构化 JSON"（协议对齐 §5.2 `{ok, op, data, warnings, rev}`），失败给 failedAt + 回滚结果；`details.comfyui` 挂完整 payload。
  - 壳页腿与 HTTP 路由复用同一 `actionCanvas`，改一处两条入口都生效。

## 5. §23 坑在批量事务里的封堵

| §23 坑 | 现象（摘要） | 批次内封堵设计 | 校验点 |
|---|---|---|---|
| ① `loadWorkflowFile` 不落定 | 整图替换不产生"真实编辑"，未保存期间画布可能被恢复回旧版 | **v0 不进 patch**（明确报错）；要"先装载再改"就拆成前置步骤：装载 → 等签名稳定 → 再开 patch；patch 以真实编辑 + `save` 收尾 | patch 后 get/revision 对账；文件、画布、`.bak.json` 三处一致 |
| ② 自动增长槽收缩改名 | 断 `values.b` 后 `values.c` 补位；照旧名再断报"没有连线"；首空槽接上才出现下一空槽 | 槽相关 edit **执行前即时解析**（基于 live `node.inputs`，不预读索引、不缓存名字）；串行执行天然对着"上一 edit 后的槽现状"；对"操作后槽名/数量变化"的节点做抽样复核 | 每步后复核目标槽按预期变化；失败即停→回滚 |
| ③ widget 槽首连静默失败 | connect 未报错但未连上；重试一次成功 | connect 单元：执行后查 `graph.links` 出现目标连线；没有 → 重试 1 次 → 仍无 → fail；**linkId=null 不再当成功** | 以 links 表为唯一判据（不依赖 connect 返回值） |
| ④ 返回是人话文本 | 别 ConvertFrom-Json / 正则解析 | patch 回执结构化（app 组装文本）；内部 verify 读 payload | —— |

**附加发现（本调研挖出的事务级隐患，非 §23）**：

- **A. `workflow` 定向链路断裂 [待实测]**：工具参数 `workflow` 被塞进 `args`（`index.js` L1702、L1712–1717），中继只转发 `{op, args}`（relay L2135–2139），而 Python 读**顶层** `body.workflow`（`__init__.py` L219）。→ 经 hui 工具链路的多页面定向**到不了桥**、实际退化为广播（多页面各执行一遍——§11 的坑）；M12 §6.9 的"定向成功"很可能走的是直连 curl（top-level `sid` 路径）。P4 若依赖定向，先修：relay 透传 `workflow` 字段，或 Python 兜底读 `args.workflow`。
- **B. writeStack 20 上限 vs 批量回滚**（见 §2.3-1）。
- **C. save 不可逆**（见 §2.3-3）。

## 6. 实现建议（给决策与执行）

1. **落点**：执行器加在桥 js（`canvas.patch` + helper）；app 加 op 与回执；`__init__.py` 不动；壳页腿不扩（代理模式下 patch 明确报"不支持"，维持现状约束）。
2. **v0 edits 白名单**：`addNode / setWidget / connect / disconnect / setNodeMode / removeNode / save`；`save` 仅限最后一条；禁 `undo / loadWorkflowFile / openWorkflow / organize`（明确报错）。`as/$` 只作用于节点引用字段。
3. **事务实现**：
   - 执行：顺序调用现成 handler（复用），批内局部收集逆操作；
   - 回滚：逆序执行局部逆操作，逐条记结果；返回 `{ok:false, failedAt, rolledBack[], rollbackErrors[], rev}`；
   - 成功：verify（默认开）→ save（若有，置尾）→ 压栈（建议压 **1 条复合逆操作**，语义="一次 patch = 一步撤销"，天然避开 20 上限；逐条压栈是备选，待主脑拍）；
   - dryRun：只跑预检（存在性 / 槽 / 类型启发式 / `$` 完备性 / save 可解析），addNode 干跑校验，输出逐条 `checks[]`；
   - 并发：patch 加 in-flight 标志（同页两个 patch 同时进来会交错，直接拒绝并明确报错）。
4. **verify 断言**：逐 edit 后置条件（widget 值、link 存在/缺失、mode、节点存在/不存在）+ 全局签名/rev 对比；verify 失败默认触发回滚（可选项 `"report"` 只报——待主脑拍）。
5. **超时**：默认 6s 是真实约束（relay 20s / app 30s 为上界）；大批量建议文档化条数上限或提 `HANA_BRIDGE_TIMEOUT`。**特别提醒**：超时 504 时前端可能已执行完——"收不到回执 ≠ 没生效"；验收脚本要"先查 rev/状态再决定重试"（与 §23① 同类教训）。
6. **定向（若 P4 要跨页）**：先修附加发现 A 的链路，再加"双页面只动目标页"验收用例；否则 P4 验收限定单页面。
7. **冒烟/验收**：`bridge-reload.ps1 -Op canvas.patch -ArgsJson '{...}'` 起手；拿"尺寸自定义"场景端到端（一次 patch 完成 + 失败注入回滚 + dryRun 预检）；失败注入建议：第二条 edit 故意指错槽名。
