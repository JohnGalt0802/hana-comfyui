## 一、先把靶子摆正：探针的两条命，宿主大卡只有半条

| | 页内心跳（自救） | 踹探针（外援） |

→ **宿主大卡没有外援，只剩自救**。本轮查的就是：自救为何失效。

## 二、判定表：变稀 vs 归零（核心尺子）

`hui-page-pulse.jsonl` 每行 `{t, n, vis}`，`n` 是**进程内自增计数**（页面加载从 0 起）。

| 现象 | 含义 | 机制 |
|---|---|---|
| 记录**变稀**（如 10s→60s 一条），`n` 继续递增 | 页面**还在**，timer 被降频 | Chromium intensive throttling（后台标签节流） |
| 记录**归零间断**（断档后 `n` 从 **1** 重来） | **JS 上下文重建** = 页面被销毁后重新加载 | iframe 卸载 / 卡片重挂 / 页面重载 |

**关键判据**：`n` 归零 ⟺ 上下文不复存在。**冻结绝不归零**（变量还在内存里）。

## 四、待验证的三种机制（本轮要查清的）

| # | 机制 | 判据 | 若成立则根因在 |
|---|---|---|---|
| M1 | 宿主主动**卸载**卡 iframe（切走/隐藏时销毁，回来重建） | 断档起点紧跟"切走"时刻；重建后 `n`=1 | 宿主挂载策略 |
| M2 | Chromium **discard**（内存压力下丢弃后台 frame） | 断档无规律；与内存压力相关 | 浏览器 |
| M3 | 宿主主界面整体被**冻结**（Electron 后台 webContents） | **不符**（应为变稀、不归零） | — 已可排除 |

**注意**：M3 若成立应表现为"变稀不归零"，实测全归零 → **M3 基本排除**，主查 M1/M2。

## 四·补（2026-10-12 晚）：根因已定位 = M1（宿主主动卸载），有宿主契约原文为证 `[实测]`

宿主自己在卡片契约里写明了策略 —— `C:\Users\John Galt\.hanako\card-guide\guide.md:180`（主脑亲手读出的原文）：

> "the host starts a card only once it first comes into view; while it is out of view its tool channel stays closed… and **once it has been scrolled far enough away the host unloads it and starts it again from its saved state when it returns**. Your card does not need to detect or work around any of this. **Keep whatever must survive in `state`, not in script variables**…"

三条推论：
1. **宿主是主动方**：看不见 → 卸载 → 回来按 saved state 重建。`n` 归零（闭包变量丢失）与这条策略**完全一致** → 根因判定 **M1**。
2. **M2（Chromium discard）非主因**：discard 是内存压力下的随机行为，与"切走即卸载"的规律断档不符；且宿主契约已明说有主动卸载。
3. **页内心跳天然保不住**：探针把 `n` 存在**脚本闭包变量**里（`setupThrottleProbe` 的 `let n = 0`），恰好踩在契约红线"别把要活的放脚本变量"上。页面一卸载，闭包与 timer 全没 → `n` 只能从 1 重来。

**旁证**：宿主对 browser viewer 有保活先例（`browser-viewer.html` 注释："隐藏一律走 visibility（`display:none` 会冻结 guest，禁止使用）"）—— 它**懂得**怎么保活，只是没给工作区卡用。

**全 `.hanako` 域检索：`backgroundThrottling` / `keepAlive` / 宿主级 `throttle` 全未命中** → 不存在任何宿主层可调的"卡保活"开关。

### 干扰项排除（方法论）
`hui-page-pulse.jsonl` 是**多页面实例共享写同一个文件**，`n` 是**每实例各自的闭包变量**。多实例并存时（如 2026-10-12 19:19 开原生窗口后），两条流交错写入，会**误呈现为密集归零**。
- 判据：单实例段内 `n` 应严格 +1；跨实例则跳变。用"实例切分"（n 非 +1 或断档 >60s 处切段）可分离。
- 已验证：01:17→13:17 一段 4320 条、n 完美 +1→4320；16:38→18:12 一段 566 条、n +1→566 —— **均为单实例连续**，归零判定成立。
- 19:19 之后的小段（n=1,5,2,6,3,7,4,8 交错）= 开窗造成的双实例交错，**不计入**销毁判定。

## 五、出路（App 侧治不了这个）

App 拦不住宿主卸载自己。两条真出路：
- **(a) 递宿主需求**：给 `realization:"page"` / 工作区卡一个"常驻不卸载"选项（或后台节流豁免）。
- **(b) 改走窗口态**：原生窗口（`detached`）不参与"滚出即卸载"，实测 hidden 下 1~3ms 应答 → 保活成立。但这是**绕开**，非治好卡态。

> 附：`pagehide`/`visibilitychange` 也能被 App 侧观测到一部分，但若宿主是"移除 iframe"型卸载，这些事件未必来得及可靠上报（待验）。
