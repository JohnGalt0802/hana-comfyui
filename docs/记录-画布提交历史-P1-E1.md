## 已知边界与实现注记

1. **seq 起点假设**：A1 断言 seq=1，依赖「`__selftest__` 目录初始不存在」；脚本预清理残留测试目录来保证。`.history/` 里非测试名目录不影响（seq 按各自目录独立计数）。
2. **B5 口径**：JS 前端层（canvas-history）已拦空图，HTTP 层不重复拦——落盘为设计行为，脚本标注记录不判 fail。
3. **C1 口径**：当前设计「每次提交都是新快照」，同 promptId 产生不同 seq、两个文件——脚本断言两次成功且 seq 递增，不改行为。
4. **C2 无锁竞态**：Python 端 commit 读索引→算 seq→追加写无锁。真并发 5 发在单机进程内（asyncio 单线程事件循环 + GIL）现实竞态窗口极小，脚本验证的是「现实窗口内无丢失、seq 无重复」；若未来改为多 worker/多进程需重新评估。
5. **索引行精确比对**：A2 用 `-ceq` 逐字符比对首行，覆盖「追加不覆盖」语义；换行符为 LF（Python `newline=""` 写 `\n`）。
6. **超大 payload**：B4 用 15MiB ASCII pad 构造，走 HTTP body 上传；若 ComfyUI 前置（代理/中继）另有 body 上限，可能先于 413 返回更小的 4xx——脚本放宽为任一 4xx 并要求不落盘。
7. **路径等价性依据**：ComfyUI aiohttp 路由挂载方式使 `/api/hana_bridge/*` 与 `/hana_bridge/*` 等价（P1-D2 实测发现，无需改代码，本组用例防回归）。
8. **信任模型**（P1-D1 起）：history-commit/list 不校验 token，仅限 8188 同源/本机调用；脚本走本机 HTTP 即符合。

## 真机首跑发现的三个脚本 bug 与修法（2026-10-11 续批）

真机首跑 4/6。逐条排查结论：**端点行为全部正确，失败全是脚本自身的 bug**。以下三条已修，只改脚本，未碰桥 JS/Python。

### Bug 1（A1/A2 假失败主因）—— `ConvertTo-Json` 拍平单元素嵌套数组

- **现象**：`New-SmallGraph` 用哈希表构造 `links = @(@(1,1,0,2,0,'IMAGE'))`，经 `ConvertTo-Json` 序列化后单元素嵌套数组被拍平成 `"links":[1,1,0,2,0,"IMAGE"]`。端点如实数出 `linkCount=6`，断言 `linkCount -eq 1` 必败。
- **端点验证**：手工用真 JSON（`"links":[[1,1,0,2,0,"IMAGE"]]`）POST 同样内容，端点返回 `linkCount=1`、快照里 links 结构原样保留——端点无错。
- **修法**：弃用「哈希表 → ConvertTo-Json」路径，改为直接构造原始 JSON 字符串：`New-SmallGraph` 直接返回已序列化的 JSON 字面量；新增 `New-CommitBodyJson` 助手拼请求体（workflow/promptId 仍走 `ConvertTo-Json` 转义保证字符串安全，graph 部分原样嵌入）；`Invoke-HanaApi` 支持 `$BodyObj` 传字符串时原样使用。
- **同类坑排查（一并修）**：C2 并发用例原本用 `[ordered]@{ nodes = @(@{…}) }` 再 `ConvertTo-Json`——`nodes=@(@{…})` 同样会被塌成单个对象，`graph.nodes` 不再是数组（nodeCount 会数错）。已改为直接拼原始 JSON。

### Bug 2（A1 at 断言假失败）—— pwsh 7 `ConvertFrom-Json` 把 "at" 解析成 datetime

- **现象**：`ConvertFrom-Json`（pwsh 7）把 `"at":"2026-10-11T00:00:00.000Z"` 解析成 datetime 对象，`$snap.at -eq '2026-10-11T00:00:00.000Z'` 变成 datetime -eq string，恒 False。
- **修法**：快照 round-trip 读回改用 `System.Text.Json.JsonDocument` 直读原始字符串（`GetProperty('at').GetString()`），同时规避 datetime 强转与嵌套数组的任何读回歧义（links 结构也能按数组精确计数）。
- **同类坑排查**：A3/D2 的 entries 只做「字段存在性」检查与路径间比对（经 `ConvertTo-Json` 再比字符串），不做 datetime 字面量比较，不受此坑影响；C1/C2 的 seq 取数与比较均为数值，同样不受影响。全脚本仅快照读回一处做字符串时间断言，已修。

### Bug 3（B4 崩溃中断）—— 格式串里的字面花括号

- **现象**：B4 的 `-Actual ("HTTP={0} body={(截断)}{1}" -f …)` 中 `{(截断)}` 被 `-f` 当占位符解析，`(` 不是 ASCII 数字 → "Expected an ASCII digit" 异常，脚本中断，B4 之后（B5/C/D 全组）没跑。
- **修法**：改为 `"HTTP={0} body(截断)={1}"`，字面花括号从格式串里去掉。
- **同类坑排查**：全脚本其余 `-f` 格式串逐条核对，均只含 `{0}`/`{1}`… 数字占位符与 `{{}}` 之外的正常字面字符，无同类问题。

### 修后验证（脚本侧）

- PowerShell AST 解析语法检查通过（`Parser.ParseFile`，0 错误）。
- 静态扫描确认：commit 请求体不再有「嵌套数组哈希表 → ConvertTo-Json」路径（A/B/C/D 全部用例改走原始 JSON 串）；无字面花括号占位符；datetime 字面量比较仅剩快照读回一处且已改 JsonDocument 字符串读法。
- 未实机运行（红线：实机由主脑执行）。

### Bug 4（真机第二轮：A1/A2 仍假失败）—— 单元素数组跨函数边界被解包

- **现象**：`Get-IndexLines` 内部 `return @(...)` 产出数组，但 PowerShell 函数输出是流——调用方 `$idx1 = Get-IndexLines $dir` 接收单元素数组时被降级成标量字符串：`$idx1[0]` 取到首字符 `{` 而非第一行，`$line1 -match '"seq":1'` 恒 False；A2 的首行 `-ceq` 比较同理。文件原始字节与 `Get-Content` 管道输出均正确，只有跨函数边界后才坏。主脑已亲手复现钉死。
- **修法**：所有跨函数边界接收这三个助手（`Get-IndexLines` / `Get-SnapshotFiles` / `Get-DirNamesUnderHistory`）返回数组的地方，一律调用侧包 `@()`，共 9 处：
  - `$idx1 = @(Get-IndexLines $dir)`（A1，含 `-match`/`[0]` 索引断言）
  - `$idx2 = @(Get-IndexLines $dir)`（A2，含首行 `-ceq` 比较）
  - A3 证据串里的 `@(Get-IndexLines $dir).Count`
  - B1 前后快照的 `@(Get-DirNamesUnderHistory) -join '|'`（两处）
  - B3 的 `@(Get-SnapshotFiles …).Count` 与 `@(Get-IndexLines …).Count`
  - C2 的 `$raceFiles = @(Get-SnapshotFiles $raceDir)`、`$raceLines = @(Get-IndexLines $raceDir)`
  - finally 清理后的 `$rest = @(Get-DirNamesUnderHistory)`
- **同类排查结论**：全脚本正则扫描「`$x = Get-*` 裸接收」残留 0 处；其余数组来源（`$nodeIds`/`$linksArr` 已包 `@()`；`$entries`/`$raceResults`/`$raceSeqs`/`$allOk` 已包或经 `@()` 包裹；`$existing` 也已包）不再有跨边界裸接收。
- **行为级验证（不碰实机）**：用临时单行 JSONL 复现——不包 `@()` 时 `$x[0]` 确为 `{`，包后取回完整行且 `-match '"seq":1'` 为 True。
