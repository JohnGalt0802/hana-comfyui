**结论：结构是 `{ [promptId]: { prompt, outputs, status, meta } }`，产物在 `outputs.<nodeId>.images[]`，每项含 `filename / subfolder / type`（实测还附 `metadata` 与 `id`）。**

### 1.2 `GET /view?filename=...&subfolder=...&type=output` 取二进制

**结论：返回的是该图片文件的 raw bytes（实测为 PNG 二进制，带 PNG 魔数 `89 50 4E 47`）；可直接作为 `<img src>` / 二进制读取。且官方端点自带 `preview=webp[;quality]` 参数，能**就地**缩放/转 webp，无需自己生成。**

**缩放 / 转 webp 能力（关键发现）：**


## 3. 出图完成时机

### 3.1 完成信号来源

**结论：ComfyUI 通过 `/ws?clientId=…` 推送事件，其中 `execution_success`（一次运行成功收尾）与 `executing`(node=null) 表示"这个 promptId 出完了"；权威收尾也可轮询 `/history/{promptId}` 看 `status.completed`。**

后端 WS 事件（`comfy-relay.mjs` 中 `handleBackendEvent` 处理，推断 + 实测 history.messages 印证）：
- `execution_start` — 开始执行（`comfy-relay.mjs:1835`）
- `executing`(node=null) — 主体执行结束、等待 history 收尾（`:1852` 注释）
- `executed` — 每个输出节点产出，带 `data.output[].filename`（`:1876`，中继已在此收集 `outputs`）
- `execution_success` — **完成**（`:1921`，置 state=completed、finishedAt）
- `execution_error` / `execution_interrupted` — 失败 / 中断（`:1897/:1912`）

App 侧 `index.js` 的 `refreshJob`（`index.js:748`）用 `/_relay/prompts`（WS 事件缓存）跟踪，并在 `!historyFetched && (rec.state==='completed' || 已等3s)` 时回查 `/_relay/history` 做**权威收尾 + 取产物**（`index.js:779-785`）。即 App 侧"出完 → 取产物"已经自动发生。

### 3.2 桥现在有没有监听 `execution_start`？能否顺带在 `execution_success` 回填？

**结论：桥（前端 hana-bridge）当前**没有**监听 `execution_*` 事件——它走的是**提交捕获**（`installQueuePromptCapture`，包装 `api.queuePrompt`，`hana-bridge…:2157-2212`），即在**人点 Queue 的瞬间**抓画布快照并上报 promptId（P1 捕获点）。后端的 `execution_*` WS 事件是由**中继 `comfy-relay.mjs`**订阅的（`startBackendEvents`，`comfy-relay.mjs:1950` 附近），桥并不直接连 WS。**

要点（推断）：
- 桥的提交捕获点：`installQueuePromptCapture` → 包装 `api.queuePrompt`，提交后 `reportHistoryCommit({graph, promptId, blocks})`（`hana-bridge…:2177-2205`），在 `setup()` 常驻安装（`:3209`）。这是 **P1 提交捕获点**，时机是"提交前/刚提交"。
- 桥侧 `api.addEventListener(EVT_CALL, …)`（`hana-bridge…:3172`）是监听**中继经 /ws 推来的指令**（宿主→桥调用），不是 ComfyUI 后端事件。
- 因此：桥**当前不在 `execution_success` 做回填**。但有两个现成接入点可考虑：
  1. **App 侧**已有 `refreshJob` 在 `execution_success`（经 `/_relay/prompts`）后自动 `settleJob` 并 `enrichOutputs` —— P4 缩略图回填挂在这里最自然（产物已就绪，直接补 webp URL）。
  2. 若坚持在桥前端回填历史条卡片，可在桥里订阅 ComfyUI 前端 `api.addEventListener("execution_success", …)`（ComfyUI 前端 api 本身支持该事件，推断；中继 `comfy-relay.mjs` 正是解析同名事件），但桥目前未用。
- **推荐**：回填逻辑放 **App 侧 `settleJob`/`enrichOutputs`**（产物上下文最全，且已处理 batch），历史条卡片 `.hhb-thumb` 在渲染时直接用产物 webp URL 即可；桥前端无需新增事件监听。

## 4. webp 缩略图怎么生成

### 4.1 桥 / 中继 Python 侧 PIL

**结论：本机 ComfyUI 的 venv Python 有 PIL 12.3.0（实测）。但 App 是 Node（中继 `comfy-relay.mjs` 是 Node，无 PIL）；桥 Python 后端 `history_store.py` 是纯标准库、未 import PIL（推断）。所以"Python 侧生成"指 ComfyUI 后端或另起 Python，而非现有 App 代码直接调用。**

- 实测：`D:\ComfyUI\venv\Scripts\python.exe -c "import PIL"` → `PIL 12.3.0`。
- 推断：`app/bridge/history_store.py` 顶部注释明确"纯 Python，零 ComfyUI 依赖 / 只用标准库"，全文无 PIL import（读 `history_store.py` 全文确认）。
- 中继 `comfy-relay.mjs` 是 Node 单文件、无第三方依赖（文件头注释），无图像库。

### 4.2 ComfyUI 自带缩略图机制

**结论：ComfyUI 后端 `/view?preview=webp[;quality]` 就是现成的"缩略/转 webp"端点（§1.2 已实测）。此外后端 `latent_preview.py` 有生图过程 latent 预览（MAX_PREVIEW_RESOLUTION），但那是过程预览、非最终产物缩略；前端 `app/assets/api/routes.py` 有 Media Assets 的 `preview_paths`（`:297/:351`，asset 预览 URL），也与 P4 出图产物不是同一回事。**

- `/view?preview=webp` — `server.py` 约 627-646 行，实测返回 `image/webp`（见 §1.2）。**这是最省事的"缩略图"源**：不落盘、按需生成、同源。
- 注意：`preview` 参数只控制**格式+质量**，**不降分辨率**（实测：原图 1024×1024 → webp 仍是全分辨率，仅转码，199KB）。若需要真正"小缩略"（如 256×256 或 48×48），`/view` 的 `preview` 不够，需要额外缩放。

### 4.3 前端 canvas 缩放可行性

**结论：前端拿到图片 URL → `new Image()` → `canvas.drawImage` → `canvas.toBlob('image/webp', q)` 可行，且 8188 同源无跨域问题（CORS 不适用同源）。但把 webp 字节回传/落盘需要走 `fetch`→`blob`→`FormData`→上传，链路比直接吃后端 `/view?preview=webp` 更长。**

- 同源：本机 8188，桥运行在 ComfyUI 前端页内，`<img>`/`fetch` 同源，无 CORS 限制（推断）。
- 缩放：`ctx.drawImage(img, 0,0, w, h)` 可任意缩到目标尺寸（如 256×256），再 `toBlob('image/webp', 0.8)`。
- 但若只是为了"在历史条卡片显示小图"，直接 `<img src="viewPath&preview=webp">` 让浏览器按 CSS 缩小显示即可，不必真的生成低分辨率字节。仅当要"落盘一个独立 .webp 缩略文件"时才需要后端/Python 缩放。

### 4.4 推荐方案（带理由）

**推荐：用 ComfyUI 后端 `/view?...&preview=webp;质量` 作为缩略图源（按需、同源、零新增代码），在 App 侧 `enrichOutputs`/渲染层把 `viewPath` 升级为带 `preview=webp` 的 URL；历史条卡片 `.hhb-thumb` 与任务卡 `task.js` 直接用此 URL 渲染 `<img>`。**

理由：
1. **零新写编码逻辑**：后端已实测能返回 `image/webp`（§1.2），复用 `viewPathOf` 拼 URL 即可（在 `index.js:640` 加 `&preview=webp;75`）。
2. **同源、无需跨域处理**：8199/8188 同源，无 CORS（推断；桥在 ComfyUI 前端页内）。
3. **不落盘、按需生成**：省去"生成→存盘→索引→清理"一整套，避免体积与过期管理。
4. **现有回填点已就位**：`hana-bridge…:2546` 注释明写"P4：换 .thumb.webp 真缩略图"，`task.js:54/96` 已用 viewPath 渲染 `<img>`，改动极小。

何时需要"真·Python 缩放落盘"（不推荐为 P4 默认）：
- 若要求卡片/列表显示**固定小尺寸位图文件**（如 48×48 头像式缩略、要落盘进历史目录 beside 快照）；
- 此时可用 ComfyUI venv 的 PIL（§4.1 实测可用）或走 ComfyUI 后端新增一个缩放端点。但 §1.2 的 `preview=webp` **不降分辨率**，要小图仍需额外缩放步骤。
- 注意：App 侧（Node 中继）无 PIL，不能在中继里直接 PIL 生成；要么调 ComfyUI 后端、要么走桥 Python 后端（目前 `history_store.py` 未带 PIL，需新增依赖/调用）。

## 5. batch 多图

### 5.1 一次运行多张图时 `outputs` 怎么表达

**结论：batch（如 KSampler batch_size=N 或 SaveImage 一次写出多帧）时，单节点 `images[]` 数组长度 = 张数；不同输出节点各自一个 `images[]`。即"节点桶 + 数组"自然表达多图，无需特殊结构。**

- 实测样本：`outputs["25"].images` 长度 1（单图）。多图时推断为 `images.length > 1`（`comfy-relay.mjs` 的 `collectOutputs` 对 `item.filename` 逐个 push，上限 200，即支持同节点多张）。
- App 侧 `collectOutputs`（`comfy-relay.mjs:2258`）：遍历 `outputs[nodeId][kind]` 数组里每个 `item`，凡带 `filename` 都收集为一条产物（带 `node` 归属），天然支持 batch 多张。

### 5.2 一个 promptId 是否总能对应一次完整运行（含 batch）

**结论：是。`/history/{promptId}` 的 `outputs` 聚合了"该 prompt 这次执行"**所有**输出节点的全部 images（含 batch 张数），`status.completed/status_str` 表示整次运行成败。一次 prompt 提交 = 一次完整运行（batch 是同一次运行内的多张，不会拆成多个 promptId）。**

- 实测：同一 prompt `3a2f28b5-…` 的 `outputs` 含节点 17（0 图）+ 25（1 图），`status.messages` 只有一组 `execution_start→execution_success`，无重复 promptId（推断：一次提交一个 promptId，batch 在同 prompt 内）。
- 注意：`/history`（不带 id）返回**所有** prompt 的字典（实测 3 条），按 promptId 取单条用 `/history/{promptId}`（`comfy-relay.mjs:2308` `handleHistory` 支持 id 参数）。
- 边界：中继 `collectOutputs` 有 200 张上限（`comfy-relay.mjs:2263` 附近 `if (out.length >= 200) return out`），极端超多图会被截断——一般 batch 不会到 200。

### 6.2 可选方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 后端 preview=webp（推荐）** | 渲染层把 viewPath 加 `&preview=webp;75`，`<img>` 同源加载 | 零新代码、按需生成、不落盘、同源无 CORS | 只转格式不降分辨率（全分辨率 webp，~200KB/张）；非独立落盘文件 | P4 绝大多数场景（卡片/列表小图显示） |
| **B. 前端 canvas 缩放** | 前端 `img→canvas→toBlob('image/webp')` | 可任意缩到目标尺寸；同源无 CORS | 要回传/落盘才"真生成文件"，链路长；仅显示则没必要 | 需固定小尺寸位图且不靠 CSS 缩放时 |
| **C. Python/PIL 生成落盘** | 用 ComfyUI venv PIL（实测 12.3.0）或后端新端点缩放写盘 | 真·小尺寸独立 .webp 文件，可进历史目录 | App 侧(Node)无 PIL，需走 ComfyUI 后端或给桥 Python 加依赖；要管体积/过期 | 必须落盘缩略（如头像式 48×48）才考虑 |

### 6.3 推荐方案
1. **默认走方案 A**：在 `app/index.js` 的 `viewPathOf` 增加可选的 preview 参数（如 `viewPathOf(o, {preview:'webp;75'})`），`enrichOutputs` 给产物补 `thumbUrl`；历史条卡片 `hana-bridge…:2546` 与任务卡 `task.js:96` 改用 `thumbUrl` 渲染 `<img>`。改动小、零新编码、已实测通。
2. **batch 多图天然支持**：`collectOutputs` 已逐张收集，`outputs[]` 带 `node` 归属；回填时按现有 `outputs` 列表遍历即可（`.hhb-thumb` 当前每条历史只 1 个缩略位，若一次运行多图需决定显示哪张——建议取第 1 张或首个有图的节点）。
3. **仅在"需要落盘小图文件"时**再考虑方案 C（用 ComfyUI 后端/PIL 缩放写盘），并复用 `/_relay/fs/write`（`comfy-relay.mjs:2993`）落盘、写入历史索引——但非 P4 必需。
4. **回填时机**：接 App 侧 `settleJob`/`enrichOutputs`（产物已就位），不要在桥前端新监听 `execution_success`（桥目前不连 ComfyUI WS，且 App 侧已自动结算）；桥前端只负责"渲染时显示 `thumbUrl`"。
