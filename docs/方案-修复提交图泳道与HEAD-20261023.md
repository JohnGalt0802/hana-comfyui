# 方案：修复提交图「回跳后提交不分叉」与小黄点不跟随

**日期**：2026-10-23
**提出**：John 报障（主泳道回跳编辑并提交，不生成新泳道，只在最右侧新加节点；HEAD 小黄点也不跟随回跳）
**主脑**：hanako
**状态**：方案已定，待实施

---

## 一、症状

1. 在主泳道回跳到某个历史节点，编辑后提交，新提交接在最右端同一条泳道上，不产生分叉（应为新泳道）。
2. 提交节点上标示「当前编辑节点」的小黄点（`.htr-tick-head`），回跳后仍停在旧节点。

---

## 二、根因（已实测取证）

### 2.1 主因：提交的 parent 被强制改成「索引末条」

线上桥 `app/bridge/js/hana-bridge-20243001.js` L3052-3105：

```js
// 2026-10-22 修（预览图绑错提交的根因）：HEAD 不能只信 localStorage。
async function fetchAuthoritativeHeadSeq() { ... 取索引最后一条主行的 seq ... }

// reportHistoryCommit 内：
let parentSeq = await fetchAuthoritativeHeadSeq();
if (parentSeq == null) {
  const head = historyHeadGet();
  if (head && head.seq != null) parentSeq = head.seq;
}
if (parentSeq != null) body.parent = parentSeq;
```

`fetchAuthoritativeHeadSeq()` 几乎总能成功，于是 parent 恒等于索引最后创建的主行节点。
回跳时虽然写了 localStorage HEAD，但读取时被抢先，形同废纸。

**必然结果**：图退化成一条链，泳道永远 1 条。

### 2.2 证据

**证据 A — 真实历史索引**（`moss-image-SFT综合`，目录 `c01b05e9-7ae7-41fe-8079-659452a55044`）：

```
seq 1..12  parent = 前一条        （线性）
seq 20     parent = 12
seq 28     parent = 20
seq 30     parent = 28
```

15 个主行节点，parent 全部等于前一条。其中 seq 28 的快照体积从 50455 字节降到 47466 字节，是明显回退后再提交的内容，它的 parent 却仍是末条 20，而非回跳目标。

**证据 B — localStorage 无 HEAD 键**：
在 Hana 的三个浏览器分区（`AppData\Roaming\hanako\Partitions\hana-browser-*`）的 LevelDB 中检索，
只有 `hana.history.tree.v1:*`（提交树展开状态）与 `hana.historyTreeView.v1`，
`hana.history.head.v1:*` 一个都不存在。HEAD 从未在这个宿主上可靠落盘。

**证据 C — 小黄点同源**：
`historyTreeRenderTree` 内 `const head = historyHeadGet(); ... if (head && head.seq === nd.seq) node.classList.add("htr-tick-head")`。
同一份易失存储，同一处失准。

## 三、修法

### 3.1 原则

HEAD（当前所在提交节点）是**图的状态**，不是浏览器的状态。放在 localStorage 里必然受分区漂移与多标签影响。
改为**后端持久化**，前端只读、只写「回跳」这一个动作。

同时保留 2026-10-22 那次修复的成果：不再让一个卡死的 HEAD 把新提交全部合并到旧节点。

### 3.2 后端契约（`history_store.py` + `__init__.py`）

**存储**：`<history_dir>/.head.json`，内容 `{"seq": 12, "at": "2026-10-22T18:44:14.000Z"}`。

**读写规则**：

| 时机 | 动作 |
|---|---|
| `commit()` 新建节点成功 | `.head.json` ← 新节点 seq |
| `commit()` 判定合并（merge 行） | `.head.json` 不变 |
| `save_commit()` 新建节点成功 | `.head.json` ← 新节点 seq |
| `head-set` 端点调用 | `.head.json` ← 指定 seq |
| 读 head 时文件缺失 / 坏 JSON / 指向不存在的主行 | 退回 `_last_node_seq(entries)` |

**parent 取值优先级**（`commit()` 与 `save_commit()` 一致）：

1. 请求体显式给了 `parent`（agent 通道等）→ 用之，且必须存在于索引主行，否则视为未给
2. `.head.json` 的 seq
3. `_last_node_seq(entries)`（索引末条主行）

**新增端点**：

```
POST /hana_bridge/history-head-set
body: { workflow, workflowId?, workflowPath?, workflowTemporary?, seq, at? }
200 → {"ok": true, "seq": 12}
400 → {"ok": false, "error": "missing_workflow" | "missing_seq" | "seq_not_found"}
```

`seq` 必须指向索引里存在的主行（无 `mergeInto`）；否则 400 `seq_not_found`。

**`history-list` 响应增加字段**：

```json
{ "ok": true, "entries": [...], "badLines": 0, "head": { "seq": 12, "at": "..." } }
```

`head` 为 `null` 表示无 HEAD（空历史 / 无法定位）。

### 3.3 前端改动（`app/bridge/js/hana-bridge-20243001.js`）

1. **`reportHistoryCommit`**：删除 `fetchAuthoritativeHeadSeq()` 的优先逻辑。用户提交路径**不再传 `parent`**，完全交给后端按 `.head.json` 决定。保留显式 `parent` 的透传（agent 通道可能用到）。
   `fetchAuthoritativeHeadSeq()` 函数本身删除（无其它调用方），或保留但不再被调用——二者择一，以不留下死代码为准。

2. **回跳成功**（`historyRollbackExecute` 内 `loadGraphData` 之后）：调用 `history-head-set` 把后端 HEAD 设为回跳目标 seq；
   保留现有 localStorage 写入作为纯 UI 缓存，但**不再作为 parent 来源**。
   调用失败不影响回跳成功，但要在控制台留痕（不再静默全吞）。

3. **小黄点**：`historyTreeRenderTree` 改为使用 `historyTreeRefresh` 缓存的 `data.head`，不再调 `historyHeadGet()`。
   即：`historyTreeRefresh` 里存 `historyTreeHead = data.head || null`，渲染时读它。

4. `historyHeadGet()` 若改造后无调用方，一并删除，避免留半死不活的旧路径。

### 3.4 镜像同步：`app/lib/commit-graph-lanes.mjs`

线上泳道算法已于 2026-10-22 重写为「单遍插入式分配」（`assignLanesRaw` + `countCrossings` / `countLaneHops` / `scoreOf`），
仓库 lib 版仍是 10-14 的旧实现（父泳道正下方插入）。必须同步，且 `commit-graph-lanes.test.mjs` 断言跟着改。

## 五、验收标准

**C（后端）**
- 新建 `.head.json` 于历史目录；新建节点后 head 跟随；merge 后 head 不变。
- `commit()` 在无显式 parent 时，parent 取 `.head.json`；`.head.json` 缺失时退回末条。
- 回跳设 head 后提交，索引 parent = 回跳目标（真分叉）。
- `list_commits` 返回 `head` 字段，且与 `.head.json` 一致。
- 单测覆盖：正常/缺失/坏 JSON/指向已删 seq 四种情形。

**D（前端）**
- 提交请求体不再带 parent。
- 回跳成功后发出 `history-head-set`，body 的 seq = 回跳目标。
- 渲染小黄点时使用 `data.head.seq`，回跳刷新后小黄点落到目标节点。
- 桥语法检查 `tools/check-bridge-syntax.mjs` 通过。

**B（lib）**
- `node app/lib/commit-graph-lanes.test.mjs` 通过。
- 与桥内联版逻辑逐条一致（含根泳道奇偶方向规则）。

**F（真机）**
- 回跳到中间节点 → 编辑 → 运行 → 提交树出现第二条泳道，新节点在父泳道相邻位置。
- 小黄点跟随回跳目标。
- 出图缩略图仍绑定到正确提交（不复活 2026-10-22 的 bug）。

## 六、风险与取舍

- **历史无法回填**：已产生的线性 parent 是既成事实，改完只对后续提交生效。
- **`.head.json` 与索引不同步**：若用户手工删改历史目录，head 可能指向不存在的 seq → 已有兜底（退回末条）。
- **跨标签页**：后端 HEAD 是 per-workflow 单值，两个标签页同时编辑同一工作流会互相拉扯 HEAD。这属于正确语义（HEAD 只有一个），不额外处理。
- **2026-10-22 的预览图修复不可回归**：验收项 F 最后一条专门守这个。
