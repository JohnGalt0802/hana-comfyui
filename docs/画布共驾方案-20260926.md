## 0. 一页摘要

**要解决的问题**：现在 agent 提交工作流是「盲提交」——它不知道画布上有什么、人刚改了什么；反过来，人也不知道 agent 动了哪里。共驾的含义是：**agent 和人共用同一张画布、同一份图状态**，双向可见。

**三条结论（先给判断）**：

1. **唯一可行路径 = ComfyUI 自有扩展机制**（custom node + `WEB_DIRECTORY` + `app.registerExtension`）。M10 之后工作区 iframe 直连 `127.0.0.1:8188`，是跨源的；壳页和 relay 都够不着画布里的 `window.app`。只有 ComfyUI 前端自己加载的扩展跑在 8188 源下，能读 `window.app.graph`。
2. **这条路径的唯一代价：要往用户的 ComfyUI 安装里放一个包**（`custom_nodes/hana_bridge/`）。实测 ComfyUI **没有**「指定额外 custom_nodes 目录」的启动参数（`--whitelist-custom-nodes` 只在 `--disable-all-custom-nodes` 时挑目录，不是加目录；`--base-directory` 是整体重定向，代价太大），所以放 `custom_nodes/` 是唯一现实路径。**这一条要你点头才动。**
3. **通道不另开端口**：前端有 CSP 会拦外部 `ws://`，所以不复用 relay 直连前端；改走「前端 ↔ ComfyUI 自带 `/ws` ↔ Python 路由 ↔ relay」。

**分期**：P1 只做「感知」（只读，零副作用），跑通再谈「写入」。

## 1. 动机与边界

### 1.1 为什么值得做

现状是两套割裂的东西：

- agent 侧 `submit`：拿 API 格式工作流去提交，**看不见画布**；
- 人侧工作区：在画布上拖节点、改参数，**agent 不知道**。

后果很具体：agent 的建议基于「它自己拼的工作流」，不是「你屏幕上那张图」；你想让 agent 帮你，得先把画的图导成 API 格式喂给它。

共驾之后，agent 读的是**你正在看的那张图**；agent 改的东西**你立刻看得见**，也能 Ctrl+Z 回退。

### 1.2 agent 能力面（要做的）

| 类 | 能力 | 底层（实测，见 §3） |
|---|---|---|
| 感知 | 读图结构（节点 / 连线 / widget 值） | `window.app.graph.toJSON()` |
| 感知 | 读当前图的可提交形态 | `app.graphToPrompt()` → `{workflow, output}` |
| 感知 | 读执行到哪一步 | `api.addEventListener('executing'/'progress'/'executed')`（`executing` 的 detail = 节点 id） |
| 感知 | 读历史 / 队列 | `api.getHistory()` / HTTP `/queue` |
| 修改 | 加 / 删节点、连线、改参数 | `LiteGraph.createNode` → `graph.add` → `node.connect` / `graph.removeNode` / widget 直写 |
| 执行 | 提交（等效点 Queue）/ 中断 | `api.queuePrompt(n, {workflow, output})` / `api.interrupt()` |
| 文件 | 读 / 存工作流 | `api.getUserData` / `api.storeUserData` / `api.listUserDataFullInfo` |

### 1.3 agent 边界（不做的）

- **不做**像素级渲染 / DOM 操作 / 鼠标键盘模拟 —— agent 读结构化 JSON，不"看"像素。
- **不做**静默写入：改画布前先读一次确认最新状态，不盲写。
- **不碰** ComfyUI 源码与前端打包产物（零改动，项目铁律）。
- **不建**第二份图状态 —— 读的就是 `window.app.graph` 那一份，杜绝状态分裂。

### 1.4 与现有 `submit` 的关系

两者并存、各管一路：`submit` 面向自动化与无人值守（老路径照走，定时任务也靠它）；`canvas` 面向「和人共驾」。`canvas` 在能力上是 `submit` 的超集加上"看得见"。

## 2. 架构与依据

### 2.1 为什么不是 relay 注入（v1 路线已作废）

9-23 稿设计的是「relay 代理前端 HTML 时 append 一段 `<script>`」。**M10 之后这条路死了**：工作区 iframe 为了绕开扩展脚本绝对路径 403，改成**直连 8188**，于是跨源 —— 壳页拿不到 `contentWindow`，relay 也不再代理 HTML，没法往响应里塞脚本。

剩下唯一的入口：**让 ComfyUI 自己加载我们的 JS**。

### 2.2 总体链路

```
agent：comfyui(action="canvas", op=...)
   ↓
App 路由：/comfyui-hana/canvas
   ↓
relay：fetch → http://127.0.0.1:8188/api/hana_bridge/call
   ↓
custom node（Python，aiohttp 路由，挂在 PromptServer.instance.routes）
   ↓ PromptServer.instance.send_sync("hana_bridge.call", {id, op, args}, sid)
ComfyUI /ws（自带通道，前端本来就连着）
   ↓ api.addEventListener("hana_bridge.call", ...)
前端 extension（js，跑在 8188 源）
   ↓ 直接读写 window.app.graph
人面前的画布（同一份图）
   ↓ 回传：api.fetchApi("/hana_bridge/result", {id, ok, payload})
Python 侧 asyncio.Future 回填 → 原路返回
```

### 2.3 三个候选通道，选 B

| 方案 | 评价 |
|---|---|
| A. extension 直连 relay 的独立 WS | ✗ 前端 CSP（`connect-src`）拦外部 `ws://`，改不掉 |
| B. **走 ComfyUI 自带 `/ws` + Python 路由** | ✓ 同源、无 CSP 问题、不开新端口；官方机制 |
| C. relay 注入 HTML | ✗ 跨源后不适用（§2.1） |

### 2.4 桥的握手（B 的关键细节，已对源码核实）

1. 前端 extension 在 `setup()` 里 POST `/hana_bridge/hello`，带上 `api.clientId` → Python 记住「当前活跃前端」。
2. relay 调 `/hana_bridge/call` 时，Python 生成 `reqId`，用 `send_sync(event, data, sid)`（**签名就是这个顺序**）把指令发给该 sid，等前端 `POST /hana_bridge/result` 回填（`asyncio.Future` + 超时，默认 5s）。
3. 超时 / 无前端 → 明确报错（`no_frontend` / `timeout`），不静默返回空。
4. **路由前缀**：`server.py` 会把自定义路由额外挂一份 `/api` 前缀（`routes.route(m, "/api"+path)`），而前端 `api.fetchApi("/x")` 正好请求 `/api/x` —— 两侧天然对上，不用手工拼接。

多标签页：先取最近上报的 sid；多前端路由留后续。

### 2.5 事件（P2）要分清两种

- **执行事件**（executing / progress / executed）：relay **已经能拿**——它自己连着 `/ws`（M0–M4 就建好的代理与 clientId 配对）。P2 只是把它接成 agent 可读的流。
- **画布编辑事件**（人加了节点、改了参数）：ComfyUI 的 `/ws` **不广播**，必须由 extension 主动上报（`api.fetchApi("/hana_bridge/event", ...)` → Python 缓存 → relay 取）。这是 P2 的真正增量。

## 3. 实测 API 清单（本机 v0.37.0 / 前端 1.53.6）

> 来自 `docs/调研-前端扩展API-20260926.md` 的一级证据（前端包内 403 个 `.js.map` 内嵌原始 TS 源码）。**下面几条修正了 9-23 稿的错误。**

| 用途 | 实测写法 | 9-23 稿的错误 |
|---|---|---|
| 读图（UI 格式） | `window.app.graph.toJSON()` | — |
| 读可提交格式 | `app.graphToPrompt()` → **`{workflow, output}`** | 写成返回 `[prompt, outputs]` |
| 提交 | `api.queuePrompt(number, {workflow, output})` | 写成直接 POST `/prompt` |
| 加节点 | **`LiteGraph.createNode(type, title?, options?)`** + `graph.add(node)` | 写成 `app.createNode`（不存在） |
| 连线 | **`node.connect(outIdx, targetNode, inIdx)`** | 写成 `graph.connect` |
| 删节点 | `graph.removeNode(node)` | 写成 `graph.remove` |
| 改参数 | `node.widgets.find(w => w.name === x).value = v` | ✓ 一致 |
| 存 / 读工作流 | `api.storeUserData` / `api.getUserData` | 写成 `saveUserData`（不存在） |
| 执行事件 | `api.addEventListener('executing'\|'executed'\|'progress', ...)` | — |
| 全局 | `window.app` 仍在（`GraphView` 内 `window.app=Z`），**但 setup 之前不存在**；`LiteGraph` 挂全局 | 稿中假设随时可用 |

**扩展注册**：`app.registerExtension({name, setup(){}, init(){}, nodeCreated(){}, ...})` —— 17 个 hook，`app` 恒为最后一个实参；`name` 必填且唯一。原型 hijack 已被官方标 Deprecated，只用官方 hook。

**前端产物结构**：`static/scripts/*.js` 与 `static/extensions/core/*.js` **全是 shim**（转发到 `window.comfyAPI.<ns>.<export>`，内部模块带 "not part of the public API" 警告）。公开扩展面是 `window.comfyAPI`（构建期注入，约 90 个命名空间）。

### P0 · 核验（不动用户环境，约半小时）

- **产出**：把本方案里所有「推断」转成「实测」。

### P1 · 只读桥（感知）—— 推荐的第一件实事

> **2026-09-26 已实施并跑通**（实读 10 节点 / 10 连线，含 pos/size/widgets；实测与四个坑见 `docs/M12-画布共驾-P1记录.md`）。
- 建 `hana_bridge` 包：`__init__.py`（只导出 `WEB_DIRECTORY`）+ `js/hana-bridge.js` + Python 路由。
- 只开 3 个动作：`canvas.get`（图结构）、`canvas.prompt`（可提交格式）、`exec.running`（当前节点）。
- relay 加转发端点；App 加 `comfyui(action="canvas", op="get"|"prompt"|"running")`。
- **验收**：你在画布上拖几个节点，agent 读出来的跟你看到的一模一样。

### P2 · 事件（实时感知）
- 执行事件接成流（relay 已有基础）。
- 画布编辑事件由 extension 上报，agent 能知道"人刚动了哪里"。

### P3 · 写入（改画布）
- 加 / 删节点、改参数、连线；每次改动可回退（LiteGraph 自带 undo）。
- 可见性：改动前后 agent 要说明改了什么。

### P4 · 闭环（读 → 建议 → 改 → 跑）
- 典型场景：agent 读你的图 → 指出「这个 steps 太低」→ 你点头 → agent 改 → agent 跑 → 你看出图。

**判断**：**自研一个薄桥（约 200 行）**——理由是它要接 Hana 原生工具面、复用现有 relay/App 架构、避免引入 MCP 依赖层；但**先读 artokun 的实现**，不重造别人已解出的部分。

### 6.1 补充：两个方案的详读结论（2026-09-26 补）

> §6 表格写于方案初稿。下面是把两个社区方案的 README 读完后（外加 CSP 实证）的更新，**artokun 的定位以本小节为准**。

**artokun/comfyui-mcp-panel —— 架构与我们几乎同构，但已停止维护**

```
panel（custom node，侧栏 tab）⇄ loopback bridge（默认 ws://127.0.0.1:9199）⇄ comfyui-mcp orchestrator（后台）⇄ 图
```

- agent 跑在**用户自己的 Claude / ChatGPT 订阅**上（`npx -y comfyui-mcp@latest connect`），无 API key。
- 操作面是**固定的 `panel_*` 白名单**（约 40 个动作），README 明确 "no eval, no DOM access"：不给万能 JS 执行。
- 覆盖度：读图（outline / query / subgraph / errors）、加删节点、连线、改 widget / property、移动缩放改名改色折叠、subgraph 进出、分组、**`panel_screenshot`（把画布渲染成 PNG 给 agent 自检）**、工作流 tab 管理、一句话加载整图、运行、画布视图、经 Manager 装节点 + 重启、**`panel_ask`（向人出题、等人选）**、`panel_set_todo`。
- **每个图改动都走 LiteGraph change tracking → 原生 Ctrl+Z 可撤销**；另有 per-turn 快照、`/revert`、double-Esc 回滚。破坏性动作（`panel_clear`、`panel_restart_comfyui`）弹确认卡。桥只绑 `127.0.0.1`。
- **现状：已停止维护**。官方出了 Comfy Agent + Comfy MCP 后，作者判断社区项目比不过官方深度集成，**仓库 2026-10-09 归档**。
- **可借鉴四处**：① 白名单式工具面（不做万能 JS）；② change tracking + per-turn 快照做撤销；③ `panel_ask` 这类「agent 向人请示」的交互原语（共驾的关键）；④ 每次编辑出活动卡的可见性设计。
- **不能照搬的原因**：它的 agent 是「住在 ComfyUI 侧栏里的另一个 agent」；我们要的是**让 Hana 的 agent 多一双眼睛**，agent 的身份、记忆、工具面都在 Hana 这边。

**ComfyUI-Copilot（AIDC-AI，5.5k★，ACL 2025，MIT）—— 定位不同，但是需求来源**

- 它是**给人用的工作流开发助手**：文字生成工作流、**一键 debug**（自动定位错误 + 修复建议 + 缺模型提示下载）、按描述改写工作流、GenLab 批量调参对比、节点 / 模型 / 下游推荐。
- 安装方式与我们一致（`custom_nodes/` + `pip install -r requirements.txt`），印证「放 custom_nodes」是社区标准做法。
- **现状：服务端 API 已停用**（节点查询 / 工作流生成等云服务下线），需自备 API Key + Base URL（可接 OpenAI / LM Studio）。
- 它自己承认两个痛点：**上下文一长就断**、**看不懂 2025-05 之后的新模型**。
- **对我们的意义**：「一键 debug」值得抄成 P2/P3 的需求（relay 已经能拿执行事件与错误信息，够支撑）。

**结论修正**：§6 的主判断不变（自研薄桥）；但「开工前先读 artokun」降级为**可选参考**（它已停维护，价值在设计思路而非依赖）。真正值得看的是它 `panel_*` 的定义方式，以及「请求 → 前端执行 → 结果回传」的超时与并发处理。
