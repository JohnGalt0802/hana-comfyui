## 一、Set/Get 是什么（一手证据）

来源：`custom_nodes/ComfyUI-KJNodes/web/js/setgetnodes.js`（Easy-Use 的 `getset.js` 是同一套命名，`widgets[0]` 同样是名字）。

源码第 583 行原文：

```js
this.isVirtualNode = true; // This node is purely frontend and does not impact the resulting prompt so should not be serialized
```

形态（真实样本 `qwen-image-2.1-workflow.json`）：

```
SetNode #93  key="文案"  inputs=[STRING ← link 949]   outputs=[links: null]
SetNode #95  key="模型"  inputs=[MODEL  ← link 916]   outputs=[links: null]
GetNode #96  key="模型"  inputs=[]                     outputs=[MODEL → link 880]
GetNode #98  key="vae"   inputs=[]                     outputs=[VAE → link 882]
```

- `SetNode`：接一个上游值、按 `widgets_values[0]` 起名，**输出不连任何东西**
- `GetNode`：**没有输入**，按同名 key 从画布取值交给下游
- 配对完全靠名字字符串，一个 Set 可被多个 Get 取

## 二、作用域（关键，决定展开策略）

KJNodes 的查找不是全局平铺，而是带层级：

| 函数 | 搜索范围 |
|---|---|
| `findSetterByName(graph, name)` | 当前图 + **祖先图**（向上找） |
| `findGettersByName(graph, name)` | 当前图 + **后代图**（向下传播） |
| `findAllNodesOfType(graph, type)` | 根图 + 全部子图 |

推论：**Set 在父图、Get 在子图内**是合法用法。子图展开时必须能跨层解析，不能只看子图内部。

## 四、通用规则设计：认形状，不认名字

不把 `SetNode`/`GetNode` 写进引擎。新增规则类型 `pull`，四个字段全部描述**位置**而非节点身份：

```json
{
  "nodeType": "GetNode",
  "rules": {
    "virtual": true,
    "pull": {
      "keyPath":     "widgets_values[0]",
      "fromType":    ["SetNode"],
      "fromKeyPath": "widgets_values[0]",
      "sourcePath":  "inputs[0]"
    }
  }
}
```

- `keyPath` / `fromKeyPath`：key 在两个节点上各自的位置（不同插件可能不同）
- `fromType`：给数组，兼容「一个存、多个取」或多变体的实现
- `sourcePath`：从配对节点的哪个输入取上游

这样 KJNodes、Easy-Use、以及将来任何自创同类机制的插件，都只需写档案，**引擎不动**。

### 解析算法

在连线重写阶段（与原 `passthrough` 同一阶段）：

1. 扫全图，按 `fromType` 收集所有 Set 类节点，建索引 `name → [节点]`
2. 对每个 `pull` 节点，按 `keyPath` 取自己的 key
3. 按索引找候选：
   - 0 个 → 该节点下游连线的上游置空 → 下游走既有「连线缺失」路径（不静默产出坏引用）
   - 1 个 → 取它的 `sourcePath` 所指输入的 link，作为真实源
   - ≥2 个 → **整份拒绝**并报「同名 Set 不唯一」，不猜
4. 类型校验：`GetNode.outputs[slot].type` 与 Set 的输入类型必须兼容（`*` 视为通配）。不兼容 → 拒绝并说明是哪两个类型（**范围已收窄：只校被消费的输出槽，见 §四-补 第 4 条**）

### 边界（必须覆盖）

| 情况 | 行为 |
|---|---|
| Set 没有输入（悬空） | 下游报连线缺失 |
| Get 找不到同名 Set | 下游报连线缺失 |
| 同名 Set 多个 | 整份拒绝，点名候选 id |
| 类型不匹配 | 整份拒绝，点明两边类型 |
| Set 在子图内、Get 在父图 | **不可见**（作用域不允许向上找 Get 的 Set），按「找不到」处理 |
| Get 在子图内、Set 在父图 | 子图展开后可见（子树继承父作用域），正常解析 |
| pull 节点被 mute（**或 bypass**，口径以 §四-补 为准） | 同 mute 规则，恒 skip 不穿透 |

## 四-补、实施口径与设计差异（2026-10-31，以本节为准）

pull 规则最终落地的口径与第四节设计有四处偏差：

| # | 第四节的设计 | 实际实施 | 为什么这么定 |
|---|---|---|---|
| 1 | 「pull 节点被 mute（mode 2）→ 恒 skip 不穿透」 | **mute(2) 与 bypass(4) 都按断链处理**：不取源 + warning，且**永不**进 `passthroughIds` | 取端没有输入槽，「穿透」在它身上只能是断链；bypass 同样是用户显式掐断，语义等同 mute。同一语义的两种状态不能一支有一支没有 |
| 2 | 边界只写了「Set 没有输入（悬空）」 | 配对到的 **Set 节点处于 mute/bypass 时也按「没有值」** 处理 | Set 被掐断，这个名字就没有值；否则会取到一条用户已经断开的线，产物看着正常、接线不是用户画的那样 |
| 3 | `keyPath` / `fromKeyPath` 各是单个路径字符串 | 两者都**允许数组**，按序回退（例 `["widgets_values_named.key", "widgets_values[0]"]`）；`sourcePath` 仍是单值 | 同一个字段在不同插件/版本里，有的写 named 对象、有的只写位置数组；数组回退让一份档案兼容两套写法 |
| 4 | 解析时逐节点做类型校验 | 预扫只负责「同名多候选 → 整份拒绝」；**类型校验只发生在被消费的输出槽上** | 预扫是全局的，孤立的取端没有下游、没有被消费的槽；在那里校验会让一个没人用的脏节点拖垮整份提交 |

**落地与验证（2026-10-31）**：`app/lib/node-adapters/` 下现有 `SetNode.json` / `GetNode.json`（KJNodes）、`easy_setNode.json` / `easy_getNode.json`（Easy-Use），加原有 `reroute.json`；版本抬到 0.18.0。真实语料：`user/default/workflows` 2921 份里含 Set/Get 的 2 份、`D:\BaiduNetdiskDownload\工作流` 137 份 UI 格式里含 Set/Get 的 49 份，「Set/Get 不在 `/object_info`」类拒绝原因全部清零。

## 五、提交树取根图（2026-10-31 更正：前提不成立，本轮不修）

### 5.1 当时的推断（2026-10-30，已作废，留作记录）

#### 现状（代码实证）

`hana-bridge` 第 252-263 行：

```js
function currentWorkflowId() {
  const gid = app && app.graph && app.graph.id;   // ← 优先
  if (typeof gid === "string" && gid.trim()) return gid.trim();
  // 回退 activeState.id
}
```

第 5622 行注释（作者原话）：`litegraph:set-graph 在任意 setGraph 时都触发（进/出子图 openSubgraph …）`。

推论：**进子图后 `app.graph` 换成子图的图，`app.graph.id` 变成子图 id**，历史目录记到子图名下。这不是设计，是副作用。

#### 影响

在子图里编辑后提交 → 历史落到子图 id 目录；退出子图再提交 → 落到主图目录。同一张画布的历史被劈成两处，且用户在提交树上看不到子图那次。

#### 拟修法（最小）

把 `currentWorkflowId()` 的优先级反过来：

1. 先取 `activeWorkflowObj().activeState.id`（来自 workflow store，进子图不变）
2. 取不到再回退 `app.graph.id`

**风险**：需要确认主图时 `activeState.id` 与 `app.graph.id` 一致，否则历史键会整体漂移。这一点**未实测**，实施前必须验证：拿几个已有历史目录的 key 与对应工作流 JSON 顶层 id 对比，确认一致后再改优先级。

### 5.2 更正（2026-10-31，读代码读到赋值点）

**前提不成立：1.57.6 上 `app.graph` 恒为根图，`currentWorkflowId()` 拿到的已经是根图 id。**

证据（`comfyui_frontend_package` 1.57.6 打包件 `static/assets/app-B03VdYVv.js`，压缩单行，检索 `rootGraphInternal`）：

- `get graph(){ return this.rootGraphInternal }`
- `get rootGraph(){ return this.rootGraphInternal || console.error(...), this.rootGraphInternal }`
- `rootGraphInternal` **全文只有一处赋值**，在 `configure()` 里（`this.addAfterConfigureHandler(t), this.rootGraphInternal=t`）
- 进子图换的是 `app.canvas.graph`（`canvas.setGraph`），`app.graph` 不跟着换
- 前端源码同 commit 的 `SubgraphNode.ts` 里也是 `get rootGraph(){ return this.graph.rootGraph }`

桥侧两处都因此天然正确：`currentWorkflowId()`（`hana-bridge-02010800.js:252-263`）读 `app.graph.id` 就是根图 id；快照 `app.graph.toJSON()` 也是整份根图，`definitions.subgraphs` 本来就在里面。

**结论：所谓「同一张画布的历史被子图劈成两处」不会发生，本轮不修，`currentWorkflowId()` 一行不动。** 第 5622 行那句注释说的是 `canvas.setGraph` 会换图，**不等于 `app.graph` 会换**——它不能用来推 `app.graph` 的语义。

### 5.3 备忘（将来若前端改语义）

若将来前端改回「`app.graph` 随 canvas 切换」的旧语义，改读 `app.rootGraph?.id ?? app.graph?.id`，不要动 `activeState`。

与子图的关系（更正后结论不变，且更强）：子图的编辑本来就并进主图历史，快照天然包含 `definitions.subgraphs`，不为子图单开历史目录。

### 6.1 结构事实（2026-10-31 核实，实施前不必重探）

真实样本：`D:\ComfyUI\ComfyUI\user\default\workflows\Qwen-Image-2.1 文生图.json`。

| 事实 | 具体 |
|---|---|
| 实例节点 `type` = 子图 id | 实例的 `type` 等于 `definitions.subgraphs[i].id`（同一个 UUID），实例自身仍保留数字 `id` |
| 实例 `inputs` 只序列化定制/被连线的槽 | 没定制、没接线的槽不落盘；`widgets_values` 是**扁平数组**，另有 `widgets_values_named` |
| `inputNode`/`outputNode` 只有两个键 | `id`（-10 / -20）与 `bounding`；**没有** slots / inputs / widgets_values |
| 槽位在同级 `inputs[]` / `outputs[]` | 条目含 `id` / `name` / `type` / `linkIds` / `localized_name` / `label` / `pos` |
| 运行时重建 | `inputNode.slots` 由同级 `inputs[]` 重建 |

对 v1 的含义：接口对接**不要**去 `inputNode`/`outputNode` 里找槽或取值，一律读 `definitions.subgraphs[i].inputs[]` / `outputs[]`；实例 widget 值对位**一律按名字**（外部连线 → 实例槽 `name` → 子图定义 `inputs[].name` → 定义下标 → `origin_id=-10` 的子图链接 → 内部消费端）：优先实例 `widgets_values_named` 逐键按名对位；无 named 时按「定义序里 -10 链接指向、且内部目标槽带 `widget` 标记」的顺序回退，项数不符拒绝。**不能按任何下标对位**：实例槽、定义输入、`widgets_values` 三轴不同轴（minimax 样本 9 槽 / 15 输入 / 13 项），按下标对位会转换成功、参数全错、零告警；moss 样本 14/14/14 只是恰好对齐（**2026-10-31 二次实施更正**，原因见踩坑 #64）。

方案（分两阶段，不合并实施）：

**v1 — 单层、接口直连、无嵌套**
1. 识别：节点 type 是 UUID 且能在 `definitions.subgraphs` 命中
2. id 重映射：内部节点 id 改为 `s<实例id>:<内部id>`，link id 改为 `s<实例id>L<原linkid>`（字符串，全局唯一——**2026-10-31 实施口径**，初稿写的「子图序号」作废：同一子图被多个实例引用时按实例区分才不串线）
3. 接口对接：外部连到实例的线，改接到 `definitions.subgraphs[i].inputs[]` 对应的内部节点（**不是** `inputNode`，它只有 `id`+`bounding`）；`outputNode` 一侧同理，按 `outputs[]` 对接外部下游
4. 任一步对不上 → 整份拒绝并定位到子图名与节点（完整拒绝边界五条见 §九）

**v2 — 嵌套 + 跨层 Set/Get 作用域**（widget 映射 v1 已做：实例 widget 值按名字对位、沿接口连线写入内部目标节点，见 §九）
- 递归展开，带深度上限（建议 8 层），超限拒绝
- Set/Get 的作用域目前按主图算，子图内 Set 是否应跨层可见待定

**为什么分两段**：id 重映射和 widget 传递是两块独立的坑，一次做完容易做出半成品，而半成品比不支持更伤人（会产出看起来正常但接错线的工作流）。

**结论先行**：v1 已落地（版本 0.19.0），且比 §六初稿多含了 widget 值传递——v2 剩嵌套与跨层 Set/Get 作用域。对 §六初稿的三处更正：id 格式改为 `s<实例id>:<内部id>`（见 §六）、widget 对位改走**按名字**对位（见 §6.1 尾注与踩坑 #64）、拒绝边界从一条扩到七条（见本节）。另有一条结构约束：实例 `inputs` 只是**定义输入的子集**（socket 与暴露的 widget），不得当作全量槽表。

### 9.1 结构事实（实施前取证，与 §6.1 相互印证）

- **`definitions.subgraphs[i].links` 是对象数组，不是数字数组**：每项是完整链接对象（`id` / `origin_id` / `origin_slot` / `target_id` / `target_slot` / `type`）。拿主图 links 的数字数组下标口径去读，全部错位——这是本批最大的坑（踩坑 #61）。
- **接口按特殊 id 直连**：`inputNode.id = -10`、`outputNode.id = -20`。子图 links 里 `origin_id=-10` 的项就是「实例输入 → 内部消费端」，`target_id=-20` 的项就是「内部生产者 → 实例输出」。展开时把这些项消化成外部连线的改接目标，不进产物 links；`-10` 作 target、`-20` 作 origin 的项属结构异常，拒绝。
- **实例 widget 值与内部节点槽的对应——一律按名字**：对位链是「外部连线 → 实例槽 `name` → 子图定义 `inputs[].name` → 定义下标 j → `origin_id=-10, origin_slot=j` 的子图链接 → 内部消费端」。widget 值优先实例 `widgets_values_named` 逐键按名对位；无 named 时按「定义序里 -10 链接指向、且内部目标槽带 `widget` 标记」的顺序回退，项数不符拒绝；named 与位置值分歧拒绝。写值分两路：目标输入已接接口连线 → 写转换器主循环的 named（按 widget 名）与位置值；没接 → 保持内部节点自己的值。**不能按任何下标**：实例槽、定义输入、`widgets_values` 三轴不同轴（minimax 样本 9/15/13），按下标对位会转换成功、参数全错、零告警；moss 样本 14/14/14 只是恰好对齐（踩坑 #64）。另注意：写内部节点时必须按**内部节点自己的 widget 名**定位——实例槽名可能与内部 widget 名不同（如实例 `value_1` → 内部 `value`）。
- **内部节点槽带 widget 标记**：内部节点 `inputs[]` 里被前端的定为 widget 的槽带 `widget: {...}` 标记（socketless 展示件除外），这是「槽证据」路径的判据；无槽证据时回退 object_info 声明序。两条路径都在 `declaredWidgetSlots` 一份实现里。
- **实例 mode**：实例自身也有 mode，2/4（静音/旁路）时 v1 直接拒绝（语义是整棵子树不动，穿透属于 v2 范畴）。

### 9.2 展开口径

入口：`workflow-tools.mjs` 的 `expandSubgraphs(wf, problems, objectInfo)`，在转换器主流程最前面调用；无 `definitions.subgraphs` 或无实例时原样返回（输出与未展开逐字一致）。

- **id 重映射**：节点 `s<实例id>:<内部id>`，link `s<实例id>L<原linkid>`（实例 id 全局唯一，天然防两实例同内部 id 串线）。
- **接口对接**：外部连线 target/origin 命中实例的，按子图 links 里的 ±10/±20 项改接到内部消费端/生产者；子图内部 links 的端点全部重映射后进产物。
- **widget 值**：按名字对位后沿接口连线写入目标节点的 named 与位置值（对位链见 §9.1，踩坑 #64 教训——任何下标口径都会在 9/15/13 这类不同轴样本上把参数写错位且零告警）。named 与位置值分歧 → 拒绝（防静默采用旧值）。`subgraphWidgetIndexOf` 负责目标输入名 → 声明序位置的查找（未知类型/名字不在声明里 → null）；`slotOrderWidgetIndexOf` 只做「未知类型时」的只读现值比对（判异同决定放行或拒绝），**绝不用于写位置**。

### 9.3 拒绝边界（七条，任一条命中即整份拒绝并点名子图名与节点）

1. **嵌套子图**：内部节点 type 仍命中 `definitions.subgraphs` 的 id → 拒绝（v1 只做单层）。
2. **实例 mode 2/4**：实例被静音/旁路 → 拒绝。
3. **widget 无法定位且现值不同**：目标输入名定位不到声明序位置，且接口连线现值与实例 widget 值不同 → 拒绝（值相同则放行）。原则：widget 值要么正确传递、要么整份拒绝，绝不静默产出错参数。
4. **结构异常**：定义缺 nodes/links 数组、内部节点缺 id 或 id 重复、links 缺 id/端点、槽位非负整数检查不过、`-10` 作 target / `-20` 作 origin、接口槽对应多条链接、输入槽被多条链接喂入、槽的 link 字段与链接不一致、输出链接不在生产者输出槽 links 里（links 缺项）——逐条点名。
5. **接线歧义**：外部连线指向实例不存在的输入槽、实例输入槽被多条外部连线指向、连线两端都是子图实例——拒绝。
6. **实例槽名不在定义里**：外部连线指向的实例输入槽 `name` 在子图定义 `inputs[]` 里找不到 → 拒绝（实例 `inputs` 只是定义输入的子集，反向不成立：出现在实例上的槽名必须能在定义里对上号）。
7. **named 与位置值分歧**：实例 `widgets_values_named` 与 `widgets_values` 同名项值不同 → 拒绝（疑似过期 named——外部脚本只改位置值的产物，防静默采用旧值）。

## 十、静音/旁路语义（2026-10-31）

### 10.1 ComfyUI 原生语义对照

| mode | 名称 | 前端行为 | 对提交语义的正确翻译 |
|---|---|---|---|
| 0 | 正常 | 执行 | 正常转换 |
| 2 | 静音（mute） | 断开连线，不执行 | **断链不执行**：相关连线断开，节点不进 prompt |
| 4 | 旁路（bypass） | 按类型把输入穿透到输出，节点自身不执行 | **按类型穿透**：同名输出槽 → 唯一同类型输入槽取源，节点不进 prompt |

此前的实现是「出现任何 mode 2/4 就整份拒绝」——语义上等于替用户判了死刑：用户在画布上把节点静音本意就是「别跑它」，不是「不许提交」（踩坑 #62；旁路漏判导致的接线错误见踩坑 #60）。

### 10.2 实现口径

- **mute（mode 2）**：断链不执行。取端不取源、下游连线一并断开。
- **bypass（mode 4）**：按类型穿透，复用既有 `pickEntry`（按名取源的三元判定）：同名输入槽优先 → 唯一同类型输入槽 → 歧义（多个同类型候选）即拒绝并点名。这与 Set/Get pull 的既有机制是同一条路，不另写一套。
- **未知 mode**：仍拒绝（不能猜）。
- **mode 预扫**：转换前先扫全图 mode，被静音/旁路的节点不再进入后续校验，避免产生「连线缺失」类次生噪音。

### 10.3 `deadWhy` 归因

连线缺失类报错原本只说「link N 缺失」，现在末尾附 `deadWhy(lid)` 归因：这条线断了是因为上游谁（节点 id 与类型）处于什么状态（被静音/被旁路/输出槽无源）。量化效果：连线缺失从 30 升到 46，正是「能走到更深一层并带归因」的表现（见 §八-补2）。

### 10.4 边界

1. **无输入的旁路节点**：bypass 节点没有任何输入可穿透 → 死链，在连线重写块内按 `pickEntry` 逐输出槽实算后归因（无任何输入 / 无同类型输入可穿透）。
2. **歧义映射**：多个同类型输入槽可作穿透源 → 拒绝并点名候选（旁路穿透的歧义拒绝在量化对照里贡献了「其他」类的 10 条，属设计使然）。
3. **未知 mode**：拒绝，不猜。

### 10.5 拒绝归因汇总（`summarizeProblems`）

报错末尾追加一段汇总：`共 N 项阻断，分类：未知类型 a（涉及类型 X ×n…）· 静音/旁路 b · 连线缺失 c · 子图 d · pull e · 其他 f`，并给出建议——未知类型通常是本机没装对应插件（装好重试）；确认是纯前端辅助件的可写适配档案（写法见 `app/skills/comfy-node-adapter/SKILL.md`）。既有报错文案逐字未变，汇总只追加在末尾；未知类型的类型名从既有文案解析，解析不到的条目只进数量不进 Top（宁可少列不编造）。
