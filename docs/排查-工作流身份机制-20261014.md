## 三、机制总结（对 hui 历史的直接意义）

| 用户操作 | id 变化 | 历史（若按 id 为主键） |
|---|---|---|
| 临时画布 → 保存为正式名 | **不变**（rename） | **自动跟随** ✅ 用户报的 bug 自动消失 |
| 画布改名 / 移动 | **不变** | 自动跟随 ✅ |
| 已存文件 → 另存为新文件 | **换新**（saveAs） | 需产品决定（跟 or 新起） |
| 复制画布（duplicate） | 换新 | 新历史 |
| 新建空白 | 新生成 | 新历史 |

**共享 id 现象解释**：id 是 JSON 持久字段，`saveAs` 继承的是"内容快照"的 id（新对象新 id，但**磁盘上被复制/导出导入的文件**会各自保留祖先 id）。故 17 个 `hui-*.json` 共 `9053fa54`、5 个 `minimax_*` 共 `e3f2b845` —— 它们是**文件级同源派生**（各自独立，却共享同一 id）。

## 五、对「换 id 主键」的结论

- **id 比 filename 键更抗漂移**：改名（rename）不换 id，正是本方案要利用的稳定性。
- **不唯一**：5 组共享 id，且当前这些文件**均无历史**，风险为 0；规则需先立（同 id 视为同一画布，或首次分叉 mint 新 id）。
- **有无 id 老画布**：`Qwen21 提示词增强器.json`（顶层 id=None），需路径/名兜底或 mint 回写。
- 桥 `canvas.save`（`hana-bridge-*.js` L2360）当前对"名字变化"一律走 `svc.saveAs` → **会换 id**；而前端原生对临时画布走 rename → **保 id**。**二者不一致，是桥侧要修的点**（对齐前端：临时画布保存应保 id）。
