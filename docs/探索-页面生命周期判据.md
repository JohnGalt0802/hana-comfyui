## 1. Chromium 页面生命周期状态谱系

Page Lifecycle API 正式定义的状态有 **6 个**（不是 4 个，你的列表里少算 `terminated` 与把 `frozen/discarded` 单列）：

| 状态 | 触发条件（进入该态） | JS 侧可观测信号 | 上游来源 |
|---|---|---|---|
| **active** | 页面可见（visible）且拥有焦点（focus） | `document.visibilityState === 'visible'` + 页面有焦点 | [chrome.com page-lifecycle-api](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)（见状态总表）|
| **passive** | 页面可见但**不**拥有焦点（如另一窗口在前） | `visibilityState === 'visible'`，但已 `blur` | 同上 |
| **hidden** | 页面不可见，且未被 frozen / discarded / terminated | `visibilityState === 'hidden'`；`visibilitychange` 事件触发 | [WICG spec](https://wicg.github.io/page-lifecycle/) / [chrome.com](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) |
| **frozen** | 浏览器把隐藏的页面冻结以省 CPU/电量/流量（隐藏→冻结经 `freeze` 事件） | 触发 `freeze` 事件；JS timer、`fetch` 回调等「可冻结任务」被挂起不再执行 | [chrome.com](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) |
| **terminated** | 页面开始卸载并从内存清空（隐藏→终止经 `pagehide` 事件） | `pagehide` 事件；之后无任何任务可启动 | [chrome.com](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) |
| **discarded** | 浏览器为回收资源而卸载页面（通常由 frozen/hidden 经系统启发式进入，**不触发任何事件**） | 丢弃**当时**不可观测；重载后可用 `document.wasDiscarded === true` 判定 | [chrome.com](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) / [WICG spec](https://wicg.github.io/page-lifecycle/) |

### JS 侧关键可观测信号
- **`document.visibilityState`**：取值 `visible` / `hidden`（历史规范还含 `prerender`、`unloaded`，见 [Page Visibility Level 2](https://www.w3.org/TR/page-visibility-2/) 与 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Document/visibilityState)）。
- **`document.wasDiscarded`**：布尔，仅在**页面重载后**为真，用于识别「本页曾被丢弃后重新加载」。[chrome.com](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) 明确：discarded 态本身不可观测，应在隐藏→冻结阶段做准备，在加载时靠 `wasDiscarded` 反应。
- **`freeze` / `resume` 事件**：Chrome 68 起提供（`document.addEventListener('freeze'/'resume', ...)`）。[chrome.com](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)
- **timer 行为**：仅 `frozen` 态会挂起「可冻结任务」（含 timer）；`hidden` 态下 timer 仍可运行（但会被 throttling，见第 2 节）。

## 2. intensive throttling（后台降频，Chrome 88+）

- **规则**：页面处于隐藏态 **超过 5 分钟**、且**静默至少 30 秒**（无声音播放、无用户通知等），浏览器对该页的链式 JS timer 启用「密集降频」——timer 唤醒被限制到**每分钟最多 1 次**。
  - 来源：[Chrome 88 定时器密集降频公告](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)（2021-01-18，明确「隐藏 >5 分钟 + 静默 ≥30 秒」）。
  - 补充：后台标签 timer 唤醒「每分钟 1 次」这一基线在 M87 即引入，[Chromium Blog 2020-11](https://blog.chromium.org/2020/11/tab-throttling-and-more-performance.html)（2020-11-17）。
- **降频时 JS 变量是否保留？——保留。**
  - 降频（throttling）≠ 卸载（unload）。页面仍停留在 `hidden` 态、仍在内存中、JS 执行上下文完整存活，只是 timer 触发频率被压低到 1 次/分钟。
  - 因此：**一个自增计数器（`let n++`）在降频期间不会归零，只是递增变慢（每分钟 +1 而非每 tick +1）**。
  - 推论依据：throttle 公告只描述「限制 timer 唤醒频率」，从未卸载或清空页面；内存/上下文保留是 throttle 与 freeze/discard 的根本区别。来源：[Chrome 88 公告](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)。（变量「保留」本身是该公告语义的直接推论，非独立被取证句；若需逐字出处见文末待核小节。）

## 3. frozen 与 discarded 的区别（核心判据）

| 维度 | frozen | discarded |
|---|---|---|
| 是否仍在内存 | **是**，内存与 JS 上下文完整保留 | **否**，被卸载以回收资源，「不再消耗内存」 |
| JS 能否运行 | 可冻结任务挂起（timer/`fetch` 回调不跑），但上下文活着；`freeze` 回调可跑完 | **任何**任务/事件/JS 都不能跑 |
| 进入时是否发事件 | 发 `freeze` | **不发任何事件**（资源受限下无法先解冻再跑脚本）|
| 计数 `n` 的命运 | **保留**，解冻（`resume`）后继续原值递增 | 重载后**全新 JS 上下文**，`n` 回到初值（通常 0） |
| 观测方式 | `freeze`/`resume` 事件 | 重载后 `document.wasDiscarded === true` |
| 来源 | [chrome.com 状态表](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) | [chrome.com 状态表](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) / [WICG spec](https://wicg.github.io/page-lifecycle/) / [dev.to 解读](https://dev.to/frehner/the-discarded-page-lifecycle-state-4lo6) |

- **结论**：frozen 不丢内存与上下文 → 计数不归零；discarded 是「整页卸载后重载」→ 计数归零，且只能在重载时用 `wasDiscarded` 反推。

## 4. iframe 与页面生命周期的关系

- **iframe 是否参与 lifecycle / 是否被降频？——参与。**
  - 跨源 iframe 若被放进与父页不同的进程、且处于 `display:none` 或不可见状态，会被节流（throttled）。[Edge/Chromium iframe 节流文档](https://learn.microsoft.com/en-us/deployedge/edge-learnmore-iframe-throttling-display)（2023-06-12）。
  - 父页面被隐藏时，子 iframe 跟随进入隐藏态，其 timer 一并被后台降频（iframe 的可见性从属于所在浏览上下文/父页可见性）。
- **iframe 被 `remove()` / 改 `src` 后重挂，上下文是否全新？——是，全新。**
  - WHATWG 规定：「当一个 iframe 元素从文档中被移除，用户代理**必须丢弃（discard）其嵌套浏览上下文**（若有）。」[whatwg/html #1279](https://github.com/whatwg/html/issues/1279)（2016-05-19）。
  - iframe `src`（或 `srcdoc`）属性被设置/变更时，用户代理会对该嵌套浏览上下文**重新加载文档**，等于新文档导航。[HTML5 iframe 规范](https://www.w3.org/TR/2010/WD-html5-20100624/the-iframe-element.html)。
  - 推论：无论是 `remove()` 后重新插入、还是改 `src` 触发重导航，都会产生**新的嵌套浏览上下文 / 新 Document**，JS 执行上下文全新建立 → 该 iframe 内的计数 `n` **归零**。
  - 该推论依据为上述两条规范；「计数归零」由「全新执行上下文」直接推出（独立逐字取证见文末待核）。

## 5. Electron 特有机制

- **`webPreferences.backgroundThrottling`（默认 `true`）**
  - 定义：「是否在页面成为后台时，对动画与 timer 进行节流」。**默认值 `true`**。[Electron WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences)
  - 副作用：它**同时影响 Page Visibility API**——当同窗口内至少一个 webContents 关闭了 backgroundThrottling 时，整个窗口及其余 webContents 都不再被节流/交换帧。[同上](https://www.electronjs.org/docs/latest/api/structures/web-preferences)
- **设为 `false` 的效果**
  - 当 `backgroundThrottling` 关闭时，**即使窗口被最小化、被遮挡（occluded）或隐藏，`visibilityState` 仍保持 `visible`**（不会被报告为 hidden），且动画/timer 不被节流。[Electron BrowserWindow 文档](https://electronjs.org/docs/latest/api/browser-window)
- **`webContents.setBackgroundThrottling(allowed)`**（实例方法）
  - 存在该方法（参数为布尔 `allowed`），配合 `contents.getBackgroundThrottling()` 读取当前值。[Electron WebContents 文档](https://www.electronjs.org/docs/latest/api/web-contents)（经检索摘要确认；该页 extract 在本环境截断，逐字出处见文末待核）。
- **BrowserWindow 隐藏 / minimize 时渲染进程的 timer 待遇**
  - 默认（`backgroundThrottling: true`）：窗口最小化/隐藏/被遮挡 → 页面临台化 → timer 与动画被节流（叠加 Chromium 自身的隐藏态降频），`visibilityState` 变为 `hidden`。
  - 设为 `false`：上述节流不发生，`visibilityState` 保持 `visible`。
  - 来源：[WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences) / [BrowserWindow](https://electronjs.org/docs/latest/api/browser-window)
- **Electron 层是否有主动 discard / 销毁 frame 的机制？——本次检索未发现。**
  - 未证实 Electron 提供独立的、主动丢弃页面/销毁 frame 的 API；Electron 复用 Chromium 的页面生命周期与帧管理。「标签页自动丢弃（Tab Discarding / Memory Saver）」是 **Chromium 层**功能（经 `chrome://discards` 或系统内存压力触发），见 [Chrome 标签丢弃公告](https://developer.chrome.com/blog/tab-discarding)（2015-08-31）与 [Chromium OS 标签丢弃设计文档](https://www.chromium.org/chromium-os/chromiumos-design-docs/tab-discarding-and-reloading/)。
  - **标「未证实」**：「Electron 没有独立主动 discard 机制」系基于「Electron 文档中未检索到此类 API」的负向结论；如需强断言，建议再查 Electron `webContents`/`BrowserWindow` 全量方法清单确认无 `discard()` 之类接口。

## 6. 判定表：现象 → 机制

| 观察到的现象 | 指向的机制 | 是否丢内存/上下文 | 计数 `n` 命运 | 可观测判据（去确认） |
|---|---|---|---|---|
| 记录**变稀但计数继续递增**（如从每 100ms 一次降到每分钟约 1 次，值仍累加） | 后台 **timer 降频**（intensive throttling，Chrome 88+；或 Electron `backgroundThrottling:true`） | **否**，页面仍在内存、上下文存活 | **保留并继续递增**（只是变慢） | `visibilityState==='hidden'`；无 `freeze`/`resume`；`wasDiscarded===false` |
| 记录变稀、且出现 `freeze` 事件后暂停，之后 `resume` 恢复 | 进入 **frozen** 态（任务挂起） | **否**，内存/上下文保留 | **保留**（冻结期不递增，解冻续增） | 监听 `freeze`/`resume`；`visibilityState` 仍 `hidden`；`wasDiscarded===false` |
| 记录**断档**，恢复后计数**归零**（从初值重来） | 页面被**重载**：`discarded` 后重载 / 正常导航 / renderer 崩溃重启 | **是**，原上下文销毁、新上下文建立 | **归零**（回到初值） | 重载后 `document.wasDiscarded === true`（仅当曾被丢弃）；或检测到完整 `load`/`DOMContentLoaded` |
| iframe 内记录断档、计数归零，而父页其它状态正常 | iframe 被 `remove()` 或 `src` 变更 → **新嵌套浏览上下文** | 该 iframe 的上下文**重建** | 该 iframe 内**归零** | 父页 `wasDiscarded===false`、未触发整页 reload；iframe 触发新 `load` |
| 窗口最小化/隐藏后记录完全正常、计数持续高频递增、`visibilityState` 仍 `visible` | Electron `backgroundThrottling: false`（关掉了后台节流） | 否 | 保留 | `visibilityState` 不因最小化变 `hidden`；Electron 侧 `getBackgroundThrottling()===false` |
| 隐藏若干分钟后整页「无征兆消失」，重开标签标题/图标还在但内容重载 | Chromium **discarded**（Memory Saver / 资源压力） | 是 | 归零 | 重开后 `document.wasDiscarded === true`；丢弃当时无事件 |

**一句话判据**：
- 「**变稀但计数不归零**」→ 只是**降频（throttle）或冻结（freeze）**，页面与内存都在，变量保留。
- 「**断档且计数归零**」→ 一定是**新 Document / 新执行上下文被建立**（discarded 重载、iframe 重挂/改 src、导航、或渲染进程崩溃重启），旧变量已消亡。

## 凭常识撰写·来源待核（未用本次检索 URL 直接佐证的推断，勿与正文结论混用）

1. **降频（throttling）期间 JS 变量保留、自增计数不归零**：本结论由「throttle 公告仅限制 timer 频率、不卸载页面」的语义直接推出；严格逐字来源（如「variables are preserved across throttling」）在本次检索中未抓到独立句，建议以 [Chrome 88 公告](https://developer.chrome.com/blog/timer-throttling-in-chrome-88) 全文 + Chromium 源码注释交叉确认。
2. **frozen 保留内存与 JS 上下文**：由 page-lifecycle 状态表「frozen 仅挂起可冻结任务、resume 可恢复」推出；若需逐字「内存保留」表述，建议查 Chromium `PageLifecycleState` 实现注释。
3. **iframe `remove()` / 改 `src` 后计数归零**：由 WHATWG「移除则丢弃嵌套浏览上下文」「改 src 则重新加载文档」两条规范推出「全新执行上下文」，从而变量归零；该「归零」属推论，非规范原文词句。
4. **`webContents.setBackgroundThrottling` / `getBackgroundThrottling` 方法签名**：本次检索仅从搜索摘要确认存在；[WebContents 文档](https://www.electronjs.org/docs/latest/api/web-contents) 的正文 extract 在本环境被截断，建议重新 extract 该页核对方法签名与版本引入点。
5. **Electron 无独立主动 discard 机制**：属负向结论（文档中未检索到对应 API）；如需强断言，应遍历 Electron `webContents`/`BrowserWindow` 全量方法清单确认无主动丢弃/销毁 frame 的接口。
