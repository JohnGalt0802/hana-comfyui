## 一、换代的五个动因

| # | 需求（John 定） | 现在的模型为什么不够 |
|---|---|---|
| 1 | **合并**：同一次触发、仅随机种子变化的多次运行 → 一个提交 | 现在「一次运行 = 一条索引行」，无法表达「一个提交含多次运行」 |
| 2 | **分支**：回跳后改再提交 = branch | 没有 `parent`，只有线性序号，表达不出树 |
| 3 | **四色**：人提交/人保存/agent 提交/agent 保存 | `source` 只有 `user`/`agent`/`unknown`，缺「跑/存」维度；且实测**恒为 user** |
| 4 | **悬停显示变更节点名** | 索引无 delta，算不出「较上次变了哪些节点」 |
| 5 | **存档**：不运行也能存画布 | 没有 `kind="save"`，所有记录都假设「跑过」 |

## 二、新数据模型

### 2.1 提交节点（= `index.jsonl` 一行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `seq` | number | 节点序号，自增，全局唯一 |
| `parent` | number \| null | 父节点 seq；根 = null。**回跳后提交 → 指向被回跳到的节点**（即分支点） |
| `source` | `"user"` \| `"agent"` \| `"unknown"` | 谁触发的（沿用旧字段，语义不变） |
| `kind` | `"run"` \| `"save"` | 跑出来的 / 主动存档的（**新**；旧数据缺省 = `run`） |
| `at` | string | 节点首个 run 的时间（存档即存档时间），ISO8601 |
| `file` | string | 主快照文件名（该节点的画布状态） |
| `nodeCount` / `linkCount` | number | 冗余，供 UI 不必读快照 |
| `blocks` | array | `[{name, source, nodeIds}]` **完整版**（见 2.4 上移） |
| `delta` | object | `{changed:[...], added:[...], removed:[...]}`，相对 `parent`（见 2.5） |
| `sig` | string | **归一化画布签名（忽略 seed 类 widget）**，用于合并判定（见 2.6） |
| `runs` | array | `[{promptId, at, images:[{filename,subfolder,type}]}]`；`kind="save"` 时为空数组 |

### 2.2 四色 = `(source, kind)` 2×2

|  | `kind="run"` | `kind="save"` |
|---|---|---|
| `source="user"` | 人提交 | 人保存 |
| `source="agent"` | agent 提交 | agent 保存 |

UI 编码：色相分「谁」（人=冷色系，agent=暖紫系），形态分「跑/存」（实心 / 空心环）。

### 2.3 快照文件（命名与位置不变）

一个节点一个主快照文件，内容 = 该节点的画布（UI 格式）。`schemaVersion` 1 → **2**。

### 2.4 `blocks` 上移（去冗余）

现状：索引里 `blocks` 是摘要 `{name,nodeCount}`；快照里是完整 `{name,source,nodeIds}`。
新：**索引存完整版**（UI 悬停/树需要 `nodeIds`）；**快照不再重复存 `blocks`**。
兼容：旧索引项缺 `source`/`nodeIds` 时，读侧按缺省处理（`source→"group"`, `nodeIds→[]`）。

### 2.5 `delta` 计算（落盘时算，不留给 UI）

落盘时对比「本节点画布」与「父节点画布」，按**节点 id + widget 值签名**算三类：
- `changed`：id 相同但 widget 值变了 → 记节点 `title`（缺失则 `type`）+ 变化的 widget 名
- `added` / `removed`：新增/删除的节点（记 `title`/`type`）

UI 悬停直接读 `delta.changed` 显示「变更节点名」。父节点快照读不到时不写 delta（`null`）。

### 2.6 合并判定（新运行捕获时）

```
新运行到达：
  1. 取当前画布归一化签名 sig（忽略 /seed/i 的 widget）
  2. 与「最近一个提交节点」的 sig 比：
     相同 → 不新建节点；把 {promptId, at} 追加到该节点 runs[]；回填 images
     不同 → 新建节点；parent = 当前 HEAD
```

- **HEAD** = 当前所在的提交节点（正常连跑时=最近节点；**回跳会改**）。用 `localStorage` per-workflow 记 `headSeq`。
- **seed 类 widget 识别**：widget name 匹配 `/seed/i`（`seed` / `noise_seed` / `rand_seed` 等）。
- 只跟「最近节点」比 → 天然避免「改走又改回」误合并。

### 2.7 `runs[].images` 回填

出图完成后（App 侧 `execution_success` → `fetchResultOutputs`）把该 `promptId` 的产物回填到对应节点 runs 的 images。桥渲染时也可用 `promptId` 实时拉 `/history/{id}` 兜底（P4 先用的就是这条路）。

## 三、存储后端抽象（回应「先切」）

### 3.1 收口原则

探查实测：ComfyUI 原生 userdata **只能整文件覆盖，不能追加**（`index.jsonl` 的命脉是追加写）。前端并发 POST 直写 → **丢行**。故**保留"收口"**：一个单写入者负责索引。

### 3.2 IO 后端接口

`history_store.py` 的**纯逻辑不变**（命名/构造/序号/剥 base64/解析）；把 IO 抽成：

```
read_text(path) / write_text(path, text) / exists(path) / list_dir(path) / makedirs(path)
```

两个实现：
- **`LocalFsBackend`**：`os` 直写（**现状等价，默认**）
- **`UserdataBackend`**：调 ComfyUI `/api/userdata`（**插件版 / 将来**）

### 3.3 提交串行化

收口进程内加 `threading.Lock`，防并发 POST 交错写索引（aiohttp 可能在线程池跑同步 handler，进程内未必天然串行——这条要实测确认，不假设）。

### 3.4 对「先切」的技术修正（须 John 知晓）

John 定「先切」的目标是**将来拆插件不返工**。探查发现「物理全切到前端 userdata」会引入并发丢行。故调整为：

> **P5 把 IO 抽成可插拔后端**（LocalFs / Userdata 两实现），默认走 LocalFs（等价现状、更稳）；Userdata 后端作为插件版实现。

目标一致达成，且不引入并发 bug。

## 四、兼容与迁移

- `schemaVersion` 1 → 2。
- **读旧数据**（不主动改写）：缺 `parent`→null；缺 `kind`→`"run"`；缺 `runs`→由顶层 `promptId`/`at` 构造单元素 runs（含实时拉图兜底）；缺 `delta`→null；缺 `blocks[].source/nodeIds`→缺省。
- 新提交按 v2 写。**不做一次性迁移脚本**（读时兼容即可；真实样本 17 条，兼容成本低于迁移风险）。
